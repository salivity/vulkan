Vulkan Subpass Dependencies and Execution Order

This article explains how Vulkan subpass dependencies establish execution order and memory synchronization between internal passes within a render pass. By configuring source and destination subpass indices alongside specific pipeline stage masks and memory access masks, developers create explicit execution barriers. This mechanism prevents data hazards, ensures determinism across GPU architectures, and enables mobile and tile-based rendering architectures to keep transient data entirely within on-chip memory.

The Role of VkSubpassDependency

In Vulkan, a render pass can be broken down into multiple sequential or parallel phases called subpasses. Subpasses do not automatically execute in sequential order based on their array index; the Vulkan driver may overlap or reorder them unless explicit synchronization is provided.

A subpass dependency is defined using the VkSubpassDependency structure. It acts as an execution and memory barrier constrained to the boundaries of the render pass. It establishes a directed acyclic graph (DAG) where the driver evaluates what work must finish before subsequent work can begin.

Specifying the Dependency Direction

The execution relationship begins with two indices:

  • srcSubpass: The index of the subpass generating the data or finishing work first.
  • dstSubpass: The index of the subpass consuming the data or executing later.

Setting srcSubpass to a lower index and dstSubpass to a higher index creates a forward dependency within the render pass. Vulkan also provides the VK_SUBPASS_EXTERNAL pseudo-subpass identifier, which links commands executing before or after the entire render pass to a specific subpass inside it.

Execution Dependencies via Pipeline Stages

To control the actual order of execution, VkSubpassDependency relies on pipeline stage masks:

  • srcStageMask: Specifies the pipeline stages in srcSubpass that must complete before execution can proceed.
  • dstStageMask: Specifies the pipeline stages in dstSubpass that must stall until the stages specified in srcStageMask have finished.

For example, if Subpass 0 writes color data and Subpass 1 reads that data as an input attachment in the fragment shader, srcStageMask is set to VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT and dstStageMask is set to VK_PIPELINE_STAGE_FRAGMENT_SHADER_BIT. The GPU can execute early pipeline stages (such as vertex fetching and vertex shading) of Subpass 1 in parallel with Subpass 0, but it will block Subpass 1’s fragment shader until Subpass 0 finishes writing color attachments.

Memory Dependencies via Access Masks

Execution ordering alone does not guarantee that memory writes are visible to subsequent reads. A memory dependency must be coupled with the execution dependency using access flags:

  • srcAccessMask: Declares the types of memory operations that must be made available (flushed from local caches) by the source subpass.
  • dstAccessMask: Declares the types of memory operations in the destination subpass that must receive visible (invalidated and re-fetched) data.

Continuing the input attachment example, setting srcAccessMask to VK_ACCESS_COLOR_ATTACHMENT_WRITE_BIT ensures write caches are flushed. Setting dstAccessMask to VK_ACCESS_INPUT_ATTACHMENT_READ_BIT ensures the fragment shader invalidates its read caches and fetches the latest written values.

Managing Attachment Layout Transitions

Subpasses frequently require attachments to change their underlying image layouts (for example, transitioning from VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL to VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL).

When a subpass dependency is defined between two subpasses, the Vulkan implementation automatically schedules and inserts layout transitions between the stages specified by srcStageMask and dstStageMask. The dependency ensures that memory writes are completed before the layout changes and that the layout transition completes before the destination stage attempts to access the attachment.

Performance Impact on Tiled GPUs

Properly specifying subpass dependencies allows Tile-Based Deferred Rendering (TBDR) GPUs, common in mobile hardware, to process multi-pass rendering efficiently. When an input attachment dependency is correctly chained within a single render pass, the hardware can keep the data resident in fast, on-chip tile memory instead of writing intermediate framebuffers out to external VRAM. If dependencies are omitted or misconfigured, the driver must fall back to costly full-memory barriers and VRAM round-trips.
