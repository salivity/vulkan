How Mesa RADV and ANV Implement Vulkan on Linux

This article explores the internal architecture and operational mechanisms of Mesa's open-source Vulkan drivers on Linux, specifically AMD's RADV and Intel's ANV. It breaks down the entire execution pipeline, detailing how the user-space Vulkan API calls traverse the Vulkan loader, undergo intermediate representation and shader compilation via NIR, interact with Linux kernel DRM modules, and ultimately execute on the physical GPU hardware.

The Userspace and Kernelspace Split

Implementing Vulkan on Linux requires dividing responsibilities between user-space libraries and kernel-space drivers through the Direct Rendering Manager (DRM) subsystem. Vulkan is not implemented directly within the Linux kernel; instead, the open-source drivers in the Mesa 3D Graphics Library—ANV for Intel hardware and RADV for AMD hardware—exist purely in user space as Installable Client Drivers (ICDs).

When an application invokes Vulkan functions, it links against the Vulkan Loader (libvulkan.so). The loader reads JSON manifest files located in system directories (such as /usr/share/vulkan/icd.d/) to identify available ICDs. It then loads the corresponding shared library (e.g., libvulkan_radeon.so or libvulkan_intel.so) and builds dispatch tables to route API calls directly to the driver implementation, bypassing loader overhead during performance-critical paths.

The user-space driver handles API validation, state tracking, pipeline compilation, and command buffer generation. Once commands and memory allocations are prepared, the driver communicates with the Linux kernel via ioctl system calls to DRM kernel modules:

  • RADV interfaces with the amdgpu kernel driver.
  • ANV interfaces with the legacy i915 or the modern xe kernel driver.

The kernel drivers are responsible for memory management, hardware scheduling, power management, display output (Kernel Mode Setting or KMS), and enforcing security boundaries between processes.

Shader Translation Pipeline: From SPIR-V to Machine Code

Vulkan applications submit programmable GPU code pre-compiled into standard SPIR-V bytecode. Because modern GPUs do not execute SPIR-V directly, both ANV and RADV rely on Mesa’s shared compiler infrastructure to lower this bytecode into hardware-specific binary machine code.

  1. SPIR-V to NIR: The driver ingests the SPIR-V module and translates it into NIR (New Intermediate Representation), an optimizing, Static Single Assignment (SSA)-based internal representation shared across Mesa.
  2. Core Optimizations: NIR executes architecture-independent optimizations, such as dead-code elimination, algebraic simplifications, constant folding, and loop unrolling.
  3. Hardware-Specific Lowering: NIR lowers generic instructions to conform to the memory layouts, input/output structures, and instruction limits of the specific GPU target.
  4. Backend Compilation:
    • RADV: Primarily uses ACO (AMD Compiler), an optimized, in-tree compiler backend designed specifically for gaming workloads to minimize shader compilation stutter. It translates NIR directly to AMD GCN/RDNA assembly. Alternatively, RADV can route NIR through an LLVM-based backend.
    • ANV: Translates NIR into Intel’s custom intermediate representations (e.g., FS/VS IRs) before processing through Intel’s Gen/Xe backend assembly generators to emit Intel machine instructions.

Memory Management and Buffer Allocation

Vulkan gives applications explicit control over GPU memory through memory types and heaps. When an application queries memory properties via vkGetPhysicalDeviceMemoryProperties, ANV and RADV inspect the hardware capabilities and map them to kernel-managed memory buffers.

Mesa drivers interact with the DRM memory managers—the Translation Table Manager (TTM) in amdgpu and the Graphics Execution Manager (GEM) in i915/xe.

  • When vkAllocateMemory is called, the driver requests a GEM buffer object (BO) from the kernel via an ioctl.
  • For host-visible memory, the driver maps the GEM object into the process’s virtual address space using mmap.
  • For device-local memory (VRAM), the allocation remains accessible exclusively to the GPU, minimizing bus traffic over PCI Express.

The drivers also implement sub-allocators to prevent excessive ioctl calls. Instead of requesting a new kernel buffer for every vkAllocateMemory request, they allocate larger memory blocks from the kernel and parcel them out to the application internally.

Command Buffer Construction and Submission

Vulkan relies on pre-recorded command buffers to achieve low CPU overhead. When an application records drawing or compute operations via vkCmdDraw or vkCmdDispatch, ANV and RADV do not communicate with the GPU immediately. Instead, they write low-level hardware packets directly into ring buffers allocated in user-space memory:

  • RADV writes Command Processor (CP) packets (such as PM4 packets for RDNA/GCN) containing GPU registers, configuration state, and memory pointers.
  • ANV constructs hardware command packets formatted specifically for Intel’s Command Streamer (CS).

Upon vkQueueSubmit, the driver finalizes the command stream and prepares synchronization primitives. Synchronization in modern Linux Vulkan drivers relies heavily on DRM sync objects (drm_syncobj), which abstract kernel DMA fences and timeline semaphores. The driver issues an execution ioctl (such as DRM_IOCTL_AMDGPU_CS for AMD or DRM_IOCTL_I915_GEM_EXECBUFFER2 / DRM_IOCTL_XE_EXEC for Intel), passing the arrays of buffer objects, command offsets, and in/out syncobj handles to the kernel scheduler for asynchronous GPU processing.

Window System Integration (WSI)

To present rendered frames to displays, Vulkan drivers implement Window System Integration extensions (VK_KHR_surface, VK_KHR_swapchain). Mesa provides a centralized WSI layer that RADV and ANV consume.

On Linux, the WSI interacts with display servers via:

  • Wayland: Allocates buffers using DRM FourCC formats through dmabuf, passing buffer file descriptors to the Wayland compositor via the linux-dmabuf protocol.
  • X11 / XCB: Communicates with the X server through the Direct Rendering Infrastructure 3 (DRI3) and Present extensions.
  • Direct-to-Display: Allows the driver to bypass display compositors entirely for VR headsets or embedded displays via DRM/KMS lease protocols.

By decoupling hardware-specific ISA generation from the generic API layer, Mesa's ANV and RADV architectures provide conformant, high-performance Vulkan implementations that maximize hardware utilization while integrating seamlessly with the Linux graphics stack.
