Vulkan Split-Frame Rendering Across Physical GPUs

Split-frame rendering (SFR) is a multi-GPU technique that divides a single target frame into multiple spatial regions, assigning each segment to a different physical graphics processing unit to be rendered in parallel. This guide explores the mechanics of split-frame rendering, compares it to alternate frame rendering, and provides the step-by-step technical process for configuring and executing SFR across multiple physical GPUs using the Vulkan API's native device group architecture.

What is Split-Frame Rendering?

Split-frame rendering divides the screen's viewport—typically horizontally, vertically, or in a checkerboard pattern—into distinct geometric regions. Each physical GPU (pGPU) processes only the primitives and pixels within its assigned scissor or viewport region.

Unlike Alternate Frame Rendering (AFR), where GPUs render entire frames sequentially (GPU 0 renders frame \(N\), GPU 1 renders frame \(N+1\)), SFR introduces virtually no additional input latency because all GPUs contribute to the current frame concurrently. However, SFR requires strict synchronization, redundant geometry processing (as all GPUs must process the scene's vertex pipeline to determine screen-space visibility), and an explicit compositing pass to merge the finished tiles into a single swapchain image.

Vulkan Multi-GPU Architecture

Vulkan supports multi-GPU configurations natively through the VK_KHR_device_group extension (promoted to core in Vulkan 1.1). Rather than creating individual VkDevice handles for each physical card, Vulkan groups compatible GPUs under a single logical device. This enables direct resource sharing, cross-GPU synchronization, and fine-grained command distribution using physical device masks.

Step 1: Enumerating Physical Device Groups

To configure SFR, you must first discover whether the host system contains GPUs linked in a cooperative group.

  1. Call vkEnumeratePhysicalDeviceGroups to retrieve available VkPhysicalDeviceGroupProperties structures.
  2. Inspect the physicalDeviceCount and physicalDevices array within each group. A group must contain two or more physical devices to support multi-GPU rendering.
  3. Verify that the devices support peer-to-peer memory access and presentation by querying vkGetPhysicalDevicePresentRectanglesKHR.

Step 2: Creating a Logical Device Group

Instantiate a single logical device that encompasses all physical devices within the chosen group:

VkDeviceGroupDeviceCreateInfo deviceGroupInfo = {};
deviceGroupInfo.sType = VK_STRUCTURE_TYPE_DEVICE_GROUP_DEVICE_CREATE_INFO;
deviceGroupInfo.physicalDeviceCount = targetGroup.physicalDeviceCount;
deviceGroupInfo.pPhysicalDevices = targetGroup.physicalDevices;

VkDeviceCreateInfo createInfo = {};
createInfo.sType = VK_STRUCTURE_TYPE_DEVICE_CREATE_INFO;
createInfo.pNext = &deviceGroupInfo;
// Specify required queues, layers, and extensions...

vkCreateDevice(targetGroup.physicalDevices[0], &createInfo, NULL, &device);

Step 3: Dividing the Viewport with Device Masks

In Vulkan, each command within a command buffer can be directed to specific physical devices within the group using a bitmask. Bit \(i\) of the mask corresponds to the \(i\)-th physical device index in the device group.

To implement SFR:

  1. Calculate the spatial division of the render target. For a two-GPU horizontal split, GPU 0 handles the top half: \[\text{Rect}_0 = [0, 0, \text{Width}, \frac{\text{Height}}{2}]\] GPU 1 handles the bottom half: \[\text{Rect}_1 = [0, \frac{\text{Height}}{2}, \text{Width}, \frac{\text{Height}}{2}]\]
  2. Use VkDeviceGroupRenderPassBeginInfo chained to VkRenderPassBeginInfo via pNext.
  3. Set deviceMask to activate all participating GPUs for the pass.
  4. Populate deviceRenderAreaCount and pDeviceRenderAreas with the respective VkRect2D dimensions calculated for each GPU. Vulkan will automatically restrict the render area for each physical device according to these bounds.

For finer control outside of the initial render pass setup, dynamically update active execution targets inside the command buffer using:

// Direct subsequent commands only to GPU 0 (bit 0 set)
vkCmdSetDeviceMask(commandBuffer, 0x01);
vkCmdSetScissor(commandBuffer, 0, 1, &topScissor);

// Direct subsequent commands only to GPU 1 (bit 1 set)
vkCmdSetDeviceMask(commandBuffer, 0x02);
vkCmdSetScissor(commandBuffer, 0, 1, &bottomScissor);

Step 4: Compositing and Inter-GPU Transfers

Once the render passes complete, the rendering results must be assembled on the physical GPU managing presentation (typically the GPU connected directly to the display output).

  1. Allocate peer-accessible image memory using the VK_PEER_MEMORY_FEATURE_COPY_SRC_BIT and VK_PEER_MEMORY_FEATURE_COPY_DST_BIT flags retrieved from vkGetDeviceGroupPeerMemoryFeatures.
  2. Issue a cross-device transfer using vkCmdCopyImage with vkCmdSetDeviceMask enabled across source and destination masks. This transfers the rendered half from the secondary GPU's local memory to the primary GPU's frame buffer memory.
  3. Synchronize cross-device operations using VkSemaphore objects configured through VkDeviceGroupSubmitInfo to ensure the blit completes before presentation begins.

Step 5: Presentation

Present the unified frame via the swapchain:

  1. Populate a VkDeviceGroupPresentInfoKHR structure.
  2. Specify the physical device that owns the presentation surface using pDeviceMasks.
  3. Chain this structure to VkPresentInfoKHR and call vkQueuePresentKHR.

By using device masks and device-group-aware render passes, Vulkan allows precise control over spatial load balancing, enabling lower per-GPU execution times without the display latency penalty inherent to temporal multi-GPU alternatives.
