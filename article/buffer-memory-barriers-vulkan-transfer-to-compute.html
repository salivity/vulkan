Buffer Memory Barriers: Vulkan Transfer to Compute

Buffer memory barriers in the Vulkan API serve as the foundational synchronization mechanism to ensure that data written during transfer operations is fully completed, made memory-visible, and safely accessible before compute shader stages attempt to read it. Without explicitly defining these barriers, the asynchronous nature of GPU queues and Vulkan’s weakly-ordered memory model will result in race conditions, where a compute shader reads stale, partially written, or corrupt buffer contents.

Execution Dependencies

In Vulkan, operations recorded into command buffers do not automatically execute in sequential order unless explicitly synchronized. When a buffer copy command (such as vkCmdCopyBuffer) is recorded on a transfer queue, it operates within the VK_PIPELINE_STAGE_TRANSFER_BIT stage. A buffer memory barrier establishes an execution dependency by defining:

  • Source Stage (srcStageMask): Set to VK_PIPELINE_STAGE_TRANSFER_BIT, instructing the GPU to wait until all pending transfer operations have finished execution.
  • Destination Stage (dstStageMask): Set to VK_PIPELINE_STAGE_COMPUTE_SHADER_BIT, preventing compute shaders from beginning execution until the transfer stage requirements are satisfied.

Memory Availability and Visibility

GPU architectures utilize distinct internal caches across different hardware blocks. Completing an operation does not automatically guarantee that modified data has been flushed to a location where another unit can read it. Buffer memory barriers manage memory domain operations via access masks:

  1. Availability Operation (srcAccessMask): Configuring this to VK_ACCESS_TRANSFER_WRITE_BIT forces the GPU to flush any internal caches modified by the transfer copy into a globally available memory domain.
  2. Visibility Operation (dstAccessMask): Configuring this to VK_ACCESS_SHADER_READ_BIT (or VK_ACCESS_UNIFORM_READ_BIT depending on the buffer descriptor type) invalidates the compute unit's local caches, forcing it to fetch the updated data from the available memory domain.

Queue Family Ownership Transfers

If the transfer copy and the compute read are executed on different queue families (for instance, a dedicated transfer queue and a general-purpose compute queue), buffer memory barriers must facilitate a Queue Family Ownership Transfer (QFOT). A buffer cannot be simultaneously accessed by two distinct queue families unless it was created with VK_SHARING_MODE_CONCURRENT, which can degrade performance.

For VK_SHARING_MODE_EXCLUSIVE resources, the ownership transfer requires two matched barriers:

  1. Release Barrier (Transfer Queue): Recorded on the transfer command buffer after the copy operation. It specifies srcQueueFamilyIndex as the transfer queue family and dstQueueFamilyIndex as the compute queue family. The srcAccessMask is set to VK_ACCESS_TRANSFER_WRITE_BIT, with dstAccessMask set to 0.
  2. Acquire Barrier (Compute Queue): Recorded on the compute command buffer prior to dispatching compute work. It uses the same queue family indices, but defines srcAccessMask as 0 and dstAccessMask as VK_ACCESS_SHADER_READ_BIT.

These two barriers must be chained across queue boundaries using a Vulkan semaphore (such as a binary or timeline semaphore) to ensure the release operation completely executes before the acquire operation begins.

Preventing Read-After-Write (RAW) Hazards

The primary role of these combined operations is the elimination of Read-After-Write (RAW) data hazards. By using VkBufferMemoryBarrier within vkCmdPipelineBarrier, developers ensure that the transfer pipeline stage fully finishes, the modified memory ranges are flushed, the destination caches are invalidated, and proper ownership is handed over, guaranteeing strictly ordered and coherent data access for compute workloads.
