How glslang and DXC Handle Vulkan SPIR-V Capabilities

When compiling shaders for Vulkan, neither glslang nor the DirectX Shader Compiler (DXC) performs dynamic runtime queries against a physical GPU. Instead, both compilers rely on ahead-of-time static analysis, language-level extensions, and user-supplied target environment flags to declare required SPIR-V capabilities (OpCapability). The generated capabilities represent a static contract that the Vulkan runtime validates when the application creates a shader module on the host device.

Static Emission Versus Runtime Querying

Compilers operate independently of the Vulkan runtime execution environment. A compiler cannot directly query VkPhysicalDeviceFeatures or vkGetPhysicalDeviceFeatures2 to inspect what the host GPU supports.

Instead, SPIR-V capabilities are handled through a rule-based emission pipeline:

  1. Feature Inference: When syntax, types, or intrinsics in the source code require specific hardware functionality, the compiler implicitly attaches the corresponding OpCapability.
  2. Explicit Target Constraints: Command-line flags configure the compiler with a maximum allowable SPIR-V and Vulkan environment version, constraining what capabilities can be legally emitted.
  3. Driver-Side Validation: The actual "query" step occurs when the host application passes the compiled bytecode to vkCreateShaderModule or pipeline creation. The Vulkan driver checks the module’s declared OpCapability instructions against the features enabled on the VkDevice.

Capability Handling in glslang

glslang is the reference Khronos compiler for GLSL and HLSL to SPIR-V. It manages capabilities using direct source mappings and target environment flags.

1. Target Environment Configuration

Using the --target-env flag (such as --target-env vulkan1.2 or --target-env vulkan1.3), developers specify the baseline environment. glslang uses this target to determine:

  • Which SPIR-V specification version to target (e.g., SPIR-V 1.5 for Vulkan 1.2).
  • Which capabilities are core to that version versus which require optional extensions.

2. Source-Level Directives

In GLSL, features often correspond to language extensions declared via preprocessor directives:

#extension GL_EXT_shader_explicit_arithmetic_types_int64 : enable

Enabling this extension signals glslang to permit 64-bit integer types and automatically inject OpCapability Int64 into the SPIR-V preamble.

3. Automatic Instruction-Based Injection

glslang traverses the Abstract Syntax Tree (AST) during code generation. If an operation inherently requires a capability, glslang adds it automatically:

  • Declaring a 16-bit float introduces OpCapability Float16.
  • Using image gather operations introduces OpCapability ImageGatherExtended.
  • Ray tracing stages introduce OpCapability RayTracingKHR.

Capability Handling in DXC

DXC uses a Clang-based backend to translate HLSL into SPIR-V when invoked with the -spirv switch. Its handling of capabilities closely mirrors glslang but adapts to HLSL shader models and Microsoft's intrinsic system.

1. Target Version and Extension Control

DXC controls the output target via specialized flags:

  • -fspv-target-env=vulkan1.X: Sets the target Vulkan environment version.
  • -fspv-extension=...: Explicitly allows or disallows specific SPIR-V extensions (e.g., -fspv-extension=SPV_KHR_ray_tracing).

If a shader requires an extension that has not been permitted via flags, DXC halts compilation with an error rather than emitting an unauthorized capability.

2. Shader Model to Capability Mapping

DXC maps HLSL shader models (-T <profile>, such as cs_6_6) to corresponding SPIR-V capability sets. For example:

  • HLSL Wave Intrinsics map directly to Vulkan subgroup capabilities, such as OpCapability GroupNonUniformBallot or OpCapability GroupNonUniformArithmetic.
  • Ray-tracing intrinsics (TraceRay()) automatically trigger OpCapability RayTracingKHR.
  • Explicit 16-bit native types (e.g., float16_t) trigger OpCapability Float16 and require the -enable-16bit-types flag.

Summary of Differences

Feature glslang DXC
Primary Input GLSL (Reference) / HLSL HLSL
Target Control --target-env vulkanX.Y -fspv-target-env=vulkanX.Y
Language Triggers #extension directives and type usage Shader Model selection (-T) and HLSL intrinsics
Extension Guards Implicit via supported extensions Explicit via -fspv-extension parameters
Hardware Interrogation None (Static emission only) None (Static emission only)

Both compilers emit all required OpCapability instructions at the top of the SPIR-V binary. If the target Vulkan device does not support every declared capability when loading the binary, the Vulkan implementation returns VK_ERROR_FEATURE_NOT_PRESENT. Application developers are responsible for ensuring that the capabilities generated by either compiler align with the features queried and enabled on the target VkDevice.
