Early Fragment Testing in Vulkan Explained

Early fragment testing optimizes the Vulkan graphics pipeline by executing depth and stencil operations before fragment shader invocation rather than after it. In complex 3D scenes, occluded geometry frequently causes overdraw, consuming valuable GPU cycles on pixels that will never be visible on the final screen. By performing coverage and depth checks prior to shading, Vulkan allows the GPU to discard occluded fragments immediately, drastically reducing memory bandwidth consumption and bypassing unnecessary mathematical computations in the fragment shader.

The Problem of Late Fragment Testing

In the traditional graphics pipeline, fragment processing follows a standard sequence: primitive assembly, rasterization, fragment shader execution, and finally per-fragment operations (depth and stencil testing). Under this default flow, every generated fragment invokes a fragment shader to compute lighting, texture lookups, and material properties.

If multiple primitives overlap in screen space, the fragment shader executes for each overlapping layer. When an opaque surface closer to the camera renders after a distant surface, the initial calculations for the distant surface are completely overwritten during the late depth test. This redundancy is known as overdraw, and in scenes with heavy fragment shader logic, it severely degrades frame rates.

How Early Fragment Testing Solves Overdraw

Early fragment testing relocates the depth and stencil tests to occur immediately after rasterization and before fragment shader execution.

When a triangle is rasterized, the GPU evaluates the fragment's interpolated depth against the existing value in the depth buffer:

  1. Depth Test Passes: If the fragment is closer to the viewer than the existing depth buffer content, it is cleared for shading. The GPU executes the fragment shader and updates the depth buffer accordingly.
  2. Depth Test Fails: If the fragment is occluded by existing geometry, the hardware terminates the fragment immediately. The fragment shader never executes, preventing the GPU from running texture fetches, arithmetic logic, and register allocations for an invisible pixel.

To maximize this optimization, applications typically render opaque geometry sorted in front-to-back order or utilize a depth pre-pass. When rendered front-to-back, the nearest surfaces write to the depth buffer first, allowing all subsequent occluded geometry to fail early depth tests quickly.

Hardware Control and GLSL Directives in Vulkan

Modern GPUs support early fragment tests implicitly at the driver level, but certain operations within the fragment shader can invalidate this automatic optimization. If a fragment shader writes to gl_FragDepth, uses the discard instruction, or modifies external memory through storage buffers or storage images, the GPU cannot safely evaluate depth beforehand without risking incorrect rendering or broken side effects. In such cases, the GPU defaults back to late fragment testing.

Developers can enforce early tests explicitly in their SPIR-V shaders by declaring the execution mode in GLSL:

layout(early_fragment_tests) in;

When this layout qualifier is present, Vulkan guarantees that depth and stencil tests occur before shader execution. If the test fails, side effects—such as storage buffer writes—are completely skipped because the shader invocation is cancelled.

If a shader modifies gl_FragDepth but still desires early optimization, extensions like conservative depth (depth_greater, depth_less) can be specified. This informs the hardware of the bounds of the depth modification, enabling the GPU to perform partial early depth rejection while still allowing shader-controlled depth adjustments.
