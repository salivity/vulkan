Non-Temporal Memory Access in Vulkan Explained

Non-temporal memory access is a technique used to read or write data while bypassing or minimizing retention in the cache hierarchy, preventing large, single-use datasets from evicting useful cached data. In Vulkan, developers can signal non-temporal access primarily at the shader level through SPIR-V memory access operands and compiler intrinsics, rather than through coarse device memory allocation flags. This article explains how non-temporal memory operates, its benefits in graphics and compute workloads, and how to implement it within the Vulkan API ecosystem.

What Is Non-Temporal Memory Access?

Standard memory transactions rely on temporal locality: the assumption that memory accessed once is likely to be accessed again in the near future. As a result, processors automatically populate multiple levels of cache (L1, L2, L3) with fetched or written cache lines.

Non-temporal memory access explicitly breaks this assumption. It informs the underlying memory controller and processor cores that the target data is "streaming" in nature—read once or written once, and unlikely to be reused immediately. Common examples include writing final frame output to a framebuffer, reading continuous sensory or particle data, or processing large compute staging buffers.

By applying non-temporal hints:

  • Cache Pollution is Reduced: Single-use data does not push high-priority, frequently reused data out of the cache.
  • Bandwidth is Optimized: On write operations, non-temporal operations can avoid "read-for-ownership" cache allocation stalls, streaming writes directly to lower-level memory or main RAM.

Signaling Non-Temporal Access in Vulkan

Vulkan handles non-temporal signaling through a combination of shader-level execution instructions and memory architecture configurations rather than a dedicated high-level API call.

1. SPIR-V Memory Operands

The core mechanism for signaling non-temporal access in Vulkan happens in the intermediate representation (SPIR-V) executed by the GPU.

The SPIR-V specification defines the NonTemporal memory operand for memory operations such as OpLoad and OpStore. When a compiler generates a load or store instruction with the NonTemporal mask set, it acts as a direct hint to the GPU driver and hardware compiler that the transaction has low temporal locality.

Depending on the GPU architecture (such as AMD RDNA or NVIDIA Ada Lovelace/Hopper), the shader compiler may translate this operand into specialized machine instructions:

  • On architectures with explicit bypass instructions, it instructs the hardware to bypass the L1 cache or mark the cache lines as immediately evictable (e.g., LRU - Least Recently Used bias).
  • On hardware that does not support non-temporal instructions, the GPU driver simply treats the instruction as a standard load or store, preserving execution correctness.

2. Shading Languages (GLSL and HLSL)

Because Vulkan shaders are written in high-level languages and compiled to SPIR-V, developers must ensure their shading code emits the NonTemporal operand.

  • GLSL: The GL_EXT_vulkan_memory_model or modern GLSL revisions allow memory qualifiers. Compilers like glslang map volatile or non-temporal qualifiers to the corresponding SPIR-V flags on storage buffers or image variables.
  • HLSL via DXC: Microsoft's DirectX Shader Compiler (DXC) can target SPIR-V (-spirv). Utilizing structured buffer or raw buffer read/write intrinsics that support non-temporal hints translates into the corresponding SPIR-V flags during compilation.

3. Host-Side Memory Properties

For host-to-device communication, Vulkan does not feature an explicit VK_MEMORY_PROPERTY_NON_TEMPORAL_BIT. Instead, developers control caching behavior through specific memory types discovered via vkGetPhysicalDeviceMemoryProperties:

  • Uncached Host Memory: Allocating memory without the VK_MEMORY_PROPERTY_HOST_CACHED_BIT allows writes from the CPU to stream directly without populating the CPU's cache, functioning similarly to non-temporal stores (such as write-combining memory).
  • Explicit Cache Flushing: When using host-visible, non-coherent memory, explicit calls to vkFlushMappedMemoryRanges push data out of host write buffers without maintaining strict cache retention policies.

Hardware Considerations

Because non-temporal hints in Vulkan are implemented at the instruction level, they are fundamentally treated as hints. A GPU is never required to bypass its cache if doing so contradicts internal hardware state or synchronization guarantees. However, when applied correctly to massive streaming datasets, non-temporal operations remain an effective tool for preventing GPU cache thrashing and maximizing sustained memory bandwidth.
