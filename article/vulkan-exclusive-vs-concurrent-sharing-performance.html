Vulkan Exclusive vs Concurrent Sharing Performance

In the Vulkan graphics and compute API, resources such as buffers and images can be defined using either VK_SHARING_MODE_EXCLUSIVE or VK_SHARING_MODE_CONCURRENT to manage access across distinct queue families. Exclusive resource sharing consistently offers higher performance than concurrent sharing because it allows the GPU driver to utilize optimal memory layouts, retain hardware compression, and eliminate ambiguous synchronization overhead. By requiring developers to explicitly transfer ownership between queue families, exclusive mode enables the underlying hardware to execute operations along highly optimized, vendor-specific fast paths.

Hardware-Level Memory Compression

The most significant performance difference between the two sharing modes stems from GPU memory compression. Modern GPUs from vendors like AMD, NVIDIA, Intel, and ARM rely on specialized compression algorithms (such as Delta Color Compression or Framebuffer Compression) to minimize memory bandwidth usage during render and compute operations.

When a resource is set to VK_SHARING_MODE_EXCLUSIVE, the driver knows that only a single queue family will access the data at any given moment. This guarantees that the hardware engine currently interacting with the resource fully supports its internal compression format. Conversely, with VK_SHARING_MODE_CONCURRENT, a resource can be accessed simultaneously or interchangeably by disparate queue families—such as graphics, compute, and transfer engines—which may have fundamentally different capabilities. To maintain data integrity across engines that cannot all decode the same proprietary compression metadata, drivers frequently disable compression entirely or drop down to a slower, uncompressed baseline format. This drastically increases memory bandwidth consumption and lowers throughput.

Deterministic Cache Invalidation and Flushing

Exclusive sharing mode requires explicit Queue Family Ownership Transfers (QFOT) via pipeline barriers. During a transfer, the application explicitly releases the resource from the source queue family and acquires it on the destination queue family.

This explicit handoff enables the driver to perform cache flushes and cache invalidations only when strictly necessary:

  • Write-back operations: Data modified in engine-specific local caches (such as an L1 compute cache) is flushed to an L2 or system cache only during the explicit release phase.
  • Cache invalidation: Stale data in the receiving queue family's caches is cleared specifically during the acquire phase.

In concurrent mode, there is no explicit ownership transfer mechanism to trigger these precise handoffs. Because multiple queue families retain simultaneous read and write permissions, the hardware and driver must apply conservative, generic memory access strategies to maintain coherence. This lack of deterministic transition points causes more frequent or overly broad cache flushes, which stall the execution pipeline and degrade cache hit rates.

Driver Optimization Paths and State Tracking

Under VK_SHARING_MODE_EXCLUSIVE, the driver avoids runtime state tracking and validation across multiple queues. Because access is mutually exclusive, the driver can schedule tasks and execute low-level layout transitions assuming localized context.

In VK_SHARING_MODE_CONCURRENT, developers must predefine an array of all queue family indices that will interact with the resource at creation time (queueFamilyIndexCount and pQueueFamilyIndices). The driver must configure the memory controller and internal tracking structures to accommodate the lowest common denominator among all designated queue families. This dynamic introduces runtime overhead, degrades the driver's ability to reorder commands effectively, and prevents hardware schedulers from maximizing instruction throughput across asynchronous compute and graphics pipelines.
