Vulkan Float16 Arithmetic Throughput on Mobile GPUs

Using half-precision (float16) arithmetic in mobile applications using the Vulkan graphics and compute API significantly enhances performance by maximizing hardware efficiency. By reducing data width from standard 32-bit floats to 16-bit representations, mobile GPUs can double their theoretical compute throughput, lower memory bandwidth consumption, alleviate register pressure, and reduce thermal overhead. This article explains the architectural mechanisms behind float16 execution in Vulkan and how developers leverage it to extract peak arithmetic throughput on resource-constrained mobile chipsets.

Native 2x ALU Packing (Double-Rate Execution)

Modern mobile GPU architectures—such as ARM Mali, Qualcomm Adreno, and Imagination PowerVR—design their Arithmetic Logic Units (ALUs) to support sub-word parallelism. When executing standard 32-bit floating-point (FP32) instructions, an ALU datapath processes one operation per cycle per lane.

When float16 (FP16) instructions are issued, the same 32-bit datapath is split into two independent 16-bit execution units. This SIMD-within-a-register approach allows the hardware to execute two FP16 fused multiply-add (FMA) or basic arithmetic operations in the time and space previously required for a single FP32 operation. Consequently, utilizing FP16 effectively doubles the peak theoretical floating-point operations per second (FLOPS) on the GPU.

Reduced Register Pressure and Higher Occupancy

A primary bottleneck in mobile shader execution is register spilling and low occupancy. Mobile GPUs have a fixed-size vector register file shared across active threads (waves or warps).

FP32 variables occupy 4 bytes per component, quickly exhausting the register file when complex shaders run. Once registers are depleted, the GPU must reduce the number of concurrently active threads, lowering occupancy and diminishing its ability to hide memory latency. FP16 variables require only 2 bytes per component. Halving the register storage footprint per variable allows the GPU scheduler to keep substantially more threads active simultaneously. Higher occupancy ensures execution units remain fed with work, leading directly to higher sustained arithmetic throughput.

Bandwidth Savings and Cache Hit Rates

Arithmetic throughput is often bound by memory latency rather than pure compute capability. When shaders sample textures, fetch uniform data, or perform storage buffer operations, transferring 16-bit values halves the data payload traveling across the bus compared to 32-bit types.

This halving of data size doubles the effective capacity of L1 and L2 caches, drastically reducing cache misses and memory stalls. By spending fewer execution cycles waiting for data to arrive from system memory, the ALUs achieve higher sustained instruction issue rates.

Vulkan Extensions for Float16 Execution

To utilize hardware-level float16 arithmetic in Vulkan, developers bypass legacy software emulation through explicit extensions and SPIR-V capabilities:

  1. VK_KHR_shader_float16_int8: Enables true 16-bit types (float16_t) directly inside shaders. This guarantees native 16-bit operations in SPIR-V via the Float16 capability, ensuring arithmetic runs on the 16-bit execution units rather than being up-converted to FP32.
  2. VK_KHR_16bit_storage: Allows structures, storage buffers, and push constants to store and load 16-bit types directly, minimizing memory overhead across compute pipelines.
  3. RelaxedPrecision Decoration: In GLSL (via precision mediump), variables are decorated with RelaxedPrecision in SPIR-V. Supported mobile drivers treat this as permission to route operations to FP16 ALUs whenever precision loss will not breach specification limits.

By targeting these extensions, compute workloads—including mobile neural network inference, particle physics, image processing, and post-processing tone mapping—achieve near-linear scaling in performance while maintaining the thermal envelope required by mobile hardware.
