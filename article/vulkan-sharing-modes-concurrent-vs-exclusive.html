Vulkan Sharing Modes: Concurrent vs Exclusive

In the Vulkan graphics and compute API, resource sharing modes define how buffers and images are accessed across different queue families. When creating a resource, developers must specify either VK_SHARING_MODE_EXCLUSIVE or VK_SHARING_MODE_CONCURRENT. This article explains the fundamental differences between these two modes, their performance implications, and how they dictate the synchronization overhead required to pass data between multiple queue families.

Queue Families and Resource Ownership

Vulkan exposes different queue families for distinct types of workloads, such as graphics, compute, and transfer (copy) operations. When an application utilizes multiple queue families, it must handle how resources are referenced and modified across those queues. Vulkan handles this through explicit resource ownership, which is governed by the sharing mode selected at resource creation.

VK_SHARING_MODE_EXCLUSIVE

In exclusive sharing mode, a resource is owned by exactly one queue family at any given time. This is the default and most widely used sharing mode in Vulkan.

  • Ownership Transfers: Before another queue family can access the resource, ownership must be explicitly transferred from the source queue family to the destination queue family. This transfer requires two pipeline barriers: a release barrier recorded in a command buffer submitted to the source queue, and an acquire barrier recorded in a command buffer submitted to the destination queue.
  • Performance: Exclusive mode provides the highest potential performance. Because the driver knows only one queue family will access the data at a time, it can apply aggressive memory optimizations, such as specialized cache compression techniques and vendor-specific layouts.
  • Synchronization Complexity: The developer is responsible for manually synchronizing and transferring ownership. Failing to properly release and acquire resources results in undefined behavior and validation layer errors.

VK_SHARING_MODE_CONCURRENT

In concurrent sharing mode, a resource can be accessed by multiple queue families simultaneously or non-concurrently without transferring ownership between them.

  • Upfront Declaration: When creating a resource with concurrent mode, the developer must explicitly define the list of queue families that will access the resource by providing queueFamilyIndexCount and pQueueFamilyIndices.
  • No Ownership Transfers: Pipeline barriers to transfer ownership (release and acquire operations) are not needed. Any queue family specified in the creation array can read from or write to the resource, provided standard execution dependencies (such as semaphores or pipeline barriers) are satisfied.
  • Performance Overhead: Concurrent mode may reduce performance compared to exclusive mode. Drivers often have to disable certain hardware-level optimizations, such as compressed color or depth/stencil layouts, to ensure the resource remains intelligible to different types of queue hardware without reformatting.
  • Data Hazards: While ownership does not need to be transferred, developers must still prevent traditional read/write and write/write hazards between queues using semaphores or fences.

Key Differences Summary

  • Ownership Requirement: Exclusive mode restricts access to one queue family until explicit transfer barriers are executed. Concurrent mode allows specified queue families to access the resource without ownership transfers.
  • Creation Requirements: Exclusive mode only requires the mode flag. Concurrent mode requires the mode flag plus an explicit array of all queue families that will access the resource.
  • Driver Optimization: Exclusive mode allows the GPU to utilize optimal layout and compression strategies. Concurrent mode may force the driver into a lower-performance, uncompressed, or generic layout to remain compatible across distinct queue architectures.
  • Standard Use Case: Exclusive mode is recommended for performance-critical resources and resources that are rarely shared. Concurrent mode is typically reserved for scenarios where frequent queue-crossing makes ownership transfers overly complex, or where resources (like staging buffers) already exist in linear, uncompressed formats.
