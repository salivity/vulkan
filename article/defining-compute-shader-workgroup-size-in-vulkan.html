Defining Compute Shader Workgroup Size in Vulkan

In Vulkan compute pipelines, the local workgroup size defines how many invocations (threads) execute cooperatively within a single compute block. This article explains the technical mechanisms that define this size—primarily through shader source qualifiers and SPIR-V execution modes—as well as dynamic overrides via specialization constants and the physical hardware limits that constrain them.

The Shader Layout Qualifier

The baseline definition of a workgroup size occurs directly within the compute shader source code (typically written in GLSL or HLSL) before being compiled to SPIR-V. In GLSL, this is established using an input layout qualifier:

layout (local_size_x = 16, local_size_y = 16, local_size_z = 1) in;

If dimensions are omitted, their sizes default to 1. This declaration translates directly into the SPIR-V intermediate representation under the OpExecutionMode instruction, specifically utilizing the LocalSize execution mode with explicit integer parameters for \(X\), \(Y\), and \(Z\).

Dynamic Sizing with Specialization Constants

Vulkan allows the local workgroup size to be configured at pipeline creation time without recompiling the shader source from scratch. This is achieved using SPIR-V Specialization Constants.

In GLSL, specialization IDs are mapped using the local_size_*_id qualifiers:

layout (local_size_x_id = 0, local_size_y_id = 1, local_size_z_id = 2) in;

When building the pipeline in Vulkan, you populate a VkSpecializationMapEntry array and assign concrete values inside a VkSpecializationInfo structure. Passing this structure into the pSpecializationInfo field of VkComputePipelineCreateInfo sets the workgroup dimensions during vkCreateComputePipelines. This maps to the LocalSizeId execution mode in SPIR-V.

Hardware Limits and Constraints

While the shader author specifies the dimensions, the target GPU defines the maximum allowable workgroup size. Vulkan exposes these physical constraints via VkPhysicalDeviceLimits, which can be queried using vkGetPhysicalDeviceProperties:

  • maxComputeWorkGroupSize[3]: An array of three integers indicating the maximum allowable size along the X, Y, and Z axes individually (e.g., [1024, 1024, 64]).
  • maxComputeWorkGroupInvocations: The maximum total number of invocations allowed in a single workgroup (the product of \(X \times Y \times Z\)). This is often smaller than the product of the individual maximum axes (e.g., a limit of 1024 total invocations).

Defining a workgroup size that exceeds either of these hardware metrics leads to validation layer errors and pipeline compilation failure.

Local Workgroup Size vs. Global Dispatch Size

The local workgroup size defines the internal structure of a single thread group, enabling threads to share data via shared memory variables and synchronize with execution barriers.

This must not be confused with the total number of workgroups launched during command buffer execution. The total volume of work is dispatched via the Vulkan host API using vkCmdDispatch:

vkCmdDispatch(commandBuffer, groupCountX, groupCountY, groupCountZ);

The overall execution grid consists of the product of the dispatch dimensions (groupCountX, groupCountY, groupCountZ) and the local workgroup dimensions (local_size_x, local_size_y, local_size_z).
