Vulkan Storage Images in Compute Shaders Explained

Storage images in the Vulkan API provide compute shaders with random-access read and write capabilities, bypassing the fixed-function texture sampling and framebuffer pipelines. While traditional sampled images rely on read-only filtering hardware and render passes handle structured pixel outputs, storage images expose raw, texel-level memory directly to shader invocations. This functionality is enabled through explicit API-side descriptor setups, memory layout management, dedicated shading language intrinsics, and application-driven synchronization.

Image Creation and Usage Flags

To use an image as a storage image, the application must explicitly create it with the VK_IMAGE_USAGE_STORAGE_BIT flag in the VkImageCreateInfo structure. This flag tells the graphics driver to allocate memory and configure resource metadata so that shader compute units can perform unformatted or raw write operations.

In addition to image creation, the view created via VkImageViewCreateInfo must match a compatible format supported by the device for storage operations. Vulkan specifications require implementations to support specific formats for storage images, which can be queried using vkGetPhysicalDeviceFormatProperties to check for the VK_FORMAT_FEATURE_STORAGE_IMAGE_BIT.

Memory Layout and Descriptors

Standard sampled textures typically reside in optimized layouts such as VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMIZED. Because compute shaders require bidirectional or unordered writes, storage images must typically be transitioned to VK_IMAGE_LAYOUT_GENERAL before dispatch. This layout ensures that the underlying cache hierarchies and compression schemes allow concurrent read and write transactions.

In the pipeline layout and descriptor set:

  • The descriptor type is specified as VK_DESCRIPTOR_TYPE_STORAGE_IMAGE.
  • Unlike combined image samplers, storage images do not pair with a VkSampler object because hardware filtering, mipmapping calculations, and normalized address wrapping are bypassed.
  • Memory addressing maps directly to discrete texel coordinates (integers) rather than floating-point UV coordinates.

Shader-Side Binding and Operations

Inside a compute shader (using GLSL or HLSL compiled to SPIR-V), storage images are declared using image types rather than sampler types, such as image2D, uimage2D, or iimage2D.

layout(set = 0, binding = 0, rgba32f) uniform image2D uOutputImage;

A format layout qualifier (such as rgba32f or r32ui) is typically required unless the Vulkan device supports the shaderStorageImageExtendedFormats feature, which relaxes format specification constraints in shader code.

Shaders interact with these resources using direct intrinsic functions:

  • imageStore(image, ivec2 coord, vec4 data): Writes data directly to the specified texel coordinate without blending.
  • imageLoad(image, ivec2 coord): Retrieves the raw data stored at the coordinate without bilinear or trilinear interpolation.
  • Atomic Operations: Functions like imageAtomicAdd or imageAtomicCompSwap enable thread-safe read-modify-write operations on single-channel integer images (e.g., r32ui), resolving race conditions among parallel invocations.

Invocations inside a compute dispatch use their unique thread coordinates (e.g., gl_GlobalInvocationID.xy) to determine which texel to access, enabling arbitrary scatter and gather memory patterns across the entire image.

Synchronization and Memory Coherency

Because Vulkan compute workloads execute in parallel across thousands of threads with weakly ordered memory access, arbitrary reading and writing introduces potential hazards (Read-After-Write, Write-After-Read, and Write-After-Write).

Storage images rely on explicit synchronization:

  1. Intra-Workgroup Synchronization: Shaders use memoryBarrierImage() combined with barrier() to ensure all writes performed by invocations within a workgroup are visible to subsequent reads.
  2. Inter-Dispatch Synchronization: Host code must insert pipeline barriers (vkCmdPipelineBarrier) using a VkImageMemoryBarrier. The barrier coordinates the transition between the producing stage (VK_PIPELINE_STAGE_COMPUTE_SHADER_BIT with VK_ACCESS_SHADER_WRITE_BIT) and the consuming stage (such as another compute dispatch, transfer command, or fragment shader read).

By replacing fixed-function hardware pipelines with direct memory addressing and explicit synchronization, storage images turn GPU compute shaders into highly versatile, parallel data processors capable of complex tasks such as ray tracing, image processing, physics simulations, and custom particle updates.
