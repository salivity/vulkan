Vulkan Compute Read-After-Write Synchronization

To safely execute read-after-write (RAW) operations across consecutive compute shader dispatches in Vulkan, applications must explicitly define both an execution dependency and a memory dependency using a pipeline barrier. Without explicit synchronization, the GPU may overlap compute dispatches or fail to flush write caches, resulting in data hazards. This article covers how to configure execution stages, establish memory access masks, and issue pipeline barriers to ensure that written buffer or storage image data is fully available and visible to subsequent reads.

Understanding the RAW Hazard in Vulkan

Vulkan follows an explicit execution and memory model. Commands submitted to a queue—such as sequential vkCmdDispatch calls—do not inherently wait for previous commands to complete, nor do they automatically invalidate or flush GPU caches.

If Dispatch A writes to a resource (such as a Storage Buffer or Storage Image) and Dispatch B reads from that same resource, a read-after-write hazard occurs. To prevent Dispatch B from reading stale or partially written data, the application must insert a pipeline barrier using vkCmdPipelineBarrier or the modernized vkCmdPipelineBarrier2 between the two dispatch calls.

Establishing Execution and Memory Dependencies

A pipeline barrier resolves data hazards by establishing two guarantees:

  1. Execution Dependency: Guarantees that execution of the first dispatch reaches a specified stage before the subsequent dispatch begins its execution stage.
  2. Memory Dependency: Guarantees that memory writes produced by the first dispatch are made available (flushed from local caches), and then made visible (invalidated in target caches) so that the subsequent dispatch can observe the new data.

For a compute-to-compute dependency, both the source and destination execution stages are the compute shader stage.

Synchronizing Storage Buffers

When dealing with SSBOs (Shader Storage Buffer Objects), an application inserts a buffer memory barrier into the command buffer between the dispatches.

Using standard Vulkan 1.0 synchronization:

  • Source Stage (srcStageMask): VK_PIPELINE_STAGE_COMPUTE_SHADER_BIT
  • Destination Stage (dstStageMask): VK_PIPELINE_STAGE_COMPUTE_SHADER_BIT
  • Source Access Mask (srcAccessMask): VK_ACCESS_SHADER_WRITE_BIT
  • Destination Access Mask (dstAccessMask): VK_ACCESS_SHADER_READ_BIT

The VkBufferMemoryBarrier must specify the target VkBuffer, the affected offset, and the size. When recorded between the two vkCmdDispatch commands, this barrier forces the GPU to finish all shader writes from Dispatch A and flush the relevant L1/L2 caches before Dispatch B executes its shader reads.

Synchronizing Storage Images

When Dispatch A writes to a storage image and Dispatch B reads from it (either as a storage image or as a sampled texture), a VkImageMemoryBarrier is required instead of a buffer barrier.

In addition to specifying srcAccessMask and dstAccessMask:

  • If Dispatch B continues reading the resource as an image with imageStore/imageLoad, keep oldLayout and newLayout set to VK_IMAGE_LAYOUT_GENERAL.
  • If Dispatch B reads the resource as a sampled texture via a texture sampler, use the barrier to transition oldLayout from VK_IMAGE_LAYOUT_GENERAL to newLayout = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL. The dstAccessMask should then be VK_ACCESS_SHADER_READ_BIT.

Using Synchronization2 (Vulkan 1.3+)

Core Vulkan 1.3 and the VK_KHR_synchronization2 extension introduce vkCmdPipelineBarrier2, which clarifies access flags and avoids ambiguity. The modern equivalent configuration uses VkMemoryBarrier2:

  • srcStageMask: VK_PIPELINE_STAGE_2_COMPUTE_SHADER_BIT
  • srcAccessMask: VK_ACCESS_2_SHADER_STORAGE_WRITE_BIT
  • dstStageMask: VK_PIPELINE_STAGE_2_COMPUTE_SHADER_BIT
  • dstAccessMask: VK_ACCESS_2_SHADER_STORAGE_READ_BIT

If the read dispatch requires sampled image access, change dstAccessMask to VK_ACCESS_2_SHADER_SAMPLED_READ_BIT.

Best Practices

  • Scope Barriers Accurately: Avoid using global memory barriers with VK_ACCESS_MEMORY_WRITE_BIT and VK_ACCESS_MEMORY_READ_BIT unless the dependency truly spans all active allocations. Targeted buffer or image barriers avoid unnecessary cache flushes.
  • Batch Barriers: If multiple resources need synchronization between dispatches, submit them in a single vkCmdPipelineBarrier call instead of issuing multiple barrier commands sequentially.
  • Queue Families: Ensure both compute dispatches are submitted to the same queue family. If transferring between distinct queue families (such as an asynchronous compute queue to a graphics queue), the barrier must explicitly define an ownership transfer using srcQueueFamilyIndex and dstQueueFamilyIndex.
