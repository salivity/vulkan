Why Vulkan Input Attachments Cannot Arbitrarily Sample

In the Vulkan graphics API, input attachments are specialized image views used within a subpass to read pixel data generated by a previous subpass. Unlike standard sampled images, input attachments strictly disallow arbitrary coordinate sampling and only permit reading from the exact fragment coordinate currently being processed. This article explains the architectural and hardware constraints—specifically tile-based GPU designs, on-chip memory limits, and subpass execution models—that prevent arbitrary coordinate access in input attachments.

Optimization for Tile-Based Rendering Architectures

The restriction against arbitrary coordinate sampling is fundamentally rooted in hardware efficiency, particularly for Tile-Based Deferred Rendering (TBDR) architectures common in mobile and modern integrated GPUs.

TBDR hardware divides the render target into small rectangular tiles (e.g., 16x16 or 32x32 pixels) and processes each tile entirely within fast, on-chip memory (tile caches or registers). When a render pass consists of multiple subpasses, input attachments enable the GPU to read the output of one subpass directly from on-chip memory in the subsequent subpass without writing the intermediate data out to main system memory (DRAM).

If a fragment shader were permitted to sample arbitrary coordinates, it could request pixel data outside the bounds of the current tile. Because only the current tile is resident in fast local memory, fetching out-of-bounds coordinates would require high-latency, bandwidth-heavy round trips to global device memory, completely breaking the TBDR performance optimization.

Prevention of Race Conditions and Synchronization Overhead

Vulkan provides fine-grained control over execution and memory dependencies between subpasses using VkSubpassDependency. Subpass dependencies with VK_DEPENDENCY_BY_REGION_BIT signal to the driver that execution dependencies are strictly localized to the corresponding pixel or fragment coordinate across subpasses.

Allowing arbitrary coordinate sampling would introduce severe spatial data races:

  • Fragments run concurrently in parallel execution waves.
  • Subpass execution does not guarantee that neighboring fragments or different tiles have completed writing their intermediate results.
  • Without arbitrary sampling restrictions, reading non-local coordinates would require massive global barriers and cache flushes between subpasses, degrading performance to the level of standard sequential render passes.

By locking the fragment shader to read only the current fragment's coordinate via subpassLoad(), Vulkan guarantees that the exact fragment being read has already finished writing in the previous subpass within that localized region.

Input Attachments vs. Sampled Textures

Standard sampled images (VK_DESCRIPTOR_TYPE_SAMPLED_IMAGE or VK_DESCRIPTOR_TYPE_COMBINED_IMAGE_SAMPLER) support arbitrary coordinates, filtering, and mipmapping because they pull data from global VRAM through the GPU's texture sampling units. This flexibility requires:

  • Flushing previous render targets to global VRAM.
  • Inserting full pipeline execution barriers (vkCmdPipelineBarrier).
  • Relying on texture caches rather than dedicated local tile memory.

Input attachments sacrifice coordinate flexibility to bypass the texture units and global memory bandwidth entirely. If an application requires reading arbitrary coordinates across a previously rendered frame (such as for Gaussian blurs, screen-space reflections, or distortion effects), standard sampled images across separate render passes must be used instead of input attachments.
