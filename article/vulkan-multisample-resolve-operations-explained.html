Vulkan Multisample Resolve Operations Explained

This article provides an overview of how Vulkan handles multisample resolve operations to downsample multisample attachments into standard, single-sample textures. In graphics rendering, Multisample Anti-Aliasing (MSAA) renders geometry to targets with multiple samples per pixel to smooth jagged edges. To display this image on a standard display or use it as a standard texture in subsequent shader passes, these extra samples must be combined—or "resolved"—into a single color value per pixel. Vulkan provides efficient hardware-level paths within its render passes and transfer commands to perform this downsampling operation.

Understanding the Resolve Operation

During multisampled rendering, color targets are allocated with sample counts greater than one (such as VK_SAMPLE_COUNT_4_BIT). A resolve operation averages the multiple color samples of each pixel into a single representative color using a standard box filter. On desktop and mobile GPUs, this is typically handled by dedicated hardware units or directly during the transition of tile memory to external memory, eliminating the need to execute manual fragment shader passes to compute sample averages.

In-Subpass Resolving

The standard and most efficient way to resolve attachments in Vulkan is during a render pass subpass using VkSubpassDescription:

  1. Attachment Pairing: The render pass configuration accepts an array of multisampled attachments in pColorAttachments and a corresponding array of single-sample attachments in pResolveAttachments.
  2. One-to-One Mapping: There is a strict one-to-one mapping between color attachments and resolve attachments. If pResolveAttachments is provided, the entry at index i receives the downsampled output of the color attachment at index i. Both attachments must share compatible color formats.
  3. Automatic Downsampling: When the subpass finishes execution, the GPU automatically downsamples the multisampled data into the resolve attachment.
  4. Memory Optimization: The multisampled attachment can be set to VK_ATTACHMENT_STORE_OP_DONT_CARE, while the resolve attachment uses VK_ATTACHMENT_STORE_OP_STORE. On tile-based architectures (TBDR) common in mobile devices, this allows the high-bandwidth multisample buffer to live strictly within fast, on-chip tile memory, writing only the final single-sample image back to system RAM.

Resolving via Dynamic Rendering

In Vulkan 1.3 or via the VK_KHR_dynamic_rendering extension, render passes can be executed without traditional render pass and framebuffer objects. In this workflow, resolves are configured directly within VkRenderingAttachmentInfo:

  • The multisample attachment is bound to imageView.
  • The target single-sample texture is bound to resolveImageView.
  • resolveMode is configured (commonly VK_RESOLVE_MODE_AVERAGE_BIT for color targets).
  • The operation runs automatically upon completing the rendering pass defined by vkCmdEndRendering.

Explicit Command Resolving with vkCmdResolveImage

If rendering and resolving cannot occur within the same subpass or dynamic rendering block, Vulkan provides an explicit command: vkCmdResolveImage.

  • Usage Flags: The source image must have VK_IMAGE_USAGE_TRANSFER_SRC_BIT, and the destination image requires VK_IMAGE_USAGE_TRANSFER_DST_BIT.
  • Layout Requirements: Before recording the command, the source image must be transitioned to VK_IMAGE_LAYOUT_TRANSFER_SRC_OPTIMAL or VK_IMAGE_LAYOUT_GENERAL, and the destination image must be in VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL or VK_IMAGE_LAYOUT_GENERAL.
  • Execution: The command takes a VkImageResolve structure defining the source and destination mip levels, array layers, and regions to resolve. Unlike subpass resolves, this occurs as a separate transfer operation outside of the rasterization pipeline.

Depth and Stencil Resolves

While color resolves use average blending, depth and stencil attachments require distinct handling because averaging depth values often causes depth-testing artifacts. Using the core Vulkan 1.2 specification (or VK_KHR_depth_stencil_resolve), developers can resolve depth and stencil data by specifying resolve modes such as:

  • VK_RESOLVE_MODE_SAMPLE_ZERO_BIT: Retains the value of sample 0.
  • VK_RESOLVE_MODE_MIN_BIT / VK_RESOLVE_MODE_MAX_BIT: Takes the minimum or maximum sample value (ideal for shadow maps and depth bounds checks).
  • VK_RESOLVE_MODE_AVERAGE_BIT: Averages depth values (valid for depth, invalid for stencil).
