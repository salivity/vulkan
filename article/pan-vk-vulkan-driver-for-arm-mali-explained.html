PanVK: Vulkan Driver for ARM Mali Explained

PanVK is an open-source Vulkan driver hosted within the Mesa 3D Graphics Library, designed to provide hardware-accelerated 3D graphics and compute capabilities for ARM Mali GPUs. This article explains what PanVK is, how it fits into the modern Linux graphics stack, and the technical mechanics behind how it translates Vulkan API calls into native instructions executed by ARM Mali hardware.

What Is PanVK?

PanVK is the Vulkan counterpart to Panfrost, Mesa’s open-source OpenGL and OpenGL ES driver for ARM Mali GPUs. Developed primarily through community reverse-engineering and upstream Linux graphics collaboration, PanVK allows Linux systems to run Vulkan applications on ARM hardware without relying on ARM's proprietary, closed-source user-space driver blobs. It primarily targets ARM's Bifrost (such as Mali-G31, G52, G72) and Valhall (such as Mali-G57, G77, G710) microarchitectures.

Translating Vulkan to ARM Mali Hardware

Implementing Vulkan on Mali hardware requires managing memory, compiling shaders, and packaging draw commands into proprietary job formats that the GPU hardware scheduler understands. PanVK achieves this through several core subsystems:

1. Common Vulkan Infrastructure (Mesa vk_runtime)

Rather than reimplementing common Vulkan state tracking from scratch, PanVK utilizes Mesa's shared Vulkan runtime layer. This framework manages API entry points, handles dispatch tables, tracks device extensions, and validates API object lifetimes. This allows PanVK developers to focus strictly on hardware-specific execution details.

2. Shader Compilation via NIR and Bi-Compiler Backends

Vulkan shaders arrive at the driver in the form of SPIR-V intermediate bytecode. PanVK processes these shaders using the following pipeline:

  • SPIR-V to NIR: The driver ingests the SPIR-V bytecode and converts it into NIR, Mesa's internal, optimization-focused intermediate representation.
  • Hardware Lowering: PanVK applies generic and Mali-specific NIR optimization passes, mapping abstract operations directly to Mali execution paradigms (such as hardware registers, texture load/store instructions, and uniform buffer handling).
  • Binary Emission: The driver uses the shared Panfrost compiler backend (Bifrost compiler or Valhall compiler) to translate the lowered NIR into native machine code targeting the execution engines of the Mali GPU.

3. Command Stream and Descriptor Encoding

ARM Mali uses a tile-based deferred rendering (TBDR) architecture, meaning the screen is split into smaller tiles, and geometry is processed before fragment shading occurs. PanVK must organize draw operations into structured GPU job chains:

  • Job Descriptors: PanVK writes out the binary data structures required by Mali hardware, configuring render passes, scissor tests, depth/stencil buffers, and multisampling configurations.
  • Pipeline and Descriptor Binding: Vulkan pipelines and descriptor sets are converted into hardware-readable tables that link shader code, samplers, textures, and uniform buffers directly in GPU-accessible memory.

4. Hardware Scheduling and Kernel Submission

Mali hardware versions submit work differently, and PanVK interfaces with the Linux kernel accordingly:

  • Bifrost and Early Valhall (Job Manager): On architectures using the traditional Job Manager interface, PanVK structures work into explicit job graphs (e.g., tiling jobs followed by fragment jobs). These graphs are submitted to the Linux kernel via the panfrost DRM/KMS kernel driver using ioctl calls.
  • Modern Valhall (Command Stream Frontend - CSF): Modern Mali GPUs abandon the raw Job Manager in favor of a microcontroller-driven Command Stream Frontend. For CSF hardware, PanVK targets the newer panthor kernel driver, emitting ring-buffer-based instruction sequences directly interpreted by the GPU's firmware.

Memory Management and Synchronization

Vulkan requires explicit memory and synchronization handling. PanVK implements Vulkan device memory by managing Direct Rendering Manager (DRM) buffer objects (BOs) backed by system RAM, configuring appropriate GPU cache attributes, and mapping them to virtual addresses accessible by the GPU MMU. Synchronization primitives, such as Vulkan semaphores and fences, are mapped directly to kernel sync files and DRM timeline synchronization objects, ensuring asynchronous compute and rendering workloads run concurrently without data hazards.
