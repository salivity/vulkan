Viewport Arrays in Vulkan for Multi-View Rendering

A viewport array in Vulkan is a graphics pipeline mechanism that allows multiple viewport and scissor rectangle definitions to be bound simultaneously, enabling the GPU to direct rendering output to different screen-space regions within a single render pass. This article explains what viewport arrays are, how they function within the Vulkan API, how shader stages control primitive routing, and how this technique optimizes multi-view rendering scenarios such as stereoscopic virtual reality, cascaded shadow maps, and split-screen viewports without the CPU overhead of repetitive draw calls.

What is a Viewport Array?

In standard rasterization workflows, a pipeline uses a single VkViewport and a single VkRect2D scissor rectangle to transform normalized device coordinates (NDC) into framebuffer coordinates. A viewport array expands this configuration by allowing an array of up to maxViewports (a hardware limit queried via VkPhysicalDeviceLimits) to be bound simultaneously.

When using a viewport array, each incoming primitive can be directed to a specific viewport within the array. This routing is controlled programmatically inside the shader pipeline rather than through state changes on the CPU.

Enabling Viewport Arrays in Vulkan

To utilize viewport arrays, the Vulkan application must explicitly enable the multiViewport feature during device creation:

VkPhysicalDeviceFeatures deviceFeatures{};
deviceFeatures.multiViewport = VK_TRUE;

When configuring the graphics pipeline, specify the number of viewports and scissors in the VkPipelineViewportStateCreateInfo structure:

VkPipelineViewportStateCreateInfo viewportState{};
viewportState.sType = VK_STRUCTURE_TYPE_PIPELINE_VIEWPORT_STATE_CREATE_INFO;
viewportState.viewportCount = viewCount; // Greater than 1
viewportState.pViewports = viewportsArray;
viewportState.scissorCount = viewCount;
viewportState.pScissors = scissorsArray;

If using dynamic state, viewports and scissors can be updated at command-buffer recording time via vkCmdSetViewport and vkCmdSetScissor, passing the starting index and array count.

Routing Primitives in Shaders

The core of multi-view rendering via viewport arrays is dynamic routing at the shader level. In high-level shading languages, this is accomplished using the built-in output variable:

  • GLSL: gl_ViewportIndex
  • HLSL: SV_ViewportArrayIndex

Historically, gl_ViewportIndex required a Geometry Shader to process primitives and assign them to specific viewports. However, through extensions such as VK_EXT_shader_viewport_index_layer (or core functionality starting in Vulkan 1.2), developers can write directly to gl_ViewportIndex from the Vertex Shader or Tessellation Evaluation Shader. This eliminates the performance penalty associated with invoking geometry shaders.

#version 460
#extension GL_ARB_shader_viewport_layer_array : enable

layout(location = 0) in vec3 inPosition;

void main() {
    gl_Position = vec4(inPosition, 1.0);
    // Assign primitive to a specific viewport based on instance ID or custom logic
    gl_ViewportIndex = gl_InstanceIndex; 
}

How Viewport Arrays Assist Simultaneous Multi-View Rendering

Viewport arrays optimize rendering architectures by solving the primary bottlenecks of multi-view systems: CPU submission overhead and redundant state synchronization.

1. Single-Pass Draw Submission

Without viewport arrays, rendering four views (such as four camera angles or cubemap faces) requires four separate draw commands, each preceded by binding a different viewport or framebuffer. With viewport arrays combined with instancing, a single draw call can replicate geometry across all target views:

  • Geometry is fetched once from memory.
  • Vertex data is transformed according to matrices specific to each view (often indexed via gl_InstanceIndex).
  • Each instance assigns its target viewport via gl_ViewportIndex.

2. Simultaneous Viewport and Layer Indexing

Viewport arrays are frequently paired with layered framebuffers (VkFramebuffer with multiple layers, such as 2D texture arrays). When extensions like VK_EXT_shader_viewport_index_layer are active, shaders can output to both gl_ViewportIndex and gl_Layer simultaneously. This allows independent viewports to map directly to distinct texture layers in one submission pass, avoiding intermediate render-target switches.

3. Reduced Driver and State Overhead

By avoiding state transitions, pipeline re-binds, and command buffer bloat, the CPU load drops significantly. The GPU handles the distribution of primitives across the defined viewports internally at the rasterization stage.

Primary Use Cases

  • Virtual Reality (VR) and Stereo Rendering: Left- and right-eye viewports can be packed side by side in a single frame buffer and rendered in a single pass.
  • Cascaded Shadow Mapping (CSM): Different shadow cascade splits can be rendered into distinct atlas regions using tailored projection matrices per viewport.
  • Cubemap Rendering: Real-time reflection probes can render multiple faces of a cubemap simultaneously into a single target atlas.
  • Split-Screen Multiplayer: Co-op or competitive games can draw shared scene geometry to independent screen quadrants efficiently.
