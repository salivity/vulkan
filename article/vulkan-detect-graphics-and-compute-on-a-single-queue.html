Vulkan: Detect Graphics and Compute on a Single Queue

This article explains how an application can determine whether a single queue family supports both graphics and compute operations concurrently in Vulkan. By querying the physical device's queue family properties, applications can inspect capability flags and implement appropriate synchronization to allow compute and graphics workloads to overlap on the same queue.

Querying Queue Family Properties

To detect support for both graphics and compute operations on a single queue, you must query the available queue families on the target physical device using vkGetPhysicalDeviceQueueFamilyProperties.

The process involves two calls to vkGetPhysicalDeviceQueueFamilyProperties:

  1. Pass NULL for the pQueueFamilyProperties parameter to obtain the count of available queue families.
  2. Allocate an array of VkQueueFamilyProperties structures and call the function again to populate the details.

Inspecting Queue Capability Flags

Each VkQueueFamilyProperties struct contains a queueFlags field, which is a bitmask of VkQueueFlagBits. To determine if a queue supports both domains, perform a bitwise AND check against both VK_QUEUE_GRAPHICS_BIT and VK_QUEUE_COMPUTE_BIT:

uint32_t queueFamilyCount = 0;
vkGetPhysicalDeviceQueueFamilyProperties(physicalDevice, &queueFamilyCount, NULL);

VkQueueFamilyProperties* queueFamilies = malloc(queueFamilyCount * sizeof(VkQueueFamilyProperties));
vkGetPhysicalDeviceQueueFamilyProperties(physicalDevice, &queueFamilyCount, queueFamilies);

int combinedQueueFamilyIndex = -1;

for (uint32_t i = 0; i < queueFamilyCount; i++) {
    VkQueueFlags flags = queueFamilies[i].queueFlags;
    if ((flags & VK_QUEUE_GRAPHICS_BIT) && (flags & VK_QUEUE_COMPUTE_BIT)) {
        combinedQueueFamilyIndex = i;
        break;
    }
}

free(queueFamilies);

According to the Vulkan specification, any implementation that supports graphics operations must expose at least one queue family that supports both graphics and compute operations. Therefore, any device capable of graphics will always expose at least one queue family where both flags are set.

Understanding Concurrency on a Single Queue

While checking flags confirms that a queue accepts both types of commands, enabling concurrent execution on a single queue depends on workload structure and synchronization:

  • In-Order Submission vs. Out-of-Order Execution: Commands submitted to a single VkQueue start in the order they are submitted, but the GPU executes stages independently. Unless restricted by pipeline barriers, compute and graphics work can overlap on hardware compute units.
  • Pipeline Barriers: To allow concurrency, avoid coarse barriers like VK_PIPELINE_STAGE_ALL_COMMANDS_BIT or VK_ACCESS_MEMORY_READ_BIT | VK_ACCESS_MEMORY_WRITE_BIT between unrelated graphics and compute passes. Tailor VkMemoryBarrier or VkImageMemoryBarrier to only the specific stages and resources requiring synchronization.
  • Independent Submissions: Compute and graphics commands can be recorded into separate VkCommandBuffer instances and submitted in a single VkSubmitInfo batch. The GPU driver can interleave these tasks if execution dependencies do not force a sequential stall.

If hardware-level asynchronous compute (simultaneous execution independent of graphics pipeline stalls) is required, applications should also check if the device exposes a separate compute-only queue family alongside the combined graphics and compute queue family.
