How Vulkan Shading Rate Palettes Map Screen Regions

Variable Rate Shading (VRS) in Vulkan allows developers to decouple render target resolution from fragment shader execution frequency, optimizing performance by reducing fragment workloads in less perceptually critical regions. Through shading rate palettes—primarily utilized in extensions such as VK_NV_shading_rate_image and related fragment shading rate mechanisms—Vulkan translates compact indices stored in a low-resolution control image into concrete fragment invocation rates, defining exactly how many pixels share a single fragment shader evaluation across the screen.

The Role of the Shading Rate Image

The foundation of screen-space rate control is a low-resolution image known as the shading rate image (or attachment). Instead of assigning a unique shading rate to every pixel individually, the framebuffer is partitioned into uniform tiles—commonly 16x16 or 8x8 pixels.

Each texel in the shading rate image directly corresponds to one of these tiles on screen. To minimize bandwidth and memory overhead, this image stores small integer indices rather than explicit multi-dimensional rate structures.

Defining the Palette

A shading rate palette functions as a lookup table (LUT) defined within the pipeline or render pass state. It maps the integer values stored in the shading rate image to specific fragment densities.

In Vulkan, entries in this palette are represented by enumerations such as VkShadingRatePaletteEntryNV. Each entry specifies:

  • Invocations per pixel: For supersampling or high-fidelity zones (e.g., 1 invocation per pixel, 2 invocations per pixel, or 4 invocations per pixel).
  • Pixels per invocation: For coarse shading (e.g., 1 invocation spanning a 2x1, 2x2, or 4x4 pixel block).
  • No invocations: Skipping shading altogether for fully occluded or masked blocks.

By configuring a palette with a set of predefined entries, the application dictates the subset of shading rates available to the pipeline.

The Mapping Pipeline

The hardware evaluates the final shading density through a structured process during the rasterization stage:

  1. Coordinate Transformation: As a primitive is rasterized, the screen-space coordinates \((X, Y)\) are divided by the implementation-defined tile size to calculate the corresponding coordinate in the shading rate image.
  2. Texel Fetch: The GPU fetches the value at that coordinate from the shading rate image.
  3. Palette Lookup: The fetched value is treated as an index into the active shading rate palette. If the index refers to entry 3, and entry 3 is configured as VK_SHADING_RATE_PALETTE_ENTRY_2_INVOCATIONS_PER_PIXEL_NV, that tile receives supersampled shading. If the index points to a 4x4 entry, a single fragment shader execution will cover a 16-pixel footprint.
  4. Out-of-Bounds Clamping: If an index in the image exceeds the number of entries provided in the palette, Vulkan implementations automatically clamp the index or fallback to a default rate (typically 1x1).

Combining Rates

Vulkan also allows shading rates to be determined per-draw or per-primitive via mesh or vertex shaders. When multiple sources define a shading rate simultaneously, the palette lookup result from the screen-region image is fed into a rate combiner.

Combiner operations (such as VK_FRAGMENT_SHADING_RATE_COMBINER_OP_MIN_KHR or MAX) evaluate the image-palette rate alongside the primitive or pipeline rates. This ensures that fine geometric details are preserved even if the palette indicates a coarse rate for that screen region, preventing visual artifacts along high-contrast silhouette edges.
