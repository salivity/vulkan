Vulkan Primary vs Secondary Command Buffers Explained

In Vulkan, command buffers are the core mechanism used to record GPU commands for execution, categorized strictly into primary and secondary levels. Primary command buffers can be submitted directly to a hardware queue and can invoke secondary command buffers, but they cannot call other primary buffers. Secondary command buffers, conversely, cannot be submitted directly to a queue; instead, they are recorded to modularize workloads, inherit rendering state, and enable efficient multi-threaded command generation before being executed by a primary buffer.

Direct Queue Submission

The most fundamental operational difference is how the buffers interface with the Vulkan queue (VkQueue).

  • Primary Command Buffers (VK_COMMAND_BUFFER_LEVEL_PRIMARY): These buffers are capable of direct submission to a device queue using vkQueueSubmit. They act as the top-level dispatch units that the GPU processes.
  • Secondary Command Buffers (VK_COMMAND_BUFFER_LEVEL_SECONDARY): These buffers cannot be passed to vkQueueSubmit. Attempting to submit a secondary buffer directly will cause an API error. Instead, they must be recorded into a primary command buffer using the vkCmdExecuteCommands function.

Multi-Threaded Command Generation

The primary architectural purpose of secondary command buffers is enabling scalable multi-threading across CPU cores.

While a single command buffer can only be recorded by one thread at a time, secondary command buffers allow an application to split complex rendering tasks—such as drawing thousands of individual scene objects—across multiple CPU worker threads simultaneously. Each thread records its subset of draw calls into an independent secondary command buffer. Once finished, a single primary command buffer records vkCmdExecuteCommands to execute the secondary buffers in a deterministic order on the main thread, minimizing submission overhead.

State Inheritance and Render Passes

Primary and secondary command buffers handle pipeline state and render pass contexts differently:

  • State Isolation: By default, command buffers do not share state. Binding a pipeline, descriptor set, or vertex buffer in one command buffer does not carry over to another, regardless of their hierarchy.
  • Render Pass Inheritance: Secondary command buffers can execute entirely inside a render pass initiated by a primary buffer. To accomplish this, the application populates VkCommandBufferInheritanceInfo during secondary buffer recording. This allows the secondary buffer to inherit the framebuffer, render pass compatibility, and occlusion query states from the parent primary buffer, preventing the overhead of re-specifying render pass instances.

Allocation and Setup

Both command buffer types are created via vkAllocateCommandBuffers using the VkCommandBufferAllocateInfo structure, differentiated solely by the level member:

VkCommandBufferAllocateInfo allocInfo{};
allocInfo.sType = VK_STRUCTURE_TYPE_COMMAND_BUFFER_ALLOCATE_INFO;
allocInfo.commandPool = commandPool;
allocInfo.level = VK_COMMAND_BUFFER_LEVEL_PRIMARY; // or VK_COMMAND_BUFFER_LEVEL_SECONDARY
allocInfo.commandBufferCount = 1;

When recording a secondary command buffer via vkBeginCommandBuffer, the pInheritanceInfo member in VkCommandBufferBeginInfo must be provided if the secondary buffer will execute within a render pass. For primary command buffers, this pointer is ignored.

Summary of Differences

Feature Primary Command Buffer Secondary Command Buffer
Queue Submission Direct via vkQueueSubmit Indirect via vkCmdExecuteCommands
Can Execute Secondary command buffers Cannot execute any buffers
Render Pass Context Begins and ends render passes Can execute within inherited render passes
Primary Use Case Top-level frame coordination Multi-threaded workload generation
