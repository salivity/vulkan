Vulkan Task Shaders: Dynamic Cluster Culling Explained

In modern Vulkan rendering, the mesh shading pipeline replaces traditional fixed-function geometry pipelines with an efficient, compute-like approach divided into task and mesh shaders. This article explores how task shader payload sharing acts as the critical bridge for dynamic cluster culling. By executing coarse-grained visibility tests and compacting surviving meshlet identifiers into a shared payload buffer before spawning mesh shader workgroups, developers can dramatically eliminate redundant geometry processing early in the graphics pipeline.

The Mesh Shading Pipeline Architecture

The Vulkan mesh shading extension (VK_EXT_mesh_shader) introduces a two-tier execution model designed to handle geometry in dense, localized batches known as meshlets or clusters:

  1. Task Shader: An optional amplification stage that operates similarly to a compute shader. It evaluates bounding geometry, computes level of detail (LOD), and dynamically dictates how many mesh shader workgroups to spawn.
  2. Mesh Shader: The primary geometry generation stage that outputs vertex and primitive data directly to the rasterizer.

Because mesh shaders consume significant register space and memory bandwidth to unpack vertices and build primitives, executing them on invisible or occluded geometry is inefficient. The task shader serves as a programmable filter that discards culled clusters prior to this expensive stage.

The Role of the Task Payload

Communication between the task shader and the downstream mesh shader occurs through a user-defined payload structure, declared using the taskPayloadSharedEXT storage qualifier in GLSL.

The task payload functions as shared memory across the workgroup and persists down to the child mesh shader invocations. Its primary characteristics include:

  • Sized by the Application: The payload holds application-specific data, typically consisting of an array of surviving cluster indices, transformation matrices, or draw parameters.
  • Per-Dispatch Persistence: Data written to the payload by the task shader workgroup is read-only by the mesh shader workgroups spawned by that specific task invocation.
  • Compact Footprint: Because task payload memory consumes on-chip storage, keeping the structure minimal ensures high hardware occupancy and lower memory pressure.

The Dynamic Cluster Culling Process

Dynamic cluster culling takes advantage of the task payload through a multi-step parallel evaluation process:

1. Coarse Bounding Evaluation

Each invocation within a task shader workgroup reads the metadata for an individual cluster or a set of clusters. This metadata includes bounding spheres or oriented bounding boxes (OBBs), along with normal cones for orientation.

The invocation then executes standard culling algorithms:

  • Frustum Culling: Testing the cluster bounding volume against the active camera view frustum planes.
  • Cone Culling (Backface Culling): Comparing the cluster's normal cone apex and angle against the view vector to eliminate clusters pointing entirely away from the camera.
  • Occlusion Culling: Testing cluster bounds against a hierarchical Z-buffer (HZB) or depth pyramid.

2. Stream Compaction

Clusters that pass all culling checks are marked as visible. To prevent holes in the dispatch and optimize mesh shader utilization, the task shader performs a parallel stream compaction:

  • Subgroup ballot operations (subgroupBallot, subgroupInclusiveAdd) compute the total number of surviving clusters and assign each visible cluster a contiguous index.
  • Each thread with a surviving cluster writes the cluster's global ID into the array defined in the taskPayloadSharedEXT struct.

3. Dynamic Dispatch Emission

Once compaction is complete, a single invocation in the task workgroup issues the dispatch call via EmitMeshTasksEXT(visibleCount, 1, 1).

If zero clusters survive the tests, EmitMeshTasksEXT(0, 0, 0) is called. This immediately halts execution for that branch, preventing any mesh shaders from being scheduled on the GPU. If clusters survive, the exact number of required mesh shader workgroups is instantiated.

Receiving the Payload in the Mesh Shader

When the spawned mesh shader workgroups begin execution:

  1. Each mesh shader reads its respective entry from the task payload using its workgroup ID (e.g., payload.clusterIndices[gl_WorkGroupID.x]).
  2. The mesh shader fetches vertex and index buffers only for the validated cluster.
  3. Vertices are transformed, primitives are assembled, and visible geometry is sent to the rasterizer.

Performance Advantages

Using task shader payload sharing for dynamic culling provides three primary architectural benefits:

  • Zero Wasted Mesh Workgroups: Mesh shaders are never launched for culled clusters, preventing the allocation of execution slots and vector registers for non-visible primitives.
  • Reduced Memory Bandwidth: Index and vertex buffers are only fetched from VRAM for visible clusters, bypassing memory lookups for occluded geometry.
  • Subgroup-Level Efficiency: By compacting payloads dynamically, mesh shaders maintain full workgroup occupancy without encountering diverging execution paths caused by culled geometry.
