Rasterization Order Attachment Access in Vulkan

This article explains how the rasterization order attachment access extension in Vulkan eliminates data hazards during simultaneous fragment reads and writes. By enforcing a deterministic, per-pixel execution order based on primitive submission, Vulkan enables developers to perform programmable blending and single-pass read-modify-write operations on framebuffer attachments without incurring the performance penalties associated with subpass barriers or pipeline stalls.

In standard Vulkan execution, fragment shaders execute in parallel across multiple execution units. When multiple primitives overlap the same pixel coordinate, their fragments are processed concurrently. If a fragment shader reads from an attachment while writing back to that same attachment (a common pattern in custom blending, order-independent transparency, and deferred shading), race conditions occur. These manifest as Read-After-Write (RAW), Write-After-Read (WAR), or Write-After-Write (WAW) data hazards because standard Vulkan does not guarantee the completion order of fragment shader invocations covering the same pixel.

Traditionally, resolving these hazards required either using fixed-function hardware blending or splitting the workload across multiple subpasses linked by subpass dependencies and pipeline barriers. While barriers guarantee correct ordering, they force the GPU to stall or flush local fragment state, significantly degrading performance, especially on mobile Tile-Based Deferred Rendering (TBDR) architectures where maintaining data in fast on-chip tile memory is critical.

The VK_EXT_rasterization_order_attachment_access extension (and its vendor-specific predecessor VK_ARM_rasterization_order_attachment_access) resolves this issue by introducing fine-grained synchronization at the rasterizer level. It guarantees that any fragment shader reading from or writing to specified attachments (color, depth, or stencil) processes overlapping pixels strictly according to the original rasterization order of the incoming geometry.

The extension introduces specific subpass description flags:

  • VK_SUBPASS_DESCRIPTION_RASTERIZATION_ORDER_ATTACHMENT_COLOR_ACCESS_BIT_EXT
  • VK_SUBPASS_DESCRIPTION_RASTERIZATION_ORDER_ATTACHMENT_DEPTH_ACCESS_BIT_EXT
  • VK_SUBPASS_DESCRIPTION_RASTERIZATION_ORDER_ATTACHMENT_STENCIL_ACCESS_BIT_EXT

When these flags are enabled on a subpass, the hardware’s rasterizer serializes memory operations targeting the same pixel coordinates. For overlapping fragments generated by primitive \(A\) (submitted first) and primitive \(B\) (submitted second), the read and write operations of \(B\) are guaranteed to observe the completed writes of \(A\). Non-overlapping fragments continue to execute in parallel without restriction.

At the hardware level, this synchronization is managed without spilling data to external VRAM. On TBDR architectures, the GPU tracks per-pixel operations within the on-chip tile buffer, preventing read-modify-write collisions while keeping the data localized in high-speed cache. On desktop architectures with fragment shader interlock capabilities, the hardware enforces order via hardware-managed per-pixel locks.

By eliminating pipeline stalls and memory flushes, rasterization order attachment access allows developers to implement complex, fully programmable blending algorithms, custom depth-stencil tests, and dynamic G-buffer updates within a single subpass while maintaining strict memory consistency.
