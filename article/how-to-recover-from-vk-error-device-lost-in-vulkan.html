How to Recover from VK_ERROR_DEVICE_LOST in Vulkan

The VK_ERROR_DEVICE_LOST error indicates that the logical device has become unavailable due to a hardware hang, driver crash, operating system timeout (such as Windows TDR), or physical hardware removal. Gracefully recovering from this error requires an application to detect the failure immediately, decouple the graphics backend from the engine's core state, safely tear down the invalidated Vulkan objects, recreate the rendering pipeline from scratch, and resume execution without crashing or terminating the host process.

Detect and Isolate the Error

The error can be returned synchronously or asynchronously by nearly any Vulkan API call that submits work, checks synchronization, or presents to a surface (e.g., vkQueueSubmit, vkWaitForFences, vkAcquireNextImageKHR, or vkQueuePresentKHR). Once VK_ERROR_DEVICE_LOST is returned, the application must transition to an internal recovery state and halt any new command recording or queue submissions across all threads.

Diagnose the Root Cause

Before destroying the context, capture diagnostic telemetry to log what caused the crash. Vulkan provides diagnostic extensions that can be queried even after device loss occurs:

  • VK_EXT_device_fault: Allows querying specific hardware and memory fault descriptions directly from the driver.
  • VK_NV_device_diagnostic_checkpoints or VK_AMD_buffer_marker: Injects markers into the command stream to pinpoint the exact draw call, dispatch, or pipeline execution that triggered the GPU freeze.

Isolate the Host-Side State

A successful recovery model relies on a strict architectural separation between the high-level application state (such as scene graphs, camera positions, game logic, and CPU-side asset caches) and low-level Vulkan objects. If vertex data, textures, and shader binaries remain cached in system RAM or on disk, the application can rebuild the rendering context without re-executing core application logic.

Safely Destroy Stale Vulkan Objects

Once a device is lost, synchronization commands like vkDeviceWaitIdle or vkQueueWaitIdle will either return VK_ERROR_DEVICE_LOST or hang. Applications must bypass normal GPU synchronization and proceed directly to destroying resources.

According to the Vulkan specification, most vkDestroy* functions remain valid to call on a lost device. The application must iterate through and destroy:

  1. Pipelines, pipeline layouts, and descriptor sets.
  2. Framebuffers, render passes, and image views.
  3. Buffers, images, and their backing VkDeviceMemory allocations.
  4. Command pools and synchronization primitives (fences, semaphores).
  5. The swapchain (VkSwapchainKHR).
  6. The VkDevice itself.

The VkInstance and the native window's VkSurfaceKHR typically remain valid and do not need to be destroyed unless the underlying physical GPU was disconnected.

Re-enumerate and Recreate the Device

Query vkEnumeratePhysicalDevices to verify the state of the hardware. If a dynamic GPU switch occurred or an external GPU was unplugged, the application must select an alternate compatible physical device or wait for the driver to recover.

Once a valid physical device is confirmed:

  1. Call vkCreateDevice to obtain a fresh VkDevice.
  2. Retrieve new queue handles using vkGetDeviceQueue.
  3. Re-initialize memory allocators (such as Vulkan Memory Allocator).
  4. Recreate the swapchain associated with the existing VkSurfaceKHR.

Reload Assets and Rebuild Pipelines

Using the preserved CPU-side data, restore the rendering pipeline:

  1. Recompile or reload cached pipeline states and pipeline caches.
  2. Reallocate GPU memory and upload geometry, materials, and uniform data back to device-local memory.
  3. Reallocate and update descriptor pools and descriptor sets.
  4. Recreate command pools and allocate new command buffers for each frame in flight.

Re-synchronize and Resume Execution

Instantiate new synchronization primitives (fences and semaphores) in their appropriate initial states. Reset all frame indices and swapchain counters to zero. Once all resources are re-bound and validated, resume the primary render loop and begin submitting frames using the newly initialized device.
