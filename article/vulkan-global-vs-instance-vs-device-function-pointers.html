Vulkan Global vs Instance vs Device Function Pointers

The Vulkan API relies on an explicit command loader architecture that categorizes function pointers into global, instance, and device levels. This article explains the technical distinctions between these three levels, detailing how they are queried, the architectural scope of each tier, and why loading device-level functions directly is critical for minimizing execution overhead in performance-sensitive graphics and compute applications.

The Vulkan Loader and Dispatch Architecture

Vulkan is designed to minimize driver overhead and eliminate hidden global state. When an application links against the Vulkan loader library (vulkan-1.dll on Windows or libvulkan.so on Linux), the library acts as an intermediary rather than the full hardware driver. The loader is responsible for managing validation layers, extensions, and dispatching calls to the appropriate Installable Client Driver (ICD).

Because different layers and devices can be active simultaneously, function pointers exist in distinct scopes. Resolving functions at the correct scope determines whether a call incurs the overhead of the loader’s dispatch table or calls directly into the hardware driver.

Global-Level Function Pointers

Global functions operate independently of any specific VkInstance or VkDevice. They represent the entry points necessary to initialize the Vulkan runtime, inspect available platform capabilities, and create an instance.

  • Key Examples: vkCreateInstance, vkEnumerateInstanceExtensionProperties, vkEnumerateInstanceLayerProperties, and vkGetInstanceProcAddr.
  • How They Are Loaded: The core global entry points are exported statically by the Vulkan loader library. Alternatively, they can be dynamically resolved from the loader using platform-specific APIs (GetProcAddress on Windows, dlsym on POSIX systems) or by passing VK_NULL_HANDLE as the instance argument to vkGetInstanceProcAddr.
  • Scope: System-wide capabilities prior to runtime configuration.

Instance-Level Function Pointers

Instance functions require a valid VkInstance handle to execute. These commands interact with the created instance and are responsible for enumerating physical devices (the actual GPUs detected on the system) and querying hardware properties, features, and queue families before a logical device is created.

  • Key Examples: vkDestroyInstance, vkEnumeratePhysicalDevices, vkGetPhysicalDeviceProperties, vkGetPhysicalDeviceFeatures, and vkCreateDevice.
  • How They Are Loaded: Retrieved dynamically via vkGetInstanceProcAddr by supplying the valid VkInstance handle and the function name as a string.
  • Dispatch Behavior: The loader creates an instance dispatch table. Calling an instance-level command routes through the loader, which evaluates any enabled instance-level layers before forwarding the call to the corresponding physical device implementation.

Device-Level Function Pointers

Device functions operate on a specific logical device (VkDevice) or objects created from it, such as VkQueue, VkCommandBuffer, VkBuffer, and VkImage. These functions constitute the vast majority of the Vulkan API and handle resource creation, pipeline state configuration, synchronization, and command recording.

  • Key Examples: vkCmdDraw, vkQueueSubmit, vkBeginCommandBuffer, vkCreateBuffer, and vkWaitForFences.
  • How They Are Loaded: Retrieved dynamically via vkGetDeviceProcAddr using the initialized VkDevice handle.
  • Dispatch Behavior and Performance: Device functions can technically be loaded using vkGetInstanceProcAddr, but doing so forces the call through the loader's dispatch mechanism, which inspects the object handle at runtime to determine the target device. In contrast, retrieving function pointers via vkGetDeviceProcAddr skips the loader's internal dispatch lookup entirely, resolving to a direct jump into the ICD. For high-frequency calls such as command recording and queue submission, querying device-level pointers directly removes per-call indirection and maximizes rendering performance.
