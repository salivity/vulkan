Vulkan Subgroup Size and Invocation Limits Guide

In Vulkan, efficient GPU computing relies on understanding the hardware execution granularity known as subgroups. This article explains what a subgroup size represents, why it varies across hardware architectures, and how an engine queries subgroup limits and capabilities using standard Vulkan structures to deploy portable, vendor-agnostic compute and graphics pipelines.

Understanding Subgroup Size

A subgroup is a collection of invocations (threads) executing concurrently in lockstep on GPU execution units. Depending on the hardware vendor, this concept is physically implemented as an NVIDIA Warp (typically 32 invocations), an AMD Wavefront (either 32 or 64 invocations), or an Intel Execution Unit thread (often 8, 16, or 32 invocations).

The subgroupSize is the number of invocations in a single subgroup. Invocations within the same subgroup can communicate directly through on-chip SIMD-lane registers via subgroup operations—such as ballots, shuffles, votes, and arithmetic reductions—without needing to synchronize through slower Workgroup Shared Memory (shared variables) or global memory.

Querying Base Subgroup Properties

Vulkan 1.1 standardized subgroup functionality into core API queries. To determine the subgroup characteristics of a device, an engine chains VkPhysicalDeviceSubgroupProperties into the pNext pointer of VkPhysicalDeviceProperties2 and calls vkGetPhysicalDeviceProperties2:

VkPhysicalDeviceSubgroupProperties subgroupProperties{};
subgroupProperties.sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_SUBGROUP_PROPERTIES;

VkPhysicalDeviceProperties2 deviceProperties{};
deviceProperties.sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_PROPERTIES_2;
deviceProperties.pNext = &subgroupProperties;

vkGetPhysicalDeviceProperties2(physicalDevice, &deviceProperties);

After the call, subgroupProperties provides critical vendor-independent baseline information:

  • subgroupSize: The default invocation size of a subgroup for the physical device.
  • supportedStages: A bitmask of VkShaderStageFlagBits indicating in which pipeline stages subgroup operations can be executed (e.g., compute, fragment, vertex).
  • supportedOperations: A bitfield representing supported subgroup operations, including VK_SUBGROUP_FEATURE_BASIC_BIT, VK_SUBGROUP_FEATURE_VOTE_BIT, VK_SUBGROUP_FEATURE_BALLOT_BIT, and VK_SUBGROUP_FEATURE_SHUFFLE_BIT.
  • quadOperationsInAllStages: A boolean indicating whether 2x2 quad operations (like derivative-adjacent helpers) are available in all supported stages.

Querying Dynamic and Variable Subgroup Limits

Modern architectures, such as AMD's RDNA, support multiple wave sizes (e.g., Wave32 and Wave64) selectable per-pipeline. To query and control variable subgroup sizes, engines use features introduced in the VK_EXT_subgroup_size_control extension and integrated into Vulkan 1.3 core.

An engine queries the bounds of subgroup sizes by appending VkPhysicalDeviceSubgroupSizeControlProperties to VkPhysicalDeviceProperties2:

VkPhysicalDeviceSubgroupSizeControlProperties extSubgroupProperties{};
extSubgroupProperties.sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_SUBGROUP_SIZE_CONTROL_PROPERTIES;

VkPhysicalDeviceProperties2 deviceProperties{};
deviceProperties.sType = VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_PROPERTIES_2;
deviceProperties.pNext = &extSubgroupProperties;

vkGetPhysicalDeviceProperties2(physicalDevice, &deviceProperties);

This struct exposes:

  • minSubgroupSize: The minimum subgroup size supported by the device (e.g., 32 on AMD, 8 on Intel).
  • maxSubgroupSize: The maximum subgroup size supported by the device (e.g., 64 on AMD, 32 on Intel/NVIDIA).
  • maxComputeWorkgroupSubgroups: The maximum number of subgroups that can participate in a single compute workgroup.
  • requiredSubgroupSizeStages: A bitmask of shader stages where a developer can explicitly force a specific subgroup size.

Requesting Explicit Subgroup Sizes in Pipelines

When subgroupSizeControl features are enabled via VkPhysicalDeviceSubgroupSizeControlFeatures, an engine can request a specific subgroup size for a shader stage by attaching VkPipelineShaderStageRequiredSubgroupSizeCreateInfo to the pNext of VkPipelineShaderStageCreateInfo.

Engines typically use these queries to tailor compute workloads: selecting smaller sizes to maximize register allocation and occupancy, or choosing larger sizes to maximize cross-invocation sharing across broader data sets.
