Vulkan Sparse Texture Residency and Tile Loading

Sparse texture residency—often referred to as partially resident textures—allows Vulkan applications to allocate massive, high-resolution textures without allocating all the underlying physical memory upfront. By breaking texture resources into uniform, virtual tiles and allocating physical device memory only for visible or high-priority areas, Vulkan optimizes memory consumption and bandwidth. This article explains how Vulkan handles sparse image creation, standard tile alignment, residency feedback, and on-demand tile streaming through asynchronous queue operations.

Virtual Allocation and Sparse Flags

In a standard Vulkan pipeline, creating a VkImage requires binding a single, contiguous block of VkDeviceMemory via vkBindImageMemory. Sparse texturing bypasses this requirement by decoupling the virtual address space of the image from physical memory.

To enable residency, an image is created with specific flags in VkImageCreateInfo:

  • VK_IMAGE_CREATE_SPARSE_BINDING_BIT: Signals that the resource's memory backing can be managed sparsely with non-contiguous allocations.
  • VK_IMAGE_CREATE_SPARSE_RESIDENCY_BIT: Enables individual mip levels and regions to be partially resident, meaning tiles can be mapped or unmapped dynamically.

When these flags are set, the driver reserves a virtual address range for the full resolution of the image (often up to 16K x 16K or higher) without committing physical memory.

Tile Shapes and Mip Tails

GPUs process sparse textures in fixed block shapes, typically sized around 64 KB per tile. Before binding memory, the application queries these dimensions using vkGetImageSparseMemoryRequirements.

The query provides two critical structures:

  1. Tile Dimensions: The width, height, and depth (in texels) of a single sparse tile for each aspect mask.
  2. Mip Tail Information: Higher mip levels are large enough to be split into individual tiles. Once mip dimensions shrink below the size of a single tile, subdividing them becomes inefficient. The driver bundles these tiny mips into a single contiguous region called the "mip tail." The mip tail must be bound to physical memory as a single unit rather than on a per-tile basis.

Asynchronous Binding with vkQueueBindSparse

Instead of standard memory binding commands, sparse textures rely on vkQueueBindSparse. This is a queue-submission command that executes on any queue supporting VK_QUEUE_SPARSE_BINDING_BIT.

The binding process involves submitting a VkBindSparseInfo structure that details:

  • The target VkImage.
  • An array of VkSparseImageMemoryBind structs specifying the mip level, subresource offset (X, Y, Z), and extent of the region to be mapped.
  • The VkDeviceMemory object and memory offset to bind to that region.

Passing a null handle for the memory unbinds the tile, freeing the underlying VkDeviceMemory back to an application-managed memory pool. Because vkQueueBindSparse is a queue operation, it can be synchronized using semaphores and fences alongside transfer and graphics workloads.

Detecting Missing Tiles

For on-demand streaming to work, the engine must identify which tiles are required for rendering. Vulkan supports this through two primary approaches:

  1. Shader Residency Feedback: Shaders use sparse image sampling instructions (such as OpImageSparseSampleImplicitLod in SPIR-V). These instructions return two components: the sampled texel data and a residency code. The shader checks the code using sparseImageOpResultARB to determine if any sampled texels were unmapped. If unmapped tiles are hit, the shader can write the missing tile coordinates to a storage buffer.
  2. Software Virtual Texturing Feedback: The application renders a low-resolution visibility pass where fragments output the required tile coordinate and mip level directly to an offscreen render target. The CPU reads back this data or a compute shader processes it to build a list of tiles entering the camera's view frustum.

The On-Demand Streaming Loop

Once the application identifies the missing tiles, the streaming pipeline proceeds through the following steps:

  1. Physical Memory Allocation: The application assigns free memory blocks from a pre-allocated VkDeviceMemory pool.
  2. Mapping: vkQueueBindSparse maps the allocated memory to the specific subresource coordinates of the image.
  3. Data Upload: The application reads the compressed texel data from disk or storage into a staging VkBuffer. A copy command (vkCmdCopyBufferToImage) transfers the texels from the staging buffer into the newly bound sparse image tiles.
  4. Synchronization: A pipeline barrier or semaphore ensures the copy operation finishes before subsequent draw commands sample from the newly resident tiles.
  5. Eviction: When tiles fall outside the view frustum or drop in required detail, the engine submits a vkQueueBindSparse call to unbind the physical memory, returning those pages to the pool for reuse.
