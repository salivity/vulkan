Non-Coherent Atom Size in Vulkan Explained

In the Vulkan graphics and compute API, managing non-coherent host memory requires an understanding of how CPU caches synchronize with the GPU. This article explains what the nonCoherentAtomSize limit represents, how non-coherent host memory functions, and why Vulkan strictly requires memory flush and invalidate operations to align to this specific hardware-defined boundary.

Host-Coherent vs. Non-Coherent Memory

When allocating host-visible memory in Vulkan using VkMemoryPropertyFlags, developers typically choose between two primary synchronization behaviors:

  • Host-Coherent Memory (VK_MEMORY_PROPERTY_HOST_COHERENT_BIT): Writes made by the CPU automatically become visible to the GPU, and vice versa, without explicit software intervention.
  • Non-Coherent Memory (Absence of VK_MEMORY_PROPERTY_HOST_COHERENT_BIT): Writes made by the CPU reside in the CPU's local caches and are not automatically guaranteed to be visible to the GPU. Similarly, writes from the GPU are not automatically reflected in the CPU's cache.

To make host writes visible to the GPU on non-coherent memory, you must call vkFlushMappedMemoryRanges. To make GPU writes visible to the host, you must call vkInvalidateMappedMemoryRanges.

What Is nonCoherentAtomSize?

The nonCoherentAtomSize is a hardware property defined inside VkPhysicalDeviceLimits. It represents the minimum granularity, in bytes, at which host-accessible memory operations (flushes and invalidations) can be performed.

At a hardware level, CPUs and memory controllers do not synchronize memory on a single-byte basis. Instead, they operate on cache lines or memory transaction blocks—commonly 64 or 128 bytes. The nonCoherentAtomSize reflects this underlying hardware granularity.

Alignment Requirements

The Vulkan specification mandates strict alignment rules for VkMappedMemoryRange:

  1. Offset Alignment: The offset member must be an integer multiple of VkPhysicalDeviceLimits::nonCoherentAtomSize.
  2. Size Alignment: The size member must either be an integer multiple of nonCoherentAtomSize or extend specifically to the end of the mapped memory range (or VK_WHOLE_SIZE).

Why Flush Ranges Must Be Aligned

The necessity of aligning flush and invalidate ranges to nonCoherentAtomSize stems from how cache architectures operate and the risks associated with partial-line operations:

1. Prevention of Data Corruption and False Sharing

Because CPU caches operate on entire cache lines, evicting (flushing) or discarding (invalidating) a region smaller than a cache line affects all bytes within that line.

  • Invalidation Risk: If you attempt to invalidate a 16-byte region in the middle of a 64-byte cache line, the CPU cache controller must invalidate the full 64-byte line. If other parts of that cache line contain dirty, unwritten CPU data, that valid CPU data is permanently lost.
  • Flush Risk: Flushing a partial line forces the entire cache line to be written back to main memory. If adjacent data in that cache line was being modified independently by another device or thread, the flush may overwrite newer data with stale data.

2. Hardware and Driver Simplicity

Enforcing strict boundaries in the specification shifts the responsibility of safe boundary management to the application. This eliminates the need for the Vulkan driver to perform expensive read-modify-write operations or software padding when synchronizing CPU and GPU caches, maximizing performance and reducing driver overhead.

3. Cross-Platform Determinism

Different hardware architectures use different cache structures. For example, desktop CPUs typically feature 64-byte cache lines, while mobile chipsets or integrated architectures may feature 128-byte or larger cache granularities. By exposing nonCoherentAtomSize and enforcing alignment rules, Vulkan ensures portable, predictable memory synchronization across all compliant devices.
