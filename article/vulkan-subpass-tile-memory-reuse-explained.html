Vulkan Subpass Tile Memory Reuse Explained

Tile-based deferred rendering (TBDR) architectures optimize bandwidth by keeping render targets in fast, on-chip tile storage rather than continually writing out to system RAM. In the Vulkan graphics API, subpasses provide an explicit mechanism that informs the driver and hardware that intermediate render targets are consumed locally by the next rendering phase. By utilizing subpass dependencies, regional execution barriers, and lazily allocated memory, developers allow the GPU to retain and alias on-chip tile memory across multiple render phases, significantly reducing memory traffic and thermal overhead.

The Role of Tile Memory in TBDR Architectures

Mobile and modern integrated GPUs divide the framebuffer into small discrete regions, typically 16x16 or 32x32 pixels, known as tiles. Instead of writing fragments directly to external video memory (VRAM), the GPU processes each tile in dedicated, high-speed on-chip registers or Static RAM (SRAM). External memory transfers represent a substantial power and latency cost. Therefore, maximizing the amount of rendering performed entirely within this on-chip storage is critical for performance.

Declaring Subpass Dependencies and Regional Execution

Within a single VkRenderPass, work is structured into sequential VkSubpassDescription blocks. When subpass \(N+1\) depends on the output of subpass \(N\), Vulkan synchronizes them using a VkSubpassDependency.

To enable tile memory reuse, this dependency must include the VK_DEPENDENCY_BY_REGION_BIT flag. This flag guarantees that operations are spatially localized: a fragment at coordinates \((x, y)\) in subpass \(N+1\) only depends on the output of the fragment at the exact same \((x, y)\) coordinate generated in subpass \(N\). Because there is no cross-pixel dependency across the render target, the hardware does not need to synchronize the entire framebuffer or flush intermediate results to external VRAM. The contents of the on-chip tile storage remain valid and accessible for the next subpass.

Input Attachments and subpassLoad()

Rather than sampling an intermediate render target as a standard texture, a subsequent subpass declares it as an input attachment (VK_IMAGE_USAGE_INPUT_ATTACHMENT_BIT). In GLSL or SPIR-V shaders, these attachments are read using subpassLoad() functions rather than standard texture sampling functions (texture()).

The subpassLoad() intrinsic restricts fetching strictly to the current pixel’s coordinates. Under the hood, the hardware driver maps this operation directly to a register read or an internal tile cache read. No texture filtering, mipmapping, or coordinate transforms occur, allowing the hardware to treat the output of the previous subpass as an immediate local input within the same hardware registers.

Memory Optimization with Lazily Allocated Images

Intermediate targets that do not need to persist after the render pass finishes—such as G-buffer attachments in deferred shading or depth/stencil buffers used only for intermediate testing—can be created with the VK_IMAGE_USAGE_TRANSIENT_ATTACHMENT_BIT.

When binding memory to these transient images, allocating them with VK_MEMORY_PROPERTY_LAZILY_ALLOCATED_BIT tells the Vulkan implementation that the image may never need physical backing in external memory. If all reads and writes are contained within the tile storage via subpasses:

  1. Load Operations: The initial attachment state can use VK_ATTACHMENT_LOAD_OP_DONT_CARE or VK_ATTACHMENT_LOAD_OP_CLEAR, allocating tile cache lines on chip without fetching from VRAM.
  2. Intermediate Subpasses: Subsequent subpasses read and overwrite the tile data in-place via input attachments.
  3. Store Operations: The final attachment state is set to VK_ATTACHMENT_STORE_OP_DONT_CARE.

Because the data is never stored back to main memory, the physical VRAM allocation is bypassed entirely. The GPU simply repurposes the on-chip tile memory addresses and register allocations for subsequent subpasses or subsequent tiles in the execution queue.
