Vulkan Local Memory Limits on Active Workgroups

In Vulkan compute pipelines, workgroup local memory—often referred to as shared memory—is a high-speed, on-chip hardware resource allocated per compute unit. Because each dispatched workgroup requests a fixed allocation of this memory, the total physical capacity of the compute unit's local data share directly dictates how many workgroups can execute concurrently. When a shader requests a large memory footprint, it reduces the number of simultaneously resident workgroups, limiting GPU occupancy and potentially degrading overall compute performance.

Hardware Resource Constraints per Compute Unit

Modern GPU architectures divide execution into compute units (CUs in AMD terminology) or Streaming Multiprocessors (SMs in NVIDIA terminology). Each compute unit houses execution engines, register files, and a dedicated pool of low-latency on-chip memory typically ranging from 32 KB to 128 KB.

In Vulkan, this memory is exposed via the Workgroup storage class in SPIR-V (or the shared keyword in GLSL). Unlike global device memory, workgroup local memory is physically bound to the compute unit executing that specific workgroup. Because the data must persist for the entire lifetime of the workgroup to allow barrier synchronization, the compute unit cannot dynamically page this memory out to VRAM.

The Allocation Formula and Occupancy Limits

When the Vulkan driver schedules a compute dispatch, the hardware scheduler assesses whether a compute unit has sufficient resources to accept an incoming workgroup. The calculation governing the local memory ceiling is deterministic:

\[\text{Active Workgroups} \le \left\lfloor \frac{\text{Total Available Local Memory per Compute Unit}}{\text{Local Memory Statically Allocated per Workgroup}} \right\rfloor\]

For example, consider a GPU architecture featuring 64 KB of local memory per compute unit:

  • If a compute shader requires 16 KB of shared memory, the compute unit can concurrently host up to 4 workgroups (provided register and thread count limits allow it).
  • If the shader's allocation increases slightly to 17 KB, the maximum number of active workgroups drops immediately to 3, leaving 13 KB of local memory unutilized.
  • If a single workgroup requests 33 KB, the scheduler can only allocate 1 workgroup to that compute unit, wasting 31 KB of memory and drastically lowering parallel throughput.

This discrete drop in parallelism is commonly referred to as an "occupancy cliff."

Impact on Latency Hiding

GPUs rely on high occupancy—having many active threads ready to execute—to hide memory latency caused by global memory reads, texture fetches, and complex arithmetic operations. When workgroup local memory usage limits the active workgroups to a low number, the compute unit runs out of alternative warps or wavefronts to switch between while waiting for memory transactions to complete. This forces the execution units into idle stall states, diminishing theoretical compute throughput.

Resource Balancing and Optimization

To prevent local memory from becoming the primary bottleneck in Vulkan:

  • Query Device Capabilities: Inspect VkPhysicalDeviceLimits::maxComputeSharedMemorySize to know the hard upper bound of supported shared memory across target hardware.
  • Tune Workgroup Dimensions: Balance invocation count and memory allocation. It is often more efficient to split large workgroups into smaller sizes (e.g., 64 or 128 invocations) that require less shared memory, allowing the scheduler greater flexibility in fitting multiple workgroups onto a single compute unit.
  • Leverage Specialization Constants: Use Vulkan specialization constants to parameterize shared memory array sizes. This allows tailoring allocation sizes at pipeline creation time based on the specific GPU architecture detected at runtime.
  • Reuse Shared Buffers: Alias local memory or reuse variables across non-overlapping phases of the compute shader to minimize the aggregate footprint declared in the shader code.
