Vulkan Sparse Virtual Texture Page Table Mapping

This article explains how the page table mapping mechanism operates for sparse virtual textures in the Vulkan API. It details how Vulkan decouples virtual image allocations from physical memory backing, how tile granularities and mip tails are structured, and how the driver and GPU translate runtime virtual texel accesses into physical memory addresses via sparse queue binding operations.

The Virtual vs. Physical Memory Decoupling

In standard Vulkan texture creation, a VkImage must be bound to a contiguous block of physical device memory (VkDeviceMemory) large enough to accommodate the entire texture across all mip levels and array layers. Sparse virtual texturing bypasses this requirement by separating the image's virtual address space from its physical backing.

When an image is created with VK_IMAGE_CREATE_SPARSE_BINDING_BIT and VK_IMAGE_CREATE_SPARSE_RESIDENCY_BIT, the Vulkan driver reserves an address range in the GPU’s virtual memory space without committing actual VRAM. Memory is only allocated and committed for regions of the texture that are actively requested or rendered, drastically reducing memory footprints for high-resolution surfaces.

Tile Granularity and Memory Requirements

Sparse textures are partitioned into standardized, multi-dimensional blocks called sparse memory tiles (or pages). To establish the page table mappings, the application queries these dimensions using vkGetImageSparseMemoryRequirements.

The implementation returns one or more VkSparseImageMemoryRequirements structures that dictate:

  • Tile Dimensions: The width, height, and depth of a memory page for a given format and aspect (typically aligning with standard GPU hardware pages, such as 64 KB blocks).
  • Mip Tail First LOD: The mip level at which individual mips become smaller than a single memory tile.
  • Mip Tail Size and Offset: The aggregate memory requirements needed to back all smaller mip levels as a single continuous unit.

Because each standard tile corresponds to a discrete page in the underlying memory architecture, virtual address translation happens at the granularity of these individual tiles.

The Sparse Binding Process (vkQueueBindSparse)

The physical-to-virtual connection is not updated through command buffers; instead, it is executed directly on a queue that supports sparse binding (a queue family marked with VK_QUEUE_SPARSE_BINDING_BIT) using the vkQueueBindSparse function.

The mapping workflow functions as follows:

  1. Allocating Physical Pages: The application allocates dedicated VkDeviceMemory blocks or sub-allocates from a pre-allocated pool to act as physical page frames.
  2. Defining the Bind Array: The application builds VkSparseImageMemoryBind structures. Each structure defines:
    • subresource: The mip level and array layer.
    • offset: The 3D coordinates (x, y, z) defining the tile's position in the virtual image.
    • extent: The dimensions of the region to be mapped (matching tile multiples).
    • memory: The VkDeviceMemory handle providing physical storage.
    • memoryOffset: The byte offset within the physical device memory.
  3. Submission and Synchronization: The mapping request is packaged into a VkBindSparseInfo structure and submitted via vkQueueBindSparse. Because binding updates the GPU’s internal page tables asynchronously, Vulkan provides semaphores and fences to synchronize these updates with rendering commands.

To unbind or evict a tile, the same operation is submitted with the memory field set to VK_NULL_HANDLE.

GPU Page Table Architecture and Address Translation

The GPU’s internal memory management unit (MMU) handles runtime address translation using a multi-level page table structure:

  1. Texture Coordinate Calculation: A shader samples a texture coordinate \((u, v, w)\) at a specific level of detail (LOD).
  2. Virtual Page Identification: The texture mapping unit (TMU) calculates the corresponding virtual tile index based on the texel coordinate and the tile dimensions reported by the driver.
  3. Page Table Lookup: The MMU traverses the GPU page tables:
    • Resident Tile (Page Hit): If the page table entry (PTE) contains a valid physical address, the MMU resolves the virtual tile index to the corresponding physical offset in VkDeviceMemory. The texel data is fetched normally.
    • Unbound Tile (Page Fault / Non-resident): If the entry points to VK_NULL_HANDLE (unmapped), the page table entry is marked as non-resident.

Residency Handling in Shaders

Unlike standard CPU virtual memory that triggers an interrupt on an unmapped page fault, Vulkan handles sparse non-residency gracefully inside hardware sampling units.

When sampling from partially populated sparse textures, shaders use specialized SPIR-V instructions (such as OpImageSparseSampleImplicitLod). These instructions return two components:

  1. The fetched color/data value (typically returning zero or a defined default if unmapped).
  2. A residency status code.

Shaders query the residency code via the Vulkan GLSL/HLSL intrinsic sparseImageOpResult(). If a tile is determined to be non-resident, the application can record this miss and dynamically stream in the missing page, queuing a new vkQueueBindSparse operation for subsequent frames.

Mip Tail Mapping

When mip levels become smaller than the dimension of a single hardware tile, managing individual page table entries becomes inefficient. Vulkan solves this with the Mip Tail.

All mip levels equal to or greater than the imageMipTailFirstLod index are grouped together. Rather than mapping discrete 3D tiles, the entire tail is mapped using a single VkSparseImageMemoryBind entry that covers the combined byte size of the remaining mip levels. This reduces page table fragmentation and minimizes metadata overhead on the memory management unit.
