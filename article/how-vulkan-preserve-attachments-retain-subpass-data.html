How Vulkan Preserve Attachments Retain Subpass Data

Vulkan’s render pass architecture is designed to optimize memory bandwidth by dividing rendering workloads into discrete subpasses, particularly on tile-based GPUs. In multi-subpass pipelines, intermediate data written in an early subpass may not be needed in the immediate next subpass, but might be required in a later one. Preserve attachments (pPreserveAttachments) solve this lifecycle challenge by explicitly telling the Vulkan driver to maintain an attachment's contents intact across subpasses where it is neither written to nor read from, preventing data corruption and hardware-level cache eviction.

The Subpass Attachment Problem

In a Vulkan VkRenderPass, each VkSubpassDescription defines the attachments it actively interacts with:

  • Color attachments (pColorAttachments)
  • Input attachments (pInputAttachments)
  • Depth/stencil attachments (pDepthStencilAttachment)
  • Resolve attachments (pResolveAttachments)

When an attachment is referenced in these arrays, the Vulkan implementation knows it must allocate resources and manage state for that data during the subpass. However, if a subpass does not explicitly reference an attachment in any of these roles, the implementation assumes the subpass has no interest in that attachment's current contents.

On Tile-Based Deferred Rendering (TBDR) architectures—common in mobile and integrated graphics hardware—render pass data often lives in fast, on-chip tile memory rather than external VRAM. If a subpass does not bind an attachment, the hardware is free to repurpose that fast on-chip memory space for other operations, effectively discarding or overwriting the intermediate data.

How Preserve Attachments Work

To ensure intermediate data survives across subpasses where it remains idle, Vulkan provides the pPreserveAttachments field within VkSubpassDescription.

An attachment listed in pPreserveAttachments is defined strictly by its integer index pointing to the pAttachments array in VkRenderPassCreateInfo. When specified:

  1. Hardware Reservation: The driver is instructed that the specified attachment's data must persist through the execution of the current subpass, even though the shaders and fixed-function stages in this subpass do not bind or modify it.
  2. Preventing Premature Eviction: On TBDR hardware, the driver will either preserve the fast tile-local storage for that attachment across the subpass or, if memory pressure demands it, safely spill the data and restore it before the subsequent subpass that consumes it.
  3. Synchronization Guarantees: Combined with proper VkSubpassDependency definitions, preserve attachments ensure that pipeline barrier dependencies accurately track the lifetime and memory consistency of the data across the entire execution graph.

A Practical Scenario

Consider a three-subpass render pass:

  • Subpass 0: Generates geometric data and writes to Attachment A (G-Buffer) and Attachment B (Material IDs).
  • Subpass 1: Performs screen-space ambient occlusion (SSAO), reading Attachment A as an input attachment and writing to Attachment C. Subpass 1 does not use Attachment B.
  • Subpass 2: Executes final composition, reading Attachment A, Attachment B, and Attachment C to produce the final image.

Without intervention, Attachment B is vulnerable during Subpass 1. Because Subpass 1 does not bind Attachment B as an input or color attachment, the implementation might discard Attachment B's contents to optimize memory.

By listing the index of Attachment B in Subpass 1’s pPreserveAttachments array, the developer guarantees that the data written in Subpass 0 remains intact until Subpass 2 reads it.

Architectural Efficiency

Preserve attachments allow Vulkan applications to keep complex, multi-stage rendering pipelines confined to a single VkRenderPass. Without preserve attachments, an application would have to split rendering workloads into separate render passes, forcing data to be flushed to high-bandwidth external VRAM and reloaded. By preserving data within the subpass structure, applications maximize the use of on-chip caches and maintain optimal memory efficiency.
