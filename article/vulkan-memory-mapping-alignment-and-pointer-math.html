Vulkan Memory Mapping Alignment and Pointer Math

In Vulkan, writing a custom memory manager requires managing device allocations and translating those allocations into usable CPU pointers for host-visible memory. A critical constraint in this process is minMemoryMapAlignment, a physical device limit that governs the valid starting offsets when calling vkMapMemory. Failing to account for this alignment constraint can lead to undefined behavior, runtime validation errors, or corrupted pointer arithmetic. This article explains how memory mapping offset alignment affects host pointer calculations, details the differences between persistent and dynamic mapping, and demonstrates the correct pointer math required to safely suballocate host-visible device memory.

The Alignment Constraint: minMemoryMapAlignment

When allocating memory using vkAllocateMemory, the driver returns a large block of VkDeviceMemory. To write data from the host (CPU), the application maps this memory using vkMapMemory. The Vulkan specification mandates that the offset parameter passed to vkMapMemory must be an integer multiple of VkPhysicalDeviceLimits::minMemoryMapAlignment (typically 64 bytes on modern hardware).

Custom allocators rarely allocate a distinct VkDeviceMemory handle for every resource. Instead, they allocate large slabs (e.g., 64 MiB or 256 MiB) and suballocate smaller segments for individual buffers and images. If a custom allocator attempts to dynamically map only the specific range assigned to a suballocation, the suballocation's offset within the VkDeviceMemory slab may not satisfy minMemoryMapAlignment.

Dynamic Mapping vs. Persistent Mapping

The impact of minMemoryMapAlignment on pointer arithmetic depends directly on your memory mapping architecture:

1. Dynamic Mapping (Per-Allocation Mapping)

If you map and unmap memory on demand, you must align the mapping boundaries explicitly:

  • Rounded Down Offset: If a suballocation begins at byte offset A, and A is not a multiple of minMemoryMapAlignment, vkMapMemory cannot be called with offset A. You must round A down to the nearest multiple: \[\text{Aligned Offset} = A - (A \bmod \text{minMemoryMapAlignment})\]

  • Adjusted Size: The mapping size must be increased by the difference between A and the aligned offset so that the requested range is fully covered.

  • Pointer Correction: vkMapMemory returns a host pointer (void* pData) corresponding to the aligned offset. To reach the actual suballocation data, you must apply an adjustment:

    uint8_t* mappedBase = (uint8_t*)pData;
size_t offsetAdjustment = allocationOffset - alignedOffset;
void* suballocationHostPtr = mappedBase + offsetAdjustment;

2. Persistent Mapping (Recommended Approach)

To avoid continuous pointer adjustment and mapping overhead, the industry standard is persistent mapping. When a host-visible VkDeviceMemory slab is allocated, map the entire slab once from offset 0 to VK_WHOLE_SIZE (or the slab's total capacity).

Since offset 0 is always a valid multiple of minMemoryMapAlignment, this completely bypasses runtime alignment checks for vkMapMemory. The pointer math simplifies to standard relative offsetting:

uint8_t* persistentBase = (uint8_t*)pMappedData; // mapped with offset = 0
void* suballocationHostPtr = persistentBase + suballocationOffset;

Resource Alignment vs. Mapping Alignment

Even with persistent mapping, pointer math interacts with other alignment limits. Different Vulkan resources have independent alignment requirements:

  • Buffer Resource Requirements: VkMemoryRequirements::alignment dictates the offset alignment inside the VkDeviceMemory block.
  • Descriptor Usage Constraints: Uniform buffers must align to minUniformBufferOffsetAlignment, and storage buffers must align to minStorageBufferOffsetAlignment.

When performing pointer arithmetic on the host side, your allocator must ensure that the GPU offset (allocationOffset) satisfies both the resource's Vulkan requirements and, if using dynamic mapping, the map alignment. A common design is to enforce that all suballocations within host-visible slabs are aligned to the least common multiple (or maximum) of minMemoryMapAlignment and the respective resource alignment. This unifies host-side and device-side offsets, ensuring that allocationOffset is naturally valid for host mapping operations.

Non-Coherent Memory and Atom Alignment

If the allocated memory type is host-visible but lacks the VK_MEMORY_PROPERTY_HOST_COHERENT_BIT property, host writes must be flushed using vkFlushMappedMemoryRanges, and host reads must be preceded by vkInvalidateMappedMemoryRanges.

Both operations require that the offset in VkMappedMemoryRange be a multiple of VkPhysicalDeviceLimits::nonCoherentAtomSize, and the size must either be a multiple of nonCoherentAtomSize or extend to the very end of the memory block.

When calculating the flush range for a suballocation:

  1. Round down the flush start: \[\text{Flush Offset} = A - (A \bmod \text{nonCoherentAtomSize})\]
  2. Round up the flush end: \[\text{Flush End} = \lceil (A + \text{Size}) / \text{nonCoherentAtomSize} \rceil \times \text{nonCoherentAtomSize}\]
  3. Set the flush size to \(\text{Flush End} - \text{Flush Offset}\).

If multiple suballocations share the same nonCoherentAtomSize cache line, an invalidation or flush from one suballocation can inadvertently overwrite or discard pending writes from an adjacent suballocation. Consequently, memory allocators must pad suballocations in non-coherent memory so that independent allocations do not share any atom boundary.
