Tracking Host Allocations with Vulkan Callbacks

This article examines the VkAllocationCallbacks structure in the Vulkan API, explaining its core components, its role in intercepting driver-level CPU memory operations, and the mechanism through which game engines utilize it to monitor, profile, and manage internal host allocations.

Understanding the Host Memory Allocator Struct

In Vulkan, memory is strictly divided into device memory (GPU-accessible memory managed via VkDeviceMemory) and host memory (CPU memory used by the Vulkan driver for internal data structures, object representations, and state management). By default, the Vulkan driver allocates host memory using the platform’s default memory management functions, such as malloc and free.

To gain control over these CPU allocations, Vulkan provides the VkAllocationCallbacks structure. When creating API objects through functions like vkCreateInstance, vkCreateDevice, or vkCreateBuffer, developers can pass a pointer to this structure instead of NULL.

The VkAllocationCallbacks structure consists of the following members:

  • pUserData: An arbitrary pointer passed through to all callback functions, typically pointing to an engine's custom memory tracking context.
  • pfnAllocation: A function pointer responsible for allocating a specified size and alignment of host memory.
  • pfnReallocation: A function pointer for resizing an existing allocation.
  • pfnFree: A function pointer for releasing previously allocated memory.
  • pfnInternalAllocation: A notification callback triggered when the driver allocates memory internally through platform-specific mechanisms.
  • pfnInternalFree: A notification callback triggered when such internal memory is released.

How Callbacks Intercept and Track Allocations

The tracking mechanism operates in two distinct operational modes: direct allocation interception and internal allocation reporting.

Direct Interception

When the driver requires CPU memory for an object, it invokes the user-defined pfnAllocation callback rather than the OS-level allocator. This function receives the size of the allocation, required memory alignment, allocation scope (VkSystemAllocationScope), and the custom pUserData pointer.

Through pUserData, the callback routes the request to the engine's memory management subsystem. The engine allocates the memory using its internal heap or custom memory arenas, updates counters tracking the current and peak CPU memory footprint, records diagnostic data (such as call sites or timestamps), and returns the pointer to the driver. The VkSystemAllocationScope parameter categorizes the lifespan of the memory—ranging from short-lived command tracking (VK_SYSTEM_ALLOCATION_SCOPE_COMMAND) to the lifetime of the entire instance (VK_SYSTEM_ALLOCATION_SCOPE_INSTANCE)—which allows the engine to assign allocations to optimal memory pools.

Internal Allocation Notifications

Certain drivers must allocate memory through native OS interfaces or runtime libraries that bypass custom allocators (such as executable memory for runtime shader compilation). In these scenarios, the driver invokes pfnInternalAllocation and pfnInternalFree.

These callbacks do not allocate memory directly; instead, they function strictly as informative hooks. The engine inspects the size, allocation type, and allocation scope reported by the callback and updates internal telemetry counters. This guarantees that total CPU memory consumption remains visible to the engine’s diagnostic tools, even when the underlying memory cannot be redirected through custom allocators.

Engine Integration Considerations

To reliably track allocations via VkAllocationCallbacks, the custom callback implementations must be entirely thread-safe, as Vulkan drivers may trigger allocations concurrently across multiple worker threads. Engine allocators typically utilize lock-free atomic operations to track overall byte counts, or use thread-local allocation contexts to minimize lock contention. When implemented correctly, these callbacks enable development teams to detect driver-level memory leaks, enforce strict host-memory budgets, and diagnose fragmentation issues within complex rendering pipelines.
