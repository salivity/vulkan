OpenCL and Vulkan Sync Using Timeline Semaphores

Timeline semaphores provide a unified, low-overhead mechanism for coordinating workloads between OpenCL and Vulkan without requiring expensive CPU-side synchronization. By utilizing a shared, monotonically increasing 64-bit integer counter exported across native platform handles, both APIs can signal and wait on fine-grained execution milestones entirely on the GPU. This eliminates the coarse-grained, single-use restrictions of legacy binary semaphores and enables complex, lock-free heterogeneous compute and graphics pipelines.

The Interoperability Challenge

Modern heterogeneous applications often combine OpenCL for specialized scientific computing, machine learning, or legacy compute kernels with Vulkan for real-time graphics rendering and display output. Historically, synchronizing data between these two APIs was inefficient:

  1. CPU Fences and Pipeline Stalls: Applications were forced to wait on host-side fences (vkWaitForFences and clFinish), stalling the CPU to ensure one API completed execution before the other began.
  2. Binary Semaphore Limitations: Traditional binary semaphores (VkSemaphore and standard cl_event objects) maintain only a binary signaled/unsignaled state. They are single-use per submission, require strict 1:1 signal-wait pairing, and must be submitted in execution order, making non-linear dependency graphs difficult to manage.

The Timeline Semaphore Model

Timeline semaphores replace the simple binary flag with a 64-bit unsigned integer payload. Instead of toggling between unsignaled and signaled:

  • A signal operation sets the timeline counter to a strictly higher value upon completion of a batch of GPU commands.
  • A wait operation blocks GPU execution of dependent work until the timeline counter reaches or exceeds a specified target value.

Because the counter is monotonically increasing, multiple submissions across different queues or APIs can wait on or signal the same primitive without resetting it. Furthermore, operations can be scheduled out-of-order on the host, as the GPU will naturally serialize execution based on the expected numeric milestones.

Bridging the APIs via External Handles

Inter-API synchronization is made possible by aligning extension ecosystems in both Khronos APIs:

  • Vulkan Support: Provided natively in Vulkan 1.2 (or via VK_KHR_timeline_semaphore) along with external memory and semaphore extensions (VK_KHR_external_semaphore, VK_KHR_external_semaphore_fd, or VK_KHR_external_semaphore_win32).
  • OpenCL Support: Provided via the cl_khr_semaphore extension family, specifically cl_khr_semaphore_timeline and external handle extensions like cl_khr_external_semaphore_opaque_fd or cl_khr_external_semaphore_win32.

Both APIs define their synchronization objects over shared native operating system abstractions—typically file descriptors (opaque_fd) on Linux/Android or shared NT handles (HANDLE) on Windows.

Implementation Workflow

Bridging OpenCL and Vulkan involves four discrete stages:

1. Semaphore Creation and Export

The application creates a timeline semaphore in one API, explicitly marking it as exportable. For example, in Vulkan, a VkSemaphore is created with VkSemaphoreTypeCreateInfo set to VK_SEMAPHORE_TYPE_TIMELINE and an initial value (often 0). An ExportSemaphoreCreateInfo structure is chained to allow exporting via the platform's handle type.

2. Handle Sharing and Import

The underlying native primitive is exported:

  • In Vulkan via vkGetSemaphoreFdKHR (Linux) or vkGetSemaphoreWin32HandleKHR (Windows).
  • In OpenCL, this native handle is passed into clCreateSemaphoreWithPropertiesKHR using property attributes such as CL_SEMAPHORE_TYPE_KHR = CL_SEMAPHORE_TYPE_TIMELINE_KHR and CL_SEMAPHORE_HANDLE_OPAQUE_FD_KHR.

Both APIs now point to the exact same underlying GPU driver sync primitive.

3. Execution and Cross-Signaling

Commands can now be dispatched concurrently:

  • OpenCL Compute Phase: OpenCL enqueues a kernel and registers a signal operation via clEnqueueSignalSemaphoresKHR, targeting a value of 1.
  • Vulkan Render Phase: Vulkan submits draw calls via vkQueueSubmit configured with a VkTimelineSemaphoreSubmitInfo structure that pauses the graphics queue until the semaphore counter reaches 1. Vulkan can simultaneously register a subsequent signal to advance the semaphore to value 2 when rendering completes.
  • Return Loop: OpenCL enqueues the next iteration of compute work with clEnqueueWaitSemaphoresKHR configured to unblock only when the semaphore hits value 2.

4. Shared Memory Access Coordination

When combined with external memory sharing (cl_khr_external_memory and VK_KHR_external_memory), memory ownership transitions are paired directly with semaphore counter milestones. The application does not need to recreate buffers, copy memory across the PCI bus, or perform explicit driver cache flushing on the host.

Technical Advantages

Timeline semaphores provide several critical performance advantages for heterogeneous graphics and compute pipelines:

  • Zero CPU-Side Stalling: Host threads enqueue all work ahead of time. Work scheduling between OpenCL and Vulkan is resolved entirely in the GPU hardware schedulers and firmware.
  • Granular Multi-Stage Pipelining: An OpenCL processing pipeline can signal milestone 1 after writing to Buffer A, and milestone 2 after writing to Buffer B. Vulkan can consume Buffer A immediately upon milestone 1 without waiting for the entire OpenCL command queue to finish.
  • Simplified Resource Lifecycles: Unlike binary semaphores, timeline semaphores do not need constant allocation, destruction, or re-exporting per frame, dramatically reducing runtime driver overhead.
