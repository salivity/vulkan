Using VkSemaphore for Vulkan GPU Queue Coordination

This article examines how VkSemaphore objects facilitate coarse-grained synchronization across distinct GPU queues in the Vulkan API. It details the necessity of cross-queue coordination, contrasts binary and timeline semaphores, breaks down the wait-signal execution model, and explains how semaphores manage resource ownership transfers between different hardware engines without stalling the host CPU.

The Need for Cross-Queue Synchronization

Modern GPUs expose multiple independent hardware queues, typically categorized into graphics, compute, and transfer families. In Vulkan, these queues execute command buffers asynchronously and concurrently. While this parallelism maximizes hardware utilization, it introduces data hazards when operations in one queue depend on the output of another.

Internal command-buffer primitives, such as vkCmdPipelineBarrier, are strictly intra-queue mechanisms. They cannot synchronize operations across different VkQueue handles. Coordinating distinct queues requires inter-queue synchronization primitives, a role fulfilled entirely on the GPU timeline by VkSemaphore.

How VkSemaphore Functions

A VkSemaphore is a GPU-to-GPU synchronization object. Unlike VkFence, which allows the CPU to wait for GPU tasks, a semaphore allows one GPU queue submission to block until another queue submission completes a specific execution milestone, all without host intervention.

Semaphores are injected into queue operations during submission via vkQueueSubmit (or through the presentation engine via vkQueuePresentKHR). The core workflow operates through signaling and waiting:

  1. Signaling: A batch submitted to Queue A is designated to signal a specific semaphore once its operations finish.
  2. Waiting: A batch submitted to Queue B is configured to wait on that same semaphore before beginning execution or before proceeding past a specified pipeline stage.

Because the synchronization is evaluated directly by the hardware scheduler, the CPU simply enqueues the work and continues execution, avoiding expensive host stalls.

Binary vs. Timeline Semaphores

Vulkan provides two distinct types of semaphores to coordinate cross-queue work:

Binary Semaphores

Binary semaphores have two states: signaled and unsignaled. When submitted to a queue to be signaled, the semaphore transitions from unsignaled to signaled upon completion of the work. The waiting queue consumes this signal and resets the semaphore back to an unsignaled state. Because binary semaphores cannot be inspected for arbitrary progression values and follow a strictly alternating signal-wait pattern, they are primarily used for straightforward handoffs, such as acquiring a swapchain image, rendering to it, and submitting it for presentation.

Timeline Semaphores

Introduced in Vulkan 1.2, timeline semaphores track a monotonically increasing 64-bit integer value rather than a binary toggle. A queue submission can specify that it will signal a timeline semaphore to a specific value (e.g., value 5), while another queue can be instructed to wait until the semaphore reaches or exceeds that target value.

Timeline semaphores provide several critical advantages for multi-queue workflows:

  • One-to-Many Dependencies: Multiple queues can independently wait for the same timeline value.
  • Many-to-One Dependencies: A single queue can wait for the maximum value among several preceding queues.
  • Out-of-Order Submissions: Batches can be submitted to the driver in any order, provided the timeline counter increments correctly at runtime.

Queue Family Ownership Transfers

When an application moves an image or buffer resource between distinct queue families—such as generating data on a transfer queue and reading it on a compute queue—it must perform a Queue Family Ownership Transfer. This process requires two paired pipeline barriers:

  1. A release barrier submitted to the source queue.
  2. An acquire barrier submitted to the destination queue.

While the barriers define the memory dependency and layout transition, they do not guarantee execution ordering between the two queues. A VkSemaphore is mandatory to bridge this gap: the source queue signals the semaphore after executing the release barrier, and the destination queue waits on that semaphore before executing the acquire barrier. This pairing ensures the destination queue never accesses the resource until the source queue has fully completed its release operations.
