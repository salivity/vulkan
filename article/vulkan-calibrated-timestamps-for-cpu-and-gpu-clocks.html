Vulkan Calibrated Timestamps for CPU and GPU Clocks

Calibrated timestamping in the Vulkan API provides a standardized mechanism to simultaneously sample execution clocks across both the host CPU and the graphics device GPU. This article examines the necessity of clock correlation in modern graphics pipelines, the mechanics of the VK_EXT_calibrated_timestamps extension, how clock domains are queried and synchronized, and how developers utilize this data to construct unified profiling timelines and optimize frame pacing.

The Problem of Independent Clock Domains

In modern computing architectures, the CPU and the GPU operate on independent crystal oscillators. Because these hardware timers run on different frequencies, start at different base offsets, and experience independent thermal drift over time, their native time values cannot be directly compared.

Standard Vulkan pipeline profiling relies on vkCmdWriteTimestamp, which writes GPU execution ticks into a query pool. While this provides accurate relative durations for GPU-only workloads, it does not reveal precisely when an event occurred relative to CPU actions, such as user input processing, physics calculations, or command buffer recording. Without a way to synchronize these domains, correlating CPU-side dispatch with GPU-side execution involves significant estimation errors.

What Is Calibrated Timestamping?

Calibrated timestamping solves this clock disparity by allowing the Vulkan driver to read both a CPU clock and a GPU clock near-simultaneously at the hardware layer. This functionality is exposed primarily through the VK_EXT_calibrated_timestamps device extension.

Instead of writing a timestamp inside a recorded command buffer, calibrated timestamps are queried on the host timeline. The driver attempts to sample the requested time domains with minimal latency between reads, returning a snapshot of both clocks along with an estimate of the measurement error.

Supported Time Domains

Vulkan categorizes system and hardware timers into distinct time domains. Before reading timestamps, applications query which domains the underlying driver and operating system support using vkGetPhysicalDeviceCalibrateableTimeDomainsEXT. Common time domains include:

  • VK_TIME_DOMAIN_DEVICE_EXT: The internal hardware clock of the GPU. This is the same clock used by standard Vulkan pipeline timestamp queries (vkCmdWriteTimestamp).
  • VK_TIME_DOMAIN_CLOCK_MONOTONIC_EXT: The POSIX CLOCK_MONOTONIC clock, commonly used on Linux and Android systems.
  • VK_TIME_DOMAIN_CLOCK_MONOTONIC_RAW_EXT: A non-adjustable monotonic clock available on POSIX systems that is not subject to NTP frequency adjustments.
  • VK_TIME_DOMAIN_QUERY_PERFORMANCE_COUNTER_EXT: The high-resolution performance counter (QPC) on Windows platforms.

The Calibration Process

To establish a correlation between the CPU and the GPU, the application calls vkGetCalibratedTimestampsEXT. The function accepts an array of VkCalibratedTimestampInfoEXT structures, where the developer specifies the target domains—typically pairing VK_TIME_DOMAIN_DEVICE_EXT with the operating system’s primary high-resolution CPU counter.

The function returns two critical outputs:

  1. The Timestamps: An array of 64-bit integer values representing the clock states at the moment of sampling.
  2. maxDeviation: A 64-bit integer representing the maximum possible error, expressed in nanoseconds. This value measures the time window it took the driver to read all requested domains. A lower deviation indicates a tighter, more accurate correlation between the sampled values.

Correlating the Clocks in Practice

Once simultaneous samples from both domains are obtained, the application can project GPU timestamps onto the CPU's timeline.

  1. GPU Tick Normalization: GPU ticks are converted to nanoseconds using the physical device’s timestampPeriod (retrieved from VkPhysicalDeviceLimits). The duration in nanoseconds equals the raw GPU ticks multiplied by timestampPeriod.

  2. Offset Calculation: The CPU timestamp is converted to nanoseconds (e.g., dividing QPC counts by the system performance frequency). The difference between the CPU time and the normalized GPU timestamp establishes a base offset:

    \[\text{Offset} = \text{Time}_{\text{CPU}} - (\text{Ticks}_{\text{GPU}} \times \text{timestampPeriod})\]

  3. Mapping Pipeline Queries: When vkCmdWriteTimestamp writes a value during frame rendering, that raw GPU tick value can now be translated to the CPU timeline:

    \[\text{Time}_{\text{Event}} = (\text{Ticks}_{\text{Event}} \times \text{timestampPeriod}) + \text{Offset}\]

Because hardware clocks experience physical drift over time due to temperature changes and clock frequency fluctuations, applications should periodically call vkGetCalibratedTimestampsEXT to recalibrate and calculate a linear regression model that accounts for drift.

Core Applications

Correlated timestamps are vital for advanced engine engineering and profiling:

  • Unified Timeline Profiling: Developer tools (such as GPU profilers and system traces) can display CPU thread traces alongside GPU hardware queue traces on a single, perfectly aligned timeline.
  • Latency Tracking: Developers can precisely calculate frame latency from the exact microsecond an input event occurred on the CPU to the exact microsecond the corresponding frame finished rendering on the GPU.
  • Dynamic Workload Balancing and Pacing: Real-time awareness of how long commands spend waiting between CPU submission and GPU execution allows graphics engines to dynamically tune frame pacing and minimize input lag.
