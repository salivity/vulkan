Vulkan Compute Shader controlBarrier Explained

In Vulkan compute shaders, controlBarrier() synchronizes the execution flow and memory operations of invocations within a specified scope. It acts as both a sequence synchronization point and a memory barrier, ensuring that all participating threads reach the same instruction before any proceed, while simultaneously enforcing memory ordering and visibility for shared or global data across the workgroup or subgroup.

Dual Role of controlBarrier()

In the underlying SPIR-V intermediate representation targeted by Vulkan, controlBarrier() compiles directly to the OpControlBarrier instruction. This instruction executes two distinct synchronization functions at the hardware level:

  1. Execution Synchronization: Pauses invocations so that no thread in the defined execution scope proceeds past the barrier until every other thread in that scope has reached it.
  2. Memory Synchronization: Flushes and invalidates memory caches according to specified memory semantics and scopes, guaranteeing that previous writes are made visible to subsequent reads.

Execution Scope

The execution scope dictates which set of shader invocations must wait for each other. In Vulkan compute pipelines, the execution scope is typically set to one of the following:

  • Workgroup Scope (ScopeWorkgroup): All invocations within the same local compute workgroup must arrive at the barrier before any can continue. This is the standard behavior for coordinating shared resources.
  • Subgroup Scope (ScopeSubgroup): Only invocations within the same hardware SIMD unit (subgroup/wavefront) synchronize. This is lighter on execution latency than a full workgroup sync.

Memory Scope and Semantics

Beyond controlling program execution flow, controlBarrier() ensures memory consistency across invocations. Without explicit memory semantics, modern GPU architectures may reorder reads and writes or leave data in local L1/register caches.

When executing, the barrier takes three memory parameters:

  • Memory Scope: Defines the boundary of invocations that will observe the memory operations (e.g., ScopeWorkgroup, ScopeDevice, or ScopeQueueFamily).
  • Memory Semantics: Specifies the ordering rules, typically using Acquire/Release semantics:
    • Release: Ensures all memory stores made by the calling invocation before the barrier are made visible before the barrier completes.
    • Acquire: Ensures all memory loads made after the barrier observe values made visible prior to or at the barrier.
    • AcquireRelease: Combines both, creating a full bidirectional memory fence.
  • Storage Class Flags: Identifies which types of memory the barrier applies to, such as Workgroup Shared Memory (WorkgroupMemory), Storage Buffers (UniformMemory or StorageBuffer), or Storage Images (ImageMemory).

Practical Execution Example

Consider a parallel reduction in a compute shader where threads write partial sums to workgroup shared memory:

  1. Invocations write their initial values into shared memory arrays.
  2. controlBarrier() is called with a workgroup execution scope, workgroup memory scope, and AcquireRelease semantics.
  3. Fast-executing invocations stall at the barrier instruction.
  4. The GPU enforces that all pending writes to shared memory are committed and visible to all other invocations in the workgroup.
  5. Once the last invocation hits the barrier, all threads are released simultaneously to begin the reduction step, safely reading the initialized values without read-after-write hazards.

Divergence and Deadlocks

When controlBarrier() is executed, all invocations within the target execution scope must be capable of reaching it. If a barrier is placed inside divergent control flow—such as a dynamic if branch that only a subset of the workgroup executes—the shader enters an undefined state, typically resulting in a GPU hang or device loss error (VK_ERROR_DEVICE_LOST).
