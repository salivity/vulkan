Vulkan Peer Memory Access and Zero-Copy Transfers

Peer memory access in Vulkan serves as the foundational mechanism that allows multiple physical GPUs within a unified device group to directly read from and write to one another's local device memory. By utilizing hardware interconnects such as PCIe with Resizable BAR or proprietary links like NVLink, peer memory access bypasses host system RAM entirely. This article explores how Vulkan leverages device groups and peer memory features to eliminate intermediate CPU staging buffers, streamline cross-device synchronization, and achieve true zero-copy data transfers for high-performance multi-GPU compute and graphics workloads.

Understanding Peer Memory Access in Vulkan

In standard multi-GPU configurations, transferring data from GPU A to GPU B traditionally requires a multi-step staging pipeline: the source GPU copies data to host-visible system memory (RAM), the CPU coordinates the transfer, and the destination GPU pulls the data from system RAM into its local VRAM. This process consumes host memory bandwidth, introduces CPU scheduling overhead, and dramatically increases end-to-end transfer latency.

Vulkan eliminates this bottleneck through device groups, introduced in the core API via the VK_KHR_device_group extension. Within a VkDeviceGroup, multiple physical devices are bound to a single logical device (VkDevice). When physical devices reside within the same group, Vulkan can expose peer memory functionality, allowing the memory controller of one GPU to issue read and write requests directly across the interconnect into the physical memory pages of another GPU.

How Peer Memory Enables Zero-Copy Execution

Zero-copy transfers mean that data is transferred or consumed directly between the producer and consumer without redundant duplicate allocations or host-memory intermediaries. Peer memory access facilitates zero-copy workflows in two primary ways:

  1. Direct Peer-to-Peer (P2P) Direct Memory Access (DMA): Using commands like vkCmdCopyBuffer or vkCmdCopyImage, the hardware executes direct DMA operations across the bus. GPU B pulls directly from the memory addresses assigned to GPU A's allocation, executing the transfer at the full bandwidth of the physical interconnect.

  2. Direct Cross-GPU Shader Access (Generic Access): Beyond explicit copies, peer memory access enables shaders running on one GPU to sample directly from images or read from buffers allocated on a peer GPU. When hardware supports generic peer addressing, the concept of a copy operation is eliminated entirely: the workload consumes the remote data inline as if it were local memory, albeit with interconnect-specific latency characteristics.

Querying Peer Memory Capabilities

Not all hardware or interconnect setups support identical peer operations. Vulkan provides explicit control by requiring developers to query peer capabilities via vkGetDeviceGroupPeerMemoryFeatures (or its KHR equivalent). This function returns a bitmask of VkPeerMemoryFeatureFlagBits for a given memory heap between source and destination device indices:

  • VK_PEER_MEMORY_FEATURE_COPY_SRC_BIT: The local memory can be used as a source for direct copies targeting a peer device.
  • VK_PEER_MEMORY_FEATURE_COPY_DST_BIT: The local memory can act as a direct destination for copies originating from a peer device.
  • VK_PEER_MEMORY_FEATURE_GENERIC_SRC_BIT: Shaders on the destination device can directly read this memory using shader resource bindings without an explicit copy.
  • VK_PEER_MEMORY_FEATURE_GENERIC_DST_BIT: Shaders on the destination device can perform direct writes or atomic operations on this memory.

If VK_PEER_MEMORY_FEATURE_GENERIC_SRC_BIT is present, developers achieve the highest tier of zero-copy capability, removing transfer commands from the command buffer entirely.

Memory Allocation and Device Masks

When allocating memory in a device group using vkAllocateMemory, the VkMemoryAllocateFlagsInfo structure allows the developer to specify a deviceMask. This bitmask dictates which physical GPUs allocate backing memory for the resource.

For a zero-copy design, an application typically sets the device mask to allocate memory physically on only the producing GPU. The consuming GPU then maps that identical memory handle into its address space. When binding resources with VkBindBufferMemoryDeviceGroupInfo or VkBindImageMemoryDeviceGroupInfo, the application defines how the resource indices map across the physical hardware, allowing one device's memory footprint to be referenced by pipelines executing on another.

Synchronization Requirements

Because peer transfers bypass the host entirely, the CPU cannot implicitly manage dependencies. Applications must coordinate cross-GPU dependencies explicitly through Vulkan synchronization primitives:

  • Execution and Memory Barriers: Standard pipeline barriers (vkCmdPipelineBarrier) must account for cross-engine access when memory is written by one GPU and subsequently read by another.
  • Semaphores across Device Groups: Vulkan allows timeline and binary semaphores to be signaled by one physical device and waited on by another within the same logical device using VkDeviceGroupSubmitInfo. This guarantees that peer memory is not modified by the producing device while the consuming device's shaders are actively reading it across the bus.

By combining granular capability queries, direct hardware interconnects, and strict synchronization primitives, peer memory access in Vulkan turns multi-GPU scaling from a bandwidth-constrained bottleneck into a low-latency, unified computing architecture.
