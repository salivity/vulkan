Occlusion Query Pooling for Vulkan GPU Culling

This article examines the critical function of occlusion query pooling in Vulkan for building efficient, GPU-driven geometry culling pipelines. In modern rendering architectures, managing query allocations via VkQueryPool allows developers to test object visibility directly on the device, bypass expensive CPU-GPU synchronization bottlenecks, and feed visibility data directly into indirect draw calls. By orchestrating queries in reusable pools and resolving results straight into GPU memory, applications achieve scalable, low-overhead occlusion culling entirely on the GPU.

The Role of VkQueryPool in GPU Pipelines

In Vulkan, occlusion queries are not individually allocated objects; instead, they are managed collectively through VkQueryPool configured with VK_QUERY_TYPE_OCCLUSION. In a CPU-driven pipeline, developers often read back query results to host memory using vkGetQueryPoolResults, which causes pipeline stalls and limits scalability.

In a fully GPU-driven culling architecture, occlusion query pooling serves as an on-chip, contiguous registry of visibility tests. Instead of pinging the CPU, query pools allow the GPU to record, evaluate, and write visibility outcomes directly into device-local storage.

Eliminating CPU Readback via Direct Buffer Copies

The primary advantage of pooling occlusion queries in Vulkan is the ability to write results directly to a VkBuffer using vkCmdCopyQueryPoolResults.

  1. Batch Testing: Bounding geometry (such as coarse bounding boxes or simplified bounding meshes) is rendered to an existing depth buffer using commands bracketed by vkCmdBeginQuery and vkCmdEndQuery. Each object maps to an index within the allocated VkQueryPool.
  2. Device-Local Copying: The results are copied directly to a GPU-accessible storage buffer using vkCmdCopyQueryPoolResults with flags like VK_QUERY_RESULT_WAIT_BIT or VK_QUERY_RESULT_64_BIT.
  3. Compute Shader Processing: A compute shader reads the visibility buffer as a storage buffer (SSBO). If the pixel count for an object exceeds zero, the geometry is marked visible. The compute shader then dynamically writes the visible draw commands into a VkDrawIndexedIndirectCommand buffer.

This workflow ensures that visibility decisions are made entirely on the GPU timeline without CPU intervention.

Amortizing Allocation and State Overhead

Creating and destroying individual query resources introduces substantial driver overhead. VkQueryPool amortizes this by pre-allocating an array of query slots.

Before execution, chunks of the pool are cleared on the command buffer timeline using vkCmdResetQueryPool. Because query resets and writes occur inside command buffers, synchronization is handled purely through Vulkan pipeline barriers (VkMemoryBarrier and VkBufferMemoryBarrier), preventing pipeline bubbles.

Mitigating Latency with Temporal Pooling

GPU occlusion queries suffer from inherent pipeline latency: results are rarely available in the immediate draw phase of the same frame without causing pipeline bubbles. Query pooling addresses this through multi-buffered, frame-delayed tracking.

Developers typically divide the query pool across multiple frames in flight or maintain dual-pool structures:

  • Frame \(N-1\) Results: Used to generate indirect draws for the current frame, exploiting the temporal coherence of moving cameras.
  • Frame \(N\) Generation: New bounding proxies are rasterized against the current depth buffer to populate the next pool slot.

Native Integration with Conditional Rendering

Occlusion query pools can also interact directly with VK_EXT_conditional_rendering. When query results are copied into a buffer via vkCmdCopyQueryPoolResults, that buffer can serve directly as a conditional rendering token via vkCmdBeginConditionalRenderingEXT. This eliminates the need for an intermediate compute pass for simpler geometry, allowing hardware to discard unselected indirect draw calls automatically.
