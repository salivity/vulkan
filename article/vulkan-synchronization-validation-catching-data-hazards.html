Vulkan Synchronization Validation: Catching Data Hazards

The Vulkan synchronization validation layer tracks resource states and simulated execution timelines to identify missing pipeline barriers, improper access flags, and data hazards like Read-After-Write (RAW), Write-After-Read (WAR), and Write-After-Write (WAW). Because Vulkan requires developers to manage memory visibility and execution dependencies explicitly, manual synchronization is prone to subtle bugs. The synchronization validation layer automates bug detection by intercepting API commands, tracking resource usage per subresource, and checking whether proper execution and memory dependencies exist before operations are scheduled.

Shadow State and Resource Access Tracking

To catch missing barriers, the synchronization validation layer maintains an internal shadow state of every active resource, including buffers and individual image subresources (down to specific mip levels and array layers). Whenever a command that accesses a resource is recorded—such as vkCmdDraw, vkCmdDispatch, or vkCmdCopyBuffer—the layer logs an access record. This record stores:

  • The specific resource and subresource range.
  • The pipeline stage executing the command (e.g., VK_PIPELINE_STAGE_FRAGMENT_SHADER_BIT).
  • The access type (e.g., VK_ACCESS_SHADER_READ_BIT or VK_ACCESS_SHADER_WRITE_BIT).
  • The sequence order and queue context in which the command occurs.

Detecting Data Hazards

Whenever a new read or write operation is encountered, the validation layer compares the incoming access against the previous recorded access for that exact memory region. A data hazard is flagged if:

  1. Read-After-Write (RAW): A read command follows a write command without an execution barrier ensuring the write has completed and an access barrier ensuring memory visibility to the reading stage.
  2. Write-After-Read (WAR): A write command is recorded on memory that is currently being read by an earlier pipeline stage that has not finished execution.
  3. Write-After-Write (WAW): Two successive write commands target the same memory location concurrently or out of order without an explicit barrier ordering them.

If a hazard is detected, the layer generates an error detailing the current command, the previous conflicting command, the involved stages, and the exact missing access masks.

Modeling Pipeline Barriers and Render Passes

The layer continuously evaluates synchronization commands, such as vkCmdPipelineBarrier, vkCmdPipelineBarrier2, vkCmdWaitEvents, and subpass dependencies in VkRenderPass. When a barrier is recorded, the layer updates its tracking state machine:

  • Execution Dependencies: It verifies that srcStageMask covers the pipeline stages of prior operations and dstStageMask covers the stages of subsequent operations.
  • Memory Dependencies: It checks whether srcAccessMask flushes pending writes to memory and dstAccessMask invalidates caches so that subsequent reads receive updated data.
  • Layout Transitions: For images, it verifies that transitions between VkImageLayout states do not occur while writes are pending or reads are still in-flight.

If a barrier defines insufficient stages or access masks to resolve prior writes, the layer leaves the hazard state unresolved and reports an error as soon as the dependent access occurs.

Cross-Queue and Multi-Command Buffer Tracking

Hazards can span multiple command buffers and queue submissions. The validation layer tracks queue submissions (vkQueueSubmit) and evaluates synchronization primitives such as timeline semaphores, binary semaphores, and fences. It ensures that queue family ownership transfers (VK_SHARING_MODE_EXCLUSIVE) are correctly initiated on the release queue and matched on the acquire queue before the destination queue accesses the resource. By evaluating the collective graph of command buffers, semaphores, and barriers, the layer identifies race conditions that standard Vulkan validation checks cannot detect.
