How Vulkan Multiview Reduces CPU Draw Calls

Vulkan’s multiview feature drastically reduces CPU overhead by enabling a single draw command to broadcast across multiple framebuffer layers simultaneously. Typically used in stereoscopic virtual reality rendering, cascaded shadow maps, and environment cubemaps, this capability removes the need for the CPU to record and submit separate draw calls for each viewpoint. By offloading primitive replication and view-dependent indexing directly to the GPU hardware, applications achieve significant performance gains on the host processor.

The Traditional Multi-View Bottleneck

In conventional rendering workflows, displaying a scene from multiple perspectives requires the CPU to iterate through the entire render loop for each view. For instance, in stereoscopic VR, the CPU must traverse the scene graph, evaluate culling, bind pipeline states, and issue vkCmdDraw calls once for the left eye and again for the right eye.

This approach doubles the CPU workload, saturating command buffers with redundant state transitions, driver validation checks, and dispatch submissions. When rendering to six cube map faces or multiple shadow cascades, this overhead scales linearly, often creating a critical CPU bottleneck that starves the GPU.

The Multiview Mechanism

Vulkan solves this redundancy through the multiview extension (VK_KHR_multiview, which is core in Vulkan 1.1). Instead of repeating commands, the developer configures a render pass with a bitmask—termed the viewMask—via VkRenderPassMultiviewCreateInfo. Each bit in this mask corresponds to a specific layer in an array-based framebuffer attachment.

When the CPU submits a single draw call within a multiview render pass:

  1. Single Submission: The host CPU records and issues vkCmdDraw or vkCmdDrawIndexed only once.
  2. Hardware Broadcasting: The GPU’s primitive distribution hardware intercepts the draw command and automatically broadcasts the incoming geometry across all active views designated by the subpass view mask.
  3. Layer Targeting: The rasterizer routes the generated fragments directly to their respective 2D texture array layers or render target slices without requiring separate framebuffer bindings.

Shader Execution and gl_ViewIndex

To handle view-specific differences—such as unique camera positions or projection matrices—Vulkan exposes the built-in shader variable gl_ViewIndex (or ViewIndex in SPIR-V).

Using gl_ViewIndex, a single vertex shader dynamically indexes into an array of uniform data (such as view-projection matrices) directly on the GPU:

layout(binding = 0) uniform CameraData {
    mat4 viewProjection[2];
} camera;

void main() {
    gl_Position = camera.viewProjection[gl_ViewIndex] * vec4(inPosition, 1.0);
}

Because view differentiation occurs internally on the GPU, the CPU does not need to rebind descriptors, update push constants, or switch shader pipelines between views.

Quantifiable Reduction in CPU Submission Rates

By shifting view replication to the GPU rasterization pipeline, multiview achieves a near-linear reduction in CPU draw call submissions:

  • Stereoscopic VR: Draw call submissions, command recording operations, and API overhead are halved (a 2:1 reduction).
  • Cascaded Shadow Maps: For three or four cascades rendered via multiview, draw call counts decrease by 66% to 75%.
  • Cubemaps: Updating six faces concurrently achieves up to a 6:1 reduction in draw call volume.

Beyond simply cutting the raw number of vkCmdDraw calls, multiview minimizes pipeline state switches, pipeline barrier synchronization, and secondary command buffer overhead. This frees substantial CPU frame time for physics, game logic, and spatial tracking while keeping the GPU fully fed with continuous, streamlined workloads.
