Vulkan Queue Ownership Transfer Barriers Explained

In Vulkan, transferring resource ownership between distinct queue families requires a two-step handshake: a release operation submitted to the source queue and a matching acquire operation submitted to the destination queue. This article explains why the Vulkan specification mandates matching memory barriers across both queues, detailing how independent hardware schedulers, disjoint cache hierarchies, and memory availability and visibility operations necessitate this dual-barrier approach for resources utilizing exclusive sharing mode.

The Purpose of Queue Family Ownership Transfers

When a VkBuffer or VkImage is created with VK_SHARING_MODE_EXCLUSIVE, it can only be accessed by one queue family at a time. This constraint allows Vulkan drivers to optimize resource layouts and cache access for the specific hardware engine executing the work. To safely pass access rights from a source queue family to a destination queue family, an explicit Queue Family Ownership Transfer (QFOT) must occur. This transfer requires two identical resource transition definitions: a release operation on the source queue and an acquire operation on the destination queue.

Hardware Disjointness and Independent Schedulers

Vulkan queue families often map to physically distinct hardware execution units, such as a dedicated compute engine, a graphics pipe, or a DMA transfer engine. These independent engines:

  • Operate under separate hardware scheduling mechanisms with no direct visibility into each other's execution streams.
  • Possess separate local cache structures (such as independent L1 caches or texture caches) that are not automatically kept coherent with one another.

Because a command buffer is recorded and submitted to a specific queue family, a barrier recorded in that buffer can only dictate execution order and cache states on that specific hardware engine. A single barrier cannot simultaneously govern the cache flushing of one engine and the cache invalidation of another.

The Release Barrier (Source Queue)

The release barrier is submitted to a queue in the source queue family. Its primary responsibilities are:

  1. Execution Synchronization: It ensures all preceding memory reads and writes directed at the resource on the source queue complete before the release is executed.
  2. Memory Availability: It performs a cache flush, pushing modified data out of the source engine’s private caches (e.g., L1 compute caches) and making it available to a common memory domain, such as shared L2 cache or system RAM.
  3. Relinquishing Ownership: Setting the barrier's srcQueueFamilyIndex to the source and dstQueueFamilyIndex to the destination signals that the source queue family will no longer access this resource without a new transfer.

The Acquire Barrier (Destination Queue)

The acquire barrier is submitted to a queue in the destination queue family. Its responsibilities balance those of the release:

  1. Memory Visibility: It performs a cache invalidation on the destination engine's local caches, ensuring that any stale cached lines for that memory address are cleared so that the newly available memory from the release operation becomes visible.
  2. Execution Synchronization: It stalls subsequent operations on the destination queue until the acquire operation finishes, preventing instructions from reading or writing data before it has been made fully coherent.
  3. Accepting Ownership: It specifies matching srcQueueFamilyIndex and dstQueueFamilyIndex parameters, legally completing the transfer in the API state machine.

Why the Handshake Must Match

The Vulkan specification requires the parameters of both the release and acquire barriers (the resource handle, subresource range, and queue family indices) to match exactly. This matching pair acts as a contract:

  • Separation of Execution and Memory: A cross-queue execution dependency is established using a synchronization primitive like a VkSemaphore. However, the semaphore only guarantees when the destination queue starts relative to the source queue; it does not dictate how memory caches are synchronized.
  • Layout Transitions: For images, if a layout transition is specified (e.g., from VK_IMAGE_LAYOUT_TRANSFER_DST_OPTIMAL to VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL), the transition happens only once across the release/acquire pair. Vulkan mandates that the transition can occur in either the release barrier or the acquire barrier, or be identical across both, to avoid conflicting layout transformations on hardware that uses specialized data compression.

Submitting only one of the two barriers results in undefined behavior. Omitting the release barrier leaves writes lingering in the source engine's caches, while omitting the acquire barrier causes the destination engine to read stale data or write to uninitialized memory domains. Both barriers are required to complete the memory lifecycle across disparate hardware engines.
