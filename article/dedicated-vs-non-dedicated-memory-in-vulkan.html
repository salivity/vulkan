Dedicated vs Non-Dedicated Memory in Vulkan

In the Vulkan graphics and compute API, memory management is explicitly controlled by the developer, requiring a deliberate choice between suballocating resources from pooled memory blocks or assigning them dedicated memory allocations. This article explains the technical differences between dedicated and non-dedicated memory allocations in Vulkan, highlighting how they affect resource limits, driver-level optimizations, cross-API interop, and overall rendering performance.

Understanding Non-Dedicated Allocations

A standard, or non-dedicated, memory allocation follows the suballocation model. In this pattern, the application allocates a large chunk of VkDeviceMemory via vkAllocateMemory (often 64 MB to 256 MB) and subdivides it across multiple VkBuffer and VkImage resources. Each resource is bound to a specific byte offset within that single memory object using vkBindBufferMemory or vkBindImageMemory.

This approach minimizes calls to the driver's memory allocator and prevents hitting hardware allocation limits.

Understanding Dedicated Allocations

A dedicated allocation associates exactly one VkBuffer or VkImage with its own exclusive VkDeviceMemory object, spanning the entire allocation starting at offset 0. This is explicitly requested using the VkMemoryDedicatedAllocateInfo structure chained to VkMemoryAllocateInfo via the pNext pointer (introduced as core in Vulkan 1.1 or via the VK_KHR_dedicated_allocation extension).

Dedicated allocations inform the driver that the memory will not be shared with other resources, allowing the driver to tailor memory properties specifically for that single resource.

Key Differences

1. Driver Optimizations and Performance

  • Non-Dedicated: Drivers must treat pooled memory as generic blocks. They cannot easily adjust low-level page table configurations or memory modes for a specific resource because other unrelated resources might share the same physical pages.
  • Dedicated: When a resource has dedicated memory, the GPU driver and hardware memory controller can apply specialized optimizations. These can include setting up specific compression modes, optimizing memory compression metadata (such as DCC for render targets on AMD GPUs), or placing the resource in a physical configuration that maximizes bandwidth for high-throughput render targets.

2. Allocation Count Limits (maxMemoryAllocationCount)

  • Non-Dedicated: Bypasses hardware limits by packing thousands of resources into a few dozen VkDeviceMemory handles.
  • Dedicated: Consumes one allocation slot per resource. Vulkan hardware exposes a hard limit via VkPhysicalDeviceLimits::maxMemoryAllocationCount, which can be as low as 4,096 on some platforms. Overusing dedicated allocations can quickly exhaust these available handles, leading to allocation failures.

3. Inter-API and Cross-Process Sharing

  • Non-Dedicated: Suballocated resources cannot easily be exported or shared because external APIs (such as CUDA, Direct3D 12, or OpenCL) require access to entire memory pages aligned to OS-level boundaries.
  • Dedicated: Dedicated allocations are typically mandatory when exporting or importing resources via VK_KHR_external_memory. Sharing a swapchain surface, video decoding buffer, or compute buffer with an external API requires dedicated backing to ensure OS-level handles point solely to that resource.

4. Aliasing and Offsets

  • Non-Dedicated: Requires proper handling of byte alignment (VkMemoryRequirements::alignment). Developers can alias multiple transient resources into the same memory offset if their lifetimes do not overlap, reducing overall VRAM footprint.
  • Dedicated: Requires an allocation offset of zero. Resource aliasing within the allocation is not possible because the memory is bound 1:1 to a single resource.

When to Use Each Allocation Type

The Vulkan specification provides the vkGetBufferMemoryRequirements2 and vkGetImageMemoryRequirements2 functions, which populate a VkMemoryDedicatedRequirements structure indicating whether a dedicated allocation is required or recommended.

  • Use Dedicated Allocation when:
    • VkMemoryDedicatedRequirements::requiresDedicatedAllocation is VK_TRUE.
    • VkMemoryDedicatedRequirements::prefersDedicatedAllocation is VK_TRUE, particularly for large, persistent render targets, depth/stencil buffers, and high-resolution textures that benefit from specialized compression.
    • You are exporting memory handles to other APIs or processes.
  • Use Non-Dedicated Allocation for:
    • Small to medium buffers (vertex, index, uniform, and staging buffers).
    • Static textures, UI elements, and sprite sheets.
    • Situations where resource count is high, ensuring the application remains well below maxMemoryAllocationCount.
