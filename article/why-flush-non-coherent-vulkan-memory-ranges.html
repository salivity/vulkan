Why Flush Non-Coherent Vulkan Memory Ranges

In Vulkan, managing device memory requires explicit control over synchronization between the host CPU and the graphics device. When working with memory types that lack the VK_MEMORY_PROPERTY_HOST_COHERENT_BIT property, developers must explicitly call vkFlushMappedMemoryRanges after writing data from the host. This article explains the architectural reasons behind this requirement, focusing on CPU caching behavior, hardware-level memory coherency, and performance implications.

The Role of CPU Caches

When a CPU thread writes to a mapped Vulkan memory pointer via vkMapMemory, the write operation does not immediately travel to physical system RAM or VRAM. Instead, modern CPUs write to high-speed local caches (L1, L2, and L3) to minimize latency. These cached modifications remain "dirty" within the CPU's local cache hierarchy until the cache lines are evicted or explicitly pushed to downstream memory.

Host-Coherent vs. Non-Coherent Memory

Vulkan categorizes host-accessible memory using specific property flags:

  • Host-Coherent Memory (VK_MEMORY_PROPERTY_HOST_COHERENT_BIT): The hardware automatically guarantees that writes made by the host are made visible to the device without manual intervention. This is typically achieved via hardware cache snooping or write-through cache policies.
  • Non-Coherent Memory: The hardware does not automatically synchronize CPU caches with the device. The memory subsystem relies entirely on the application to signal when cached data must be transferred.

Why Flushing Is Required

Because non-coherent memory lacks automatic synchronization mechanisms, the GPU has no way of knowing that data in the CPU cache has changed. If the GPU attempts to read from a mapped range before the cache is written back, it will read stale or uninitialized data directly from RAM.

Calling vkFlushMappedMemoryRanges instructs the CPU to clean the specified dirty cache lines, forcing the written bytes out of the host caches and into a memory domain accessible by the GPU. Only after this flush operation completes—and after appropriate pipeline barriers or semaphores synchronize the transfer—can the GPU reliably access the modified payload.

Architectural Flexibility and Performance

Vulkan delegates cache flushing to the developer to maximize performance across diverse hardware architectures:

  1. Eliminating Hardware Overhead: On architectures without hardware-level cache snooping (common in mobile System-on-Chips and certain discrete GPU configurations), enforcing automatic coherency requires expensive write-through caches or bus monitoring, which consumes significant memory bandwidth and power.
  2. Batching Memory Operations: Explicit flushing allows developers to perform multiple writes across large buffers and flush them in a single, batched operation. This minimizes cache line evictions and reduces memory bus traffic compared to continuous implicit synchronization.

In summary, vkFlushMappedMemoryRanges is essential for non-coherent memory because it bridges the gap between host CPU caches and device-visible storage, ensuring data integrity without imposing hardware-enforced performance penalties.
