Vulkan Conditional Rendering Without CPU Readbacks

This article explains how graphics engines use the VK_EXT_conditional_rendering extension in Vulkan to bypass latency-inducing CPU readbacks of occlusion queries. Traditional occlusion culling requires copying visibility results back to the host, introducing multi-frame stalls and pipeline bubbles. By configuring and binding GPU-side conditional rendering buffers directly into the command stream, engines allow the GPU to make autonomous draw-call decisions entirely on-chip.

The Problem with Traditional CPU Readbacks

In a standard occlusion query workflow, the engine renders simplified proxy geometry (like bounding boxes) inside vkCmdBeginQuery and vkCmdEndQuery. To decide whether the full-detail mesh should be drawn, the CPU must read the query result using vkGetQueryPoolResults.

Because the GPU operates asynchronously, reading this data back to the host creates a dilemma: either the CPU blocks until the rendering finishes (causing massive pipeline stalls), or the engine defers the result by one or two frames (introducing visible pop-in artifacts).

The Architecture of Vulkan Conditional Rendering

The VK_EXT_conditional_rendering extension resolves this latency by keeping the decision pipeline strictly within GPU memory. Instead of routing visibility results through host memory, the engine writes query outputs directly to a VkBuffer. The GPU's command processor then reads this buffer directly to evaluate whether subsequent rendering commands should be executed or discarded.

Implementation Workflow

1. Enabling the Extension

During device creation, the engine must enable the VK_EXT_conditional_rendering extension and activate the conditionalRendering feature inside the VkPhysicalDeviceConditionalRenderingFeaturesEXT structure.

2. Writing Visibility Results to a Buffer

Engines typically obtain visibility status via occlusion queries or compute-based culling passes:

  • Occlusion Query Path: The engine dispatches bounding-box occlusion queries to a query pool. Instead of calling vkGetQueryPoolResults, it invokes vkCmdCopyQueryPoolResults inside the command buffer. This command transfers the pass/fail results directly into a designated VkBuffer with VK_BUFFER_USAGE_CONDITIONAL_RENDERING_BIT_EXT.
  • Compute Culling Path: A GPU compute shader performs hierarchical-Z (Hi-Z) or frustum testing and writes a 1 (visible) or 0 (occluded) directly into the conditional buffer.

3. Configuring the Conditional Rendering Buffer

Before executing the high-detail draw calls, the engine populates a VkConditionalRenderingBeginInfoEXT structure:

  • buffer: The VkBuffer handle holding the visibility flags.
  • offset: The byte offset pointing to the specific 32-bit integer allocated for this specific draw call or object.
  • flags: Determines evaluation rules. By default, a non-zero value in the buffer renders the geometry, while zero discards it. If inverted logic is needed (e.g., zero indicates pass), VK_CONDITIONAL_RENDERING_INVERTED_BIT_EXT is set.

4. Encapsulating Commands

The engine wraps the rendering commands between conditional scope markers:

VkConditionalRenderingBeginInfoEXT condInfo = {};
condInfo.sType = VK_STRUCTURE_TYPE_CONDITIONAL_RENDERING_BEGIN_INFO_EXT;
condInfo.buffer = visibilityBuffer;
condInfo.offset = objectOffset;
condInfo.flags = 0; // Non-zero = execute

vkCmdBeginConditionalRenderingEXT(commandBuffer, &condInfo);

// These commands are evaluated on the GPU timeline
vkCmdBindPipeline(commandBuffer, VK_PIPELINE_BIND_POINT_GRAPHICS, meshPipeline);
vkCmdBindVertexBuffers(commandBuffer, 0, 1, &vertexBuffer, &offset);
vkCmdDrawIndexed(commandBuffer, indexCount, 1, 0, 0, 0);

vkCmdEndConditionalRenderingEXT(commandBuffer);

Execution at the Hardware Level

When vkCmdBeginConditionalRenderingEXT is active, the GPU’s command processor fetches the integer stored at the designated buffer memory address. If the condition evaluates to false, the hardware skips the wrapped draw calls, state changes, or dispatches directly in the frontend command streamer.

This approach completely eliminates CPU synchronization points, eliminates query result latency, and ensures high GPU utilization without CPU-side visibility tracking.
