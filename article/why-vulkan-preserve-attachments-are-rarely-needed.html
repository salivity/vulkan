Why Vulkan Preserve Attachments Are Rarely Needed

In the Vulkan API, preserve attachments allow a render pass to declare that an attachment's contents must remain intact across intermediate subpasses that do not explicitly read from or write to it. While vital for bandwidth optimization on mobile tile-based architectures, preserve attachments are rarely needed on modern desktop graphics cards. This article explains the architectural differences between mobile and desktop GPUs, why immediate-mode desktop hardware naturally retains framebuffer data, and how modern Vulkan practices make preserve attachments largely obsolete for desktop-focused development.

What Preserve Attachments Do

When configuring a VkSubpassDescription, developers can pass an array of indices via pPreserveAttachments. This array explicitly informs the driver that although the current subpass does not bind or touch the specified attachment, the data within that attachment must not be discarded because a subsequent subpass will need it.

Desktop Immediate-Mode vs. Mobile Tile-Based Rendering

The requirement for preserve attachments stems directly from Tile-Based Deferred Rendering (TBDR) architectures, which dominate mobile hardware such as ARM Mali, Qualcomm Adreno, and Imagination PowerVR GPUs.

  • TBDR (Mobile): Render targets are split into small, on-chip tiles. Color and depth data reside in fast, transient tile memory (SRAM). If Subpass 1 writes to Attachment A, Subpass 2 ignores it, and Subpass 3 requires Attachment A, the driver needs to know whether it must preserve that tile's memory across Subpass 2. Without declaring Attachment A as a preserve attachment in Subpass 2, the hardware might overwrite the tile memory or evict it to high-latency system RAM.
  • Immediate-Mode Rendering (Desktop): Modern desktop GPUs from AMD, NVIDIA, and Intel predominantly use Immediate-Mode Rendering (IMR) or hybrid architectures with unified, large cache hierarchies (L2/L3). Framebuffer attachments live in dedicated VRAM or coherent cache lines rather than transient tile scratchpads that are aggressively wiped between subpass transitions.

Why Desktop Hardware Ignores the Need

On desktop GPUs, subpasses are typically lowered by the driver into standard pipeline barriers, cache flushes, and sequential draw calls. Because the framebuffer is backed by persistent VRAM:

  1. Persistent Memory Allocation: Attachments allocated in device-local memory do not magically vanish when an intermediate draw call or subpass ignores them. The memory addresses remain allocated and untouched until overwritten or explicitly cleared.
  2. Driver Optimization: Desktop Vulkan drivers translate multi-subpass render passes into conventional execution passes. If a subpass does not reference an attachment, the desktop GPU simply does not issue read or write instructions against that attachment's memory address. The data naturally remains preserved.
  3. No Forced Eviction: Desktop GPUs do not require developer-directed hints to keep non-active attachments from being cleared in the middle of a render pass because there is no localized, per-tile on-chip buffer to swap out.

The Rise of Dynamic Rendering

The introduction of Vulkan 1.3 and the VK_KHR_dynamic_rendering extension further reduces the relevance of preserve attachments on desktop systems. Dynamic rendering bypasses the traditional VkRenderPass and VkFramebuffer abstraction altogether, eliminating subpasses and the associated preserve attachment declarations in favor of explicit pipeline barriers and simplified rendering loops.

Because modern desktop hardware inherently preserves untouched VRAM allocations across rendering operations, manual preservation declarations yield no performance benefit or safety guarantee, rendering them practically irrelevant for desktop graphics pipelines.
