Queue Family Ownership Transfers in Vulkan

In Vulkan, transferring resource ownership between disparate queue families requires a coordinated two-step synchronization mechanism known as release and acquire barriers. When resources are created with exclusive sharing mode to maximize hardware efficiency, they can only be accessed by one queue family at a time. Shifting access—such as moving an image from an asynchronous compute queue to a main graphics queue—requires executing a release barrier on the originating queue family to make writes available, followed by an acquire barrier on the target queue family to make those writes visible.

Exclusive Sharing Mode and Queue Families

Vulkan allows resources (buffers and images) to be created using either VK_SHARING_MODE_CONCURRENT or VK_SHARING_MODE_EXCLUSIVE. While concurrent mode permits simultaneous access from multiple queue families without ownership transfers, it can introduce driver overhead and disable hardware-specific memory compression. Exclusive mode delivers optimal memory bandwidth and performance, but enforces strict ownership: a resource belongs to exactly one queue family at any given point in execution. Accessing an exclusive resource from another queue family without an explicit ownership transfer produces undefined behavior.

The Release Barrier (Source Queue)

The ownership transfer begins on the queue family currently holding ownership (the source queue). A pipeline barrier (vkCmdPipelineBarrier or vkCmdPipelineBarrier2) is recorded into a command buffer submitted to this source queue. This operation is defined as the "release" barrier.

Key parameters for the release barrier include:

  • Queue Family Indices: srcQueueFamilyIndex must be the index of the source queue family, and dstQueueFamilyIndex must be the index of the target queue family.
  • Access Masks: srcAccessMask (or srcStageMask/srcAccessMask in synchronization2) must specify the memory operations performed on the source queue that need to be completed and made available. The dstAccessMask is ignored in a release operation and is conventionally set to 0.
  • Resource Range: The specific buffer memory barrier or image memory barrier describing the subresources being transferred.

The release barrier ensures that all memory writes performed by the source queue are committed and made available for handoff.

The Acquire Barrier (Destination Queue)

The transfer completes on the queue family receiving ownership (the destination queue). A matching pipeline barrier is recorded and submitted to this destination queue, functioning as the "acquire" barrier.

Key parameters for the acquire barrier include:

  • Queue Family Indices: Must exactly match the values specified in the release barrier (srcQueueFamilyIndex remains the source index, and dstQueueFamilyIndex remains the destination index).
  • Access Masks: The srcAccessMask is ignored in an acquire operation and is set to 0. The dstAccessMask must specify the access types the destination queue will use (for example, VK_ACCESS_SHADER_READ_BIT), ensuring the incoming memory is made visible to those specific stages.

The acquire barrier takes the memory previously made available by the release operation and makes it visible to the destination queue's pipeline stages.

Cross-Queue Synchronization

A pipeline barrier only synchronizes execution within the queue to which it is submitted. It cannot enforce execution order across two independent physical queues. Therefore, an external synchronization primitive—almost universally a VkSemaphore—must bridge the gap between the source queue's submission and the destination queue's submission.

  1. The source queue command buffer executes operations, ending with the release barrier.
  2. The source queue's vkQueueSubmit signals a semaphore upon completion.
  3. The destination queue's vkQueueSubmit waits on that semaphore before executing the command buffer containing the acquire barrier.

This ensures the acquire barrier does not execute before the release barrier has completely finished making the memory available.

Image Layout Transitions

When transferring images, layout transitions can be combined with the ownership transfer. The oldLayout and newLayout fields must be identical in both the release barrier and the acquire barrier. The actual transition occurs either during the release or during the acquire phase, managed by the driver, ensuring the image arrives at the destination queue in the desired format without corruption.
