Why Vulkan GPU Timestamps Require Frequency Conversion

In the Vulkan graphics API, GPU timestamps generated by query pools cannot be read directly as CPU nanoseconds because they measure hardware-specific clock cycles rather than standardized units of time. The GPU operates on an independent hardware timer whose frequency is determined by the device vendor and hardware architecture. To convert these raw integer tick counts into standard nanoseconds or align them with CPU-side profiling timelines, developers must multiply the timestamp differences by the device’s specific timestamp period property or use calibration extensions.

Independent Hardware Clock Domains

The central processor (CPU) and the graphics processor (GPU) run on physically isolated oscillators. While modern CPUs provide access to high-resolution system timers that operating systems map to standard nanosecond units (such as POSIX monotonic clocks or Windows performance counters), GPUs implement internal counter registers tied to their own clock domains.

These internal GPU counters increment at a rate dictated by the chip's internal timer frequency. Because different hardware vendors—and even different architectures within the same vendor—utilize disparate clock designs, a single tick on one GPU does not represent the same physical duration as a tick on another.

The Vulkan Timestamp Period

Vulkan exposes raw, 64-bit integer values when querying timestamps via vkGetQueryPoolResults or vkCmdCopyQueryPoolResults. The API specification does not mandate that these ticks represent nanoseconds. Instead, it provides the physical scale through the device limits structure.

Within VkPhysicalDeviceLimits, the field timestampPeriod specifies the number of nanoseconds it takes for the GPU timestamp counter to increment by a single value (1.0 tick). The calculation to determine the elapsed real-time duration between two GPU timestamps is:

\[\text{Elapsed Time (ns)} = (\text{Timestamp}_{\text{End}} - \text{Timestamp}_{\text{Start}}) \times \text{timestampPeriod}\]

If timestampPeriod is 1.0, one tick equals one nanosecond. However, many GPU architectures report values such as 52.083, 10.0, or other fractional figures depending on their clock frequency (for instance, a 19.2 MHz or 27 MHz reference clock). Interpreting the raw counter directly as nanoseconds without applying this multiplier results in significantly distorted timing data.

Disparate Epochs and Synchronization

Beyond the difference in frequency, GPU timestamps and CPU timers operate on entirely different base timelines (epochs).

  • CPU timers are typically referenced against system boot time or a standardized arbitrary epoch.
  • GPU timers start counting based on GPU initialization, power-on states, or context creation.

Because the starting point (time zero) differs between the processors, a raw GPU timestamp cannot be compared against a CPU timestamp such as std::chrono::high_resolution_clock::now() simply by scaling the frequency. Doing so requires correlating the two timelines simultaneously. Vulkan addresses this cross-device correlation through the VK_EXT_calibrated_timestamps extension, which samples CPU and GPU clock domains concurrently to establish a shared reference point. Without this calibration and subsequent frequency adjustment, correlating GPU work with CPU frame dispatch remains impossible.
