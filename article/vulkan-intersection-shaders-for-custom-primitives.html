Vulkan Intersection Shaders for Custom Primitives

Vulkan's hardware-accelerated ray tracing framework natively supports triangles, but developers can render custom non-triangular geometries, such as mathematically perfect spheres, using intersection shaders. By encapsulating these non-triangular shapes inside axis-aligned bounding boxes (AABBs) within the acceleration structure, Vulkan delegates the exact ray-geometry intersection testing to a user-defined intersection shader. This article explains how the Vulkan ray tracing pipeline integrates these shaders, processes bounding volumes, executes analytical intersection math, and reports hit results back to the pipeline.

The Procedural Geometry Pipeline

Standard hardware ray tracing utilizes fixed-function ray-triangle intersection units built into modern GPUs. To accommodate arbitrary mathematical shapes—such as spheres, splines, or implicit surfaces—Vulkan bypasses these fixed-function units by defining geometric geometry as procedural.

Instead of passing vertex and index buffers to a Bottom-Level Acceleration Structure (BLAS), developers provide an array of Axis-Aligned Bounding Boxes using the VkAccelerationStructureGeometryAabbsDataKHR structure. The Vulkan acceleration structure builder computes the hierarchy strictly around these bounding volumes.

Triggering the Intersection Shader

When a ray traverses the Top-Level and Bottom-Level Acceleration Structures, the traversal hardware evaluates ray intersections against the bounding boxes. If a ray intersects an AABB containing custom geometry, the traversal hardware pauses and invokes the associated intersection shader (VK_SHADER_STAGE_INTERSECTION_BIT_KHR).

Inside the intersection shader, the developer has access to the current ray properties in object space via built-in GLSL or HLSL variables:

  • gl_ObjectRayOriginEXT: The origin of the ray transformed into the object's local space.
  • gl_ObjectRayDirectionEXT: The direction vector of the ray.
  • gl_RayTminEXT and gl_RayTmaxEXT: The valid interval along the ray where a hit can occur.

Calculating the Custom Intersection

The intersection shader implements the specific mathematical test for the primitive. For a sphere centered at the origin with radius \(r\), the ray equation \(\mathbf{P}(t) = \mathbf{O} + t\mathbf{D}\) is substituted into the sphere equation \(\|\mathbf{P}\|^2 - r^2 = 0\).

This produces a quadratic equation: \[at^2 + bt + c = 0\]

Where:

  • \(a = \mathbf{D} \cdot \mathbf{D}\)
  • \(b = 2(\mathbf{O} \cdot \mathbf{D})\)
  • \(c = \mathbf{O} \cdot \mathbf{O} - r^2\)

The shader calculates the discriminant \(\Delta = b^2 - 4ac\). If \(\Delta < 0\), the ray misses the sphere entirely, and the shader terminates without reporting a hit. If \(\Delta \ge 0\), the shader solves for the nearest positive parameter \(t\) that falls within the valid range \([t_{\min}, t_{\max}]\).

Reporting the Hit to the Pipeline

Once a valid intersection distance \(t\) is determined, the shader communicates this result back to the traversal engine using the built-in function reportIntersectionEXT().

hitAttributeEXT vec3 hitNormal;

void main()
{
    float t = solveRaySphereIntersection();
    
    if (t >= gl_RayTminEXT && t <= gl_RayTmaxEXT)
    {
        // Calculate the surface normal at the hit point
        vec3 hitPoint = gl_ObjectRayOriginEXT + t * gl_ObjectRayDirectionEXT;
        hitNormal = normalize(hitPoint);
        
        // Report hit distance and hit kind
        reportIntersectionEXT(t, 0U);
    }
}

The function takes two parameters:

  1. Hit Distance (\(t\)): The parametric distance along the ray vector.
  2. Hit Kind: An application-defined integer specifying attributes like front-facing or back-facing hit states.

When reportIntersectionEXT() is invoked, Vulkan executes the any-hit shader (if configured) to handle transparency or discard logic. If accepted, the pipeline automatically updates the ray's current maximum distance (gl_RayTmaxEXT) to \(t\), pruning any potential hits located farther along the ray. Once traversal finishes, the closest reported intersection invokes the closest-hit shader, which receives the custom hit attributes (such as hitNormal) to compute final lighting and shading.

Advantages and Performance Trade-offs

Using intersection shaders for custom primitives eliminates geometric tessellation artifacts, rendering mathematically smooth curves at any magnification level while significantly reducing memory overhead by eliminating dense vertex and index buffers.

However, procedural intersection shaders run as software on programmable compute units rather than on the GPU's fixed-function ray-triangle hardware. To maintain high performance, developers must ensure bounding boxes fit the target geometry as tightly as possible to minimize false-positive shader invocations, and mathematical intersection routines must remain computationally lightweight.
