Vulkan Compute Shader Occupancy and SIMD Vector Width

This article examines how Single Instruction, Multiple Data (SIMD) vector width—represented as subgroup size in the Vulkan API—directly influences compute shader occupancy across major GPU architectures. It details how execution widths on hardware from NVIDIA, AMD, Intel, and mobile vendors dictate register allocation, divergence penalties, and thread scheduling. Developers will gain an understanding of how tailoring compute workgroup configurations to vendor-specific SIMD execution units balances hardware utilization and latency hiding.

The Role of SIMD Width and Occupancy

In Vulkan, the fundamental hardware execution unit for compute workloads is the subgroup (known vendor-specifically as a warp on NVIDIA or a wavefront on AMD). The SIMD vector width defines how many invocations (threads) execute in lockstep across a single vector processing unit.

Occupancy measures the ratio of active subgroups resident on a compute engine (such as an AMD Compute Unit, NVIDIA Streaming Multiprocessor, or Intel Xe Core) relative to the hardware’s theoretical maximum. High occupancy is critical for latency hiding: when one subgroup stalls on a high-latency global memory load, the hardware thread scheduler switches execution to another ready subgroup.

SIMD width directly determines how many resources a single subgroup consumes, creating an inherent tension between subgroup size, register consumption, and total active occupancy.

Architectural Differences Across Vendors

Different hardware vendors implement fundamentally distinct approaches to SIMD vector widths, which directly alters how compute kernels achieve optimal occupancy.

NVIDIA (Fixed Width)

NVIDIA GPUs have consistently maintained a fixed SIMD vector width of 32 threads, termed a warp. In Vulkan, NVIDIA hardware reports a static subgroup size of 32 via VkPhysicalDeviceSubgroupProperties. Because the execution width is static, developers cannot alter the physical SIMD width directly to optimize occupancy. Instead, occupancy on NVIDIA hardware is dictated entirely by allocating workgroups in integer multiples of 32 and managing per-thread register usage so that multiple warps can coexist simultaneously on an SM's register file.

AMD (Dual Wave32 and Wave64)

AMD transitioned from the legacy GCN architecture (fixed Wave64) to RDNA, which natively introduces Wave32 execution alongside Wave64 support.

  • Wave32: Halves the operational latency of instructions requiring subgroup-wide reductions and reduces divergent execution penalties. Because a Wave32 subgroup requires half the registers of a Wave64 subgroup to launch, it allows the scheduler to instantiate more active waves per Dual Compute Unit, frequently yielding higher occupancy.
  • Wave64: Useful for high-throughput, non-divergent math with high instruction-level parallelism, but runs a higher risk of exhausting compute unit vector registers, which lowers occupancy.

Using Vulkan’s VK_EXT_subgroup_size_control (promoted to core in Vulkan 1.3), developers on AMD platforms can explicitly request VK_SHADER_CORE_SUBGROUP_SIZE_CONTROL_FLAG_COMPUTE_FULL_SUBGROUPS_BIT and specify whether a compute pipeline should compile to Wave32 or Wave64 via pipeline shader stage creation flags.

Intel (Variable SIMD Compilation)

Intel architectures (Gen9 through Xe-HPG and Xe-LPG) utilize flexible Execution Units (EUs) or Vector Engines capable of running SIMD8, SIMD16, or SIMD32 configurations. The Vulkan driver compiler evaluates shader complexity and register pressure to select the SIMD width:

  • SIMD8 / SIMD16: Selected when a compute shader consumes a large number of registers. While each individual wave processes fewer invocations, smaller widths avoid spilling registers to scratch memory, preserving functional occupancy.
  • SIMD32: Selected for simpler compute kernels with minimal register requirements, maximizing raw compute throughput per dispatch at the cost of requiring more physical registers per subgroup.

Mobile GPUs (ARM Mali and Qualcomm Adreno)

Mobile architectures adopt varied, often narrower SIMD layouts designed for power efficiency.

  • ARM Mali (Valhall/5th Gen): Operates on 16-wide warp execution engines. Workgroups with irregular dimensions suffer lower efficiency if they do not cleanly map to multiples of 16.
  • Qualcomm Adreno: Typically uses 64- or 128-thread execution waves depending on the generational architecture and precision mode (FP32 vs. FP16), making register file partitioning critical to avoiding severe occupancy drops on mobile thermal budgets.

The Interplay Between Register Pressure and SIMD Width

Every physical execution unit has a finite register file size. When a compute shader is dispatched, registers are allocated per invocation across the entire SIMD width.

\[\text{Registers Per Subgroup} = \text{Registers Per Thread} \times \text{SIMD Width}\]

If a compute shader requires 64 registers per thread:

  • On a 32-wide SIMD architecture, a single subgroup requires \(64 \times 32 = 2,048\) registers.
  • On a 64-wide SIMD architecture, that same subgroup demands \(64 \times 64 = 4,096\) registers.

If an execution unit possesses an allocation ceiling of 16,384 registers, the 32-wide configuration can maintain up to 8 active subgroups concurrently on that unit. The 64-wide configuration can only maintain 4 active subgroups. If the total number of subgroups falls below the hardware scheduler’s threshold to mask memory latency, the execution pipeline stalls, degrading throughput regardless of theoretical arithmetic capacity.

Thread Divergence Penalties

Branch divergence occurs when invocations within the same subgroup follow differing execution paths (e.g., an if-else condition). GPUs serialize these paths, executing both branches with inactive threads masked out.

Wider SIMD configurations (such as SIMD64) exponentially increase the statistical probability that threads within a subgroup will diverge. Divergence reduces execution efficiency: if half the invocations in a Wave64 follow branch A and half follow branch B, the execution unit operates at 50% vector efficiency during both passes. In contrast, smaller SIMD configurations (SIMD16 or SIMD32) segment workloads into finer grains, enabling independent branches to resolve without penalizing unrelated invocations, thereby preserving higher effective computational occupancy.

Strategic Implementation in Vulkan

To achieve balanced occupancy across varying SIMD widths:

  1. Query Hardware Properties: Inspect VkPhysicalDeviceSubgroupSizeControlProperties to determine minSubgroupSize, maxSubgroupSize, and supported stages.
  2. Explicitly Set Subgroup Sizes: Where available, leverage VkPipelineShaderStageRequiredSubgroupSizeCreateInfo to mandate optimal sizes (e.g., setting Wave32 on AMD for register-heavy algorithms).
  3. Align Workgroup Dimensions: Size compute workgroups as direct multiples of the platform's maximum expected SIMD width (typically 32 or 64) to prevent "tail threads"—partially filled subgroups that reserve full register sets while operating at partial hardware efficiency.
  4. Monitor Occupancy vs. Latency: Profile using vendor tools (such as NVIDIA Nsight, AMD Radeon Developer Tool Suite, or Intel VTune). Maximizing raw occupancy is secondary to overall execution time; highly optimized shaders with lower occupancy can outperform high-occupancy shaders if the execution units maintain sufficient instruction-level parallelism to hide memory latency without register spilling.
