Atomic Load, Store, and Exchange in Vulkan Memory Model

The formalized Vulkan memory model, adapted from the C++11 and C11 memory models for massively parallel GPU architectures, formally defines how concurrent memory accesses operate across shader invocations. Within this model, atomic load, store, and exchange operations provide race-free primitives to read, write, and update shared locations in Workgroup and Storage Buffer memory classes. By pairing these operations with explicit memory semantics—such as Relaxed, Acquire, Release, and AcquireRelease—and defining their memory scope, the model establishes strict guarantees for ordering, visibility, and synchronization across threads.

Memory Scopes and Semantics

In Vulkan's formalized memory model, atomic operations cannot be understood in isolation; their behavior depends on two required parameters: Memory Scope and Memory Semantics.

  • Memory Scope defines the boundary of invocations that participate in the synchronization. Scopes range from small to broad execution domains: Subgroup, Workgroup, QueueFamily, Device, and CrossDevice (System).
  • Memory Semantics define the ordering and visibility constraints applied to surrounding non-atomic and atomic memory accesses. These include Relaxed, Acquire, Release, AcquireRelease, and SequentiallyConsistent.

Under this framework, standard caches on modern GPUs are not assumed to be automatically coherent across execution units. Atomic operations act as the synchronization points that order memory operations and enforce cache availability and visibility operations.

Atomic Load Operations

An atomic load reads a value from a specified memory address as a single, indivisible operation, preventing partial reads caused by concurrent writes.

  • Supported Semantics: Atomic loads support Relaxed, Acquire, and SequentiallyConsistent semantics. An atomic load cannot take Release or AcquireRelease semantics.
  • Relaxed Atomic Load: Guarantees that the read itself is atomic and coherent with respect to the memory location, but it establishes no ordering constraints relative to other memory accesses. Surrounding loads and stores can be freely reordered around a relaxed atomic load.
  • Acquire Atomic Load: Acts as a one-way memory barrier. It prevents any subsequent memory reads or writes (in program order) from being reordered before the atomic load. When paired with a matching atomic Release operation performed by another invocation within the defined scope, the Acquire load synchronizes with that release, ensuring that all memory writes made prior to the release operation become visible to the acquiring invocation.

Atomic Store Operations

An atomic store overwrites the value at a targeted memory location indivisibly, ensuring that no reading thread observes a torn or incomplete write.

  • Supported Semantics: Atomic stores support Relaxed, Release, and SequentiallyConsistent semantics. They cannot take Acquire or AcquireRelease semantics.
  • Relaxed Atomic Store: Writes the value atomically to the target location within the given scope without enforcing ordering on surrounding memory instructions.
  • Release Atomic Store: Enforces that all preceding memory writes and reads (in program order) completed by the calling invocation are committed and made available before the atomic store itself becomes visible. Once an invocation at the matching scope observes this store via an Acquire operation, all data published prior to the Release store is guaranteed to be visible to that invocation.

Atomic Exchange Operations

An atomic exchange is a read-modify-write (RMW) primitive that replaces the value at a memory address with a new value and returns the original value in a single indivisible step.

  • Supported Semantics: Because an exchange performs both a read and a write, it supports the full range of synchronization semantics: Relaxed, Acquire, Release, AcquireRelease, and SequentiallyConsistent.
  • Acquire Semantics: Orders subsequent operations after the read phase of the exchange.
  • Release Semantics: Orders preceding operations before the write phase of the exchange.
  • AcquireRelease Semantics: Combines both constraints, effectively allowing the exchange to act as a synchronization bridge. It imports visibility of previous writes via its acquire component and exports visibility of current writes via its release component.

Atomic exchange operations participate in the modification order of a memory location. If multiple invocations execute atomic exchanges on the same address concurrently, the Vulkan memory model guarantees that they will be serialized into a total order. Each exchange observes the value written by the immediately preceding operation in that modification order.

Synchronization and Data Race Freedom

Under the Vulkan memory model, non-atomic accesses to the same memory location by multiple invocations result in a data race and undefined behavior unless separated by synchronization. Atomic load, store, and exchange operations do not generate data races among themselves. Furthermore, when configured with Acquire and Release semantics over a shared scope, these operations form synchronized-with edges, allowing developers to establish safe producer-consumer relationships for non-atomic payloads across GPU execution boundaries.
