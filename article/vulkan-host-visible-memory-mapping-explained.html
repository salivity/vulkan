Vulkan Host-Visible Memory Mapping Explained

In the Vulkan API, memory mapping for host-visible memory is the mechanism that bridges the CPU and GPU memory spaces. It allows the CPU (the host) to obtain a valid virtual address pointer to a block of GPU-accessible memory (VkDeviceMemory). This article explains what host-visible memory is, how mapping transforms device allocations into standard host pointers, the role of cache coherency, and best practices for moving data efficiently between the CPU and GPU.

What Is Host-Visible Memory?

When allocating memory in Vulkan via vkAllocateMemory, you must select a memory type supported by the physical device that matches your resource requirements. If an allocation includes the VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT flag, the driver guarantees that the host (CPU) can access this memory directly over the system bus (such as PCIe) or via shared unified memory in integrated architectures.

Host-visible memory is typically used for staging buffers, frequently updated uniform buffers, or dynamic vertex data that the CPU needs to write to before rendering.

The Role of Memory Mapping

By default, an allocated VkDeviceMemory handle represents an opaque GPU resource; the CPU cannot dereference or write to it directly. Memory mapping translates this device handle into a standard CPU virtual memory address.

This is accomplished using the vkMapMemory function:

void* pData;
vkMapMemory(device, memory, offset, size, 0, &pData);

Once mapped, pData becomes a raw host pointer (e.g., void*). The CPU can now read from or write to this memory region using standard operations such as memcpy, SIMD vector instructions, or direct assignment. When CPU access is complete, the application can call vkUnmapMemory, though unmapping is not strictly required after every write.

Memory Coherency and Flushing

Mapped memory behavior depends on whether the memory type also features the VK_MEMORY_PROPERTY_HOST_COHERENT_BIT property:

  • Host-Coherent Memory: If the allocation has the HOST_COHERENT_BIT, the host cache and device memory are automatically kept in sync by hardware. Any write by the CPU becomes visible to the GPU without extra API calls, though proper Vulkan synchronization (such as pipeline barriers) is still required to order GPU operations.
  • Non-Coherent Memory: If the memory is host-visible but lacks the host-coherent flag, CPU writes may remain trapped in the CPU’s L1/L2 cache lines. To ensure the GPU sees the written data, the application must explicitly flush the modified address ranges using vkFlushMappedMemoryRanges. Conversely, if the GPU writes to this memory and the CPU needs to read it, the CPU must call vkInvalidateMappedMemoryRanges to invalidate its local caches before reading.

Persistent Mapping

In modern Vulkan architectures, frequent mapping and unmapping incurs unnecessary overhead. Vulkan explicitly supports persistent mapping, where an application calls vkMapMemory once during initialization and keeps the pointer valid for the entire lifetime of the allocation. The application then uses synchronization primitives (such as fences and semaphores) along with offsets or ring buffers to safely update data without redundant mapping calls.
