Memory Barriers in Vulkan Compute Shaders Explained

This article explores the purpose and mechanics of memory barriers inside compute shaders within the Vulkan API. It covers how the GPU's weakly ordered memory model necessitates synchronization, the critical distinction between execution control and memory visibility, the specific types of intra-shader memory barriers available, and how these barriers prevent data races across invocations in a workgroup.

The Problem: Weakly Ordered GPU Memory

Vulkan operates on a weakly ordered, highly parallel memory architecture. When a compute shader executes, thousands of invocations (threads) run concurrently across multiple compute units. By default, the GPU does not guarantee the order in which memory writes become visible to other invocations, nor does it guarantee that writes will be immediately flushed from local registers or L1 caches to shared memory caches or VRAM.

Without explicit synchronization, reading data that was written by another invocation can lead to race conditions, including Read-After-Write (RAW), Write-After-Read (WAR), and Write-After-Write (WAW) hazards.

The Purpose of In-Shader Memory Barriers

The primary purpose of an in-shader memory barrier is to ensure memory ordering and memory visibility:

  1. Ordering: It enforces that all memory stores issued before the barrier are processed before any memory loads or stores issued after the barrier.
  2. Visibility: It ensures that modifications made by one invocation are made visible to other invocations that share a memory scope (such as the workgroup or the entire GPU).

Execution Barriers vs. Memory Barriers

In shader languages like GLSL or HLSL running over Vulkan's SPIR-V intermediate representation, there is a fundamental difference between execution barriers and memory barriers:

  • Execution Barrier (barrier()): Pauses execution of an invocation until all other invocations within the same workgroup reach the same point in the code. However, an execution barrier alone does not guarantee that non-shared memory writes are visible.
  • Memory Barrier (memoryBarrier*()): Controls the ordering and visibility of memory transactions. It does not pause thread execution unless coupled with an execution barrier.

In practice, compute shaders frequently pair memory barriers with execution barriers to ensure that data written by one thread can safely be read by another thread within the same workgroup.

Types of In-Shader Memory Barriers

GLSL and SPIR-V provide specialized memory barrier functions tailored to specific memory types. Using granular barriers avoids unnecessary cache flushes and maintains performance:

  • memoryBarrierShared(): Synchronizes access exclusively to shared memory (workgroup-local storage). It ensures that all writes to shared variables made by the invocation prior to the barrier are committed and accessible to other invocations in the workgroup.
  • memoryBarrierBuffer(): Applies to Shader Storage Buffer Objects (SSBOs). It guarantees that writes to storage buffers complete and are made visible according to the specified memory scope.
  • memoryBarrierImage(): Applies to storage images (image2D, image3D, etc.). It ensures that imageStore operations are committed before subsequent image reads or writes take place.
  • memoryBarrier(): A global memory barrier that synchronizes all memory types simultaneously, including shared memory, storage buffers, and images. While convenient, it can introduce unnecessary latency if only a specific memory type needs synchronization.
  • groupMemoryBarrier(): Similar to memoryBarrier(), but restricts the ordering and visibility scope to invocations within the local workgroup.

Scope and Coherence

In-shader memory barriers work in tandem with type qualifiers such as coherent. In Vulkan GLSL, marking a storage buffer or image as coherent informs the compiler that the data is shared across invocations, preventing the compiler from caching values in registers across barrier boundaries. When an invocation issues a memory barrier on a coherent resource, the hardware flushes the writes to the common cache level shared by the communicating invocations, guaranteeing safe and deterministic concurrent execution.
