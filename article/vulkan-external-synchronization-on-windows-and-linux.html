Vulkan External Synchronization on Windows and Linux

This article provides an overview of how the Vulkan graphics and compute API interoperates with external operating system synchronization primitives. By leveraging dedicated Vulkan extensions, developers can import and export semaphores and fences as native Windows handles or Linux file descriptors. This functionality facilitates cross-process synchronization and low-overhead interoperability with native platform APIs, display servers, and other graphics frameworks like Direct3D, OpenGL, and CUDA.

The External Synchronization Architecture

Vulkan separates the concept of internal synchronization from external handle exchange through a modular extension structure:

  1. Base Extensions: VK_KHR_external_memory_capabilities, VK_KHR_external_semaphore_capabilities, and VK_KHR_external_fence_capabilities define the queries used to determine platform support for external handle types.
  2. Core Abstractions: VK_KHR_external_semaphore and VK_KHR_external_fence define the mechanics of associating Vulkan synchronization primitives with external payloads.
  3. Platform-Specific Bindings: Specific extensions map these primitives to operating system objects, including Win32 handles on Windows and POSIX file descriptors on Linux.

When a synchronization primitive is exported, ownership of the underlying sync payload can either be shared or transferred (payload copy vs. handle transfer), depending on the platform object type and handle flags.

Integration on Windows

On Microsoft Windows, Vulkan integrates with native synchronization objects via VK_KHR_external_semaphore_win32 and VK_KHR_external_fence_win32. These extensions allow synchronization primitives to interface with Win32 HANDLE types.

Handle Types

  • NT Handles (VK_EXTERNAL_SEMAPHORE_HANDLE_TYPE_OPAQUE_WIN32_BIT): Secure, reference-counted operating system handles. They require explicit duplication via DuplicateHandle or process-to-process passing and can have Windows security attributes applied.
  • KMT Handles (VK_EXTERNAL_SEMAPHORE_HANDLE_TYPE_OPAQUE_WIN32_KMT_BIT): Legacy global handles representing kernel-mode objects. They are faster to instantiate but lack fine-grained security controls and cannot cross session boundaries.
  • Direct3D Interoperability (VK_EXTERNAL_SEMAPHORE_HANDLE_TYPE_D3D12_FENCE_BIT): Directly maps a Vulkan timeline semaphore to a Direct3D 12 ID3D12Fence object. This enables direct GPU-side synchronization between Vulkan and DirectX 12 queues without CPU intervention.

Windows Workflow

  1. Creation: A VkExportSemaphoreCreateInfo structure containing the target handle type is chained to the VkSemaphoreCreateInfo pNext pointer.
  2. Exporting: After creation, the application retrieves the native Win32 handle using vkGetSemaphoreWin32HandleKHR.
  3. Importing: Another process or native API imports the handle using vkImportSemaphoreWin32HandleInfoKHR. If importing a D3D12 fence, the application specifies the shared NT handle created by the Direct3D runtime.

Integration on Linux

On Linux, Vulkan relies on POSIX file descriptors (FDs) through VK_KHR_external_semaphore_fd and VK_KHR_external_fence_fd. Synchronization models on Linux fall into two primary paradigms: explicit sync files and DRM synchronization objects.

Handle Types

  • Opaque File Descriptors (VK_EXTERNAL_SEMAPHORE_HANDLE_TYPE_OPAQUE_FD_BIT): Transfers an opaque GPU driver-specific payload encapsulated within a standard POSIX file descriptor.
  • Sync Files (VK_EXTERNAL_SEMAPHORE_HANDLE_TYPE_SYNC_FD_BIT): Represents the Linux kernel's explicit synchronization framework (sync_file objects). This is widely used on Android and modern Linux Wayland compositors to track buffer availability and GPU completion.
  • DRM Sync Objects (VK_EXTERNAL_SEMAPHORE_HANDLE_TYPE_DRM_SYNCOBJ_BIT): Directly exposes Linux Direct Rendering Manager (DRM) synchronization objects. DRM syncobjs support both binary and timeline synchronization, making them the standard synchronization primitive for modern Wayland window systems and cross-driver coordination.

Linux Workflow

  1. Creation: The application configures VkExportSemaphoreCreateInfo with the appropriate handle type (e.g., SYNC_FD_BIT or OPAQUE_FD_BIT).
  2. Exporting: The native file descriptor is generated via vkGetSemaphoreFdKHR. For SYNC_FD_BIT, the handle must be exported after a GPU batch is submitted because sync files represent single-use kernel fence snapshots. Exporting a sync_file temporarily invalidates or consumes the Vulkan semaphore's signal state.
  3. Importing: A consuming application imports the file descriptor using vkImportSemaphoreFdInfoKHR. Once imported, the target application uses native POSIX calls (such as poll() or epoll()) or binds the handle directly to another GPU context to await signal completion.

Timeline Semaphores and Future Compatibility

With the introduction of timeline semaphores (VK_KHR_timeline_semaphore / Vulkan 1.2), external synchronization expanded from strictly binary states (signaled/unsignaled) to monotonic counter-based synchronization. On Windows, this maps directly to ID3D12Fence handles. On Linux, timeline semaphores map to DRM syncobj timeline points. This alignment ensures that modern low-level APIs across Windows and Linux can synchronize execution pipelines without CPU-side stalls.
