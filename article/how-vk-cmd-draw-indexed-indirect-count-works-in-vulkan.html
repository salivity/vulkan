How vkCmdDrawIndexedIndirectCount Works in Vulkan

This article explains how the vkCmdDrawIndexedIndirectCount function in the Vulkan API enables fully GPU-driven rendering pipelines by allowing the GPU to determine draw call counts at runtime. By moving batch generation, culling, and count resolution directly onto the device, applications can execute variable numbers of draw calls without reading data back to the host, thereby eliminating CPU stalls and dramatically reducing frame latency.

The Limitation of Standard Indirect Drawing

In standard indirect rendering via vkCmdDrawIndexedIndirect, the parameters for each draw call (index count, instance count, first index, vertex offset, and first instance) reside on the GPU in a VkBuffer. However, the total number of draws executed—the drawCount parameter—is hardcoded by the CPU during command buffer recording.

If a compute shader performs visibility culling or level-of-detail (LOD) selection, the exact number of visible items is known only to the GPU. With standard indirect drawing, developers face two inefficient options:

  1. Allocate space for the maximum potential draws and have the compute shader zero out dead draws (wasting GPU command-processor cycles on empty invocations).
  2. Read the computed draw count back to the CPU via a mapped buffer (creating a pipeline stall that forces the CPU to wait for GPU execution).

How vkCmdDrawIndexedIndirectCount Solves the Problem

Originally introduced via the VK_KHR_draw_indirect_count extension and integrated into Vulkan 1.2 core, vkCmdDrawIndexedIndirectCount allows the draw count itself to be stored in GPU memory.

The command signature takes two distinct buffers:

  • buffer: The VkBuffer containing an array of VkDrawIndexedIndirectCommand structures.
  • countBuffer: The VkBuffer containing a single 32-bit unsigned integer representing the actual number of draws to execute.

When this command is recorded, the CPU does not supply the live draw count. Instead, it provides the count buffer, a byte offset into that buffer, and a static maxDrawCount limit.

Step-by-Step GPU-Driven Workflow

  1. Compute Pre-Pass: A compute shader processes bounding boxes or geometry data for a scene. It performs frustum culling, occlusion testing, or LOD calculations across thousands of potential meshes.
  2. Dynamic Generation: When an object passes the visibility tests, the compute shader performs an atomic add (atomicAdd) on an integer counter located in the count buffer. The returned index determines where in the indirect draw buffer to write that mesh’s VkDrawIndexedIndirectCommand.
  3. Pipeline Synchronization: A pipeline barrier (vkCmdPipelineBarrier) ensures the compute shader finishes writing to both the indirect draw buffer and the count buffer before the draw phase begins. The barrier sets the source access mask to VK_ACCESS_SHADER_WRITE_BIT and the destination access mask to VK_ACCESS_INDIRECT_COMMAND_READ_BIT.
  4. Execution by the Command Processor: The GPU command processor reads the integer from countBuffer. It clamps this value to the CPU-defined maxDrawCount using min(countValue, maxDrawCount) to prevent buffer overflows. The GPU then executes exactly that many draws from the indirect buffer.

Eliminating CPU Readbacks

By keeping both the command data and the invocation count inside GPU memory, the execution flow remains entirely on the device timeline. The CPU records command buffers well ahead of execution without needing to know how many meshes are visible in any given frame.

This architecture avoids CPU-GPU synchronization points (such as fences or mapped buffer flushes), keeps the graphics queue saturated, and maximizes throughput for complex, dynamic scenes.
