Vulkan Buffer Device Address vs Virtual Memory Pointers

This article explains the core differences in Vulkan between physical storage buffer addresses and virtual memory pointers, detailing how each is addressed, where they execute, and how they interact with system and device hardware. While both concepts deal with memory locations, physical storage buffer addresses provide 64-bit GPU-accessible pointers directly inside shader code to eliminate descriptor overhead, whereas virtual memory pointers encompass either CPU-side host virtual addresses obtained through mapping or traditional descriptor-abstracted GPU memory references.

Understanding Physical Storage Buffer Addresses

A physical storage buffer address (introduced widely via the VK_KHR_buffer_device_address extension and core in Vulkan 1.2) is a 64-bit integer (VkDeviceAddress) representing a direct GPU memory address. In shaders, this corresponds to the PhysicalStorageBuffer storage class in SPIR-V or the GL_EXT_buffer_reference extension in GLSL.

Key characteristics include:

  • Shader Execution: The GPU can dereference these addresses natively within shaders using standard C-style pointer mechanics.
  • Descriptor Bypass: Shaders do not need to bind buffers to descriptor sets. Instead, 64-bit addresses can be passed via push constants, uniform buffers, or embedded within other buffers.
  • Complex Data Structures: It enables pointer chasing on the GPU, making it straightforward to implement graphs, linked lists, trees, and acceleration structures for ray tracing.
  • Safety: There is no hardware-enforced bounds checking by default; invalid memory dereferences cause device-loss errors or GPU hangs.

Understanding Virtual Memory Pointers

In Vulkan programming, virtual memory pointers generally refer to two distinct mechanisms: CPU host virtual addresses and traditional GPU virtual memory abstractions.

Host Virtual Memory Pointers

When allocating memory with vkAllocateMemory using a host-visible memory type, you retrieve a CPU virtual memory pointer using vkMapMemory.

  • Execution Context: Exists strictly within the operating system’s virtual memory space for the CPU.
  • Accessibility: Accessible only by the CPU host application. The GPU cannot read or write to this pointer directly; it interacts with the underlying memory via Vulkan synchronization commands and caches.
  • Purpose: Primarily used for staging, uploading data, and updating dynamic uniforms from the host.

Abstracted GPU Virtual Memory

Historically, Vulkan handles GPU virtual memory via handles (VkDeviceMemory, VkBuffer) and bindings (VkDescriptorSet). The GPU's Memory Management Unit (MMU) maps allocations into its virtual address space, but these addresses are hidden behind resource descriptors and pipeline bindings. The shader refers to an index (a binding slot) rather than an explicit memory address.

Architectural Impact

The primary distinction lies in accessibility and indirection. A host virtual memory pointer is managed by the operating system’s MMU for CPU execution. A physical storage buffer address is a GPU-side address that allows compute and graphics shaders to bypass the Vulkan descriptor abstraction layer.

Although named "physical" storage buffer addresses to distinguish them from abstract logical bindings, these addresses are still mapped through the GPU's internal MMU virtual address space. However, they function as raw pointers from the shader's perspective, removing the descriptor indirection layer and allowing the GPU to treat its memory with the same pointer-driven flexibility long enjoyed by the CPU.
