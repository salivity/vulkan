Real-Time Preemption Across Vulkan Queues

Vulkan provides robust support for concurrent workloads through multiple queue families and priority abstractions, but it cannot strictly guarantee hard real-time preemption across different queues. While extensions and priority levels allow developers to hint at execution urgency, the underlying hardware scheduling, pipeline architectures, and specification definitions prevent deterministic, microsecond-level interruption of running workloads. Understanding this behavior requires examining how Vulkan defines queues, how modern GPUs implement preemption, and the role of OS-level scheduling.

The Vulkan Queue and Priority Model

In Vulkan, command buffers are submitted to queues (VkQueue) representing underlying execution channels on the device. Vulkan supports relative queue priorities via the pQueuePriorities parameter in VkDeviceQueueCreateInfo, assigning values from 0.0 (lowest) to 1.0 (highest). Additionally, extensions such as VK_KHR_global_priority expose system-level priority bands (Low, Medium, High, Realtime).

However, the core Vulkan specification explicitly defines these priority values as execution hints rather than preemptive guarantees. The specification does not mandate that a higher-priority submission immediately halts or interrupts in-flight commands on a lower-priority queue. It only suggests that the implementation should favor the execution of higher-priority work when resources become available.

Hardware Preemption Granularity

True real-time preemption requires the ability to interrupt a running task deterministically at any point in execution and quickly switch context to a critical task. Modern GPU architectures generally do not support arbitrary, instruction-level preemption across all pipeline stages due to the massive amount of state data held in register files and shared memory.

Instead, preemption typically operates at coarse granularity:

  • Command buffer boundaries: The scheduler waits for a full command buffer or sub-pass to finish before context switching.
  • Draw or dispatch boundaries: The GPU switches tasks between individual draw calls or compute dispatches.
  • Triangle or wave/warp boundaries: Compute units finish their current thread groups or primitives before switching to another queue's tasks.

Because compute shaders or long-running render passes can tie up Execution Units (EUs) or Streaming Multiprocessors (SMs) for unpredictable durations, a newly submitted command on a higher-priority queue must often wait for running warps to retire naturally, introducing variable latency that violates strict real-time criteria.

Resource Contention and Hardware Queue Mapping

Vulkan queues are logical abstractions that do not always map 1:1 to independent hardware command processors or isolated compute units. Even when an application utilizes distinct queues (such as a compute queue alongside a graphics queue), those queues frequently compete for the same execution hardware, memory caches, and memory bandwidth.

Unless the GPU hardware supports dedicated spatial partitioning—where specific execution engines are completely isolated from one another—work executing from one queue will contend with work from another. This contention can stall a higher-priority task even if the hardware scheduler supports mid-dispatch context switching.

Operating System and Driver Scheduling

Vulkan command submission operates above driver and kernel schedulers, such as WDDM on Windows or DRM/KMS on Linux. The OS graphics driver controls how command streams are scheduled onto hardware ring buffers.

While OS-level schedulers can preempt GPU contexts (for example, to prevent Desktop Window Manager timeouts or to prioritize interactive windows), these operations prioritize system responsiveness rather than deterministic real-time deadlines. Context switches at this level incur non-deterministic latency penalties as pipeline state, caches, and registers are saved and restored.

Real-Time Alternatives: Vulkan SC and Spatial Partitioning

For systems requiring strict determinism, standard Vulkan is typically not used. The Khronos Group developed Vulkan SC (Safety Critical) to address high-reliability environments such as automotive displays and avionics.

Even in safety-critical contexts, determinism is rarely achieved through aggressive cross-queue preemption. Instead, architectures rely on:

  • Spatial Hardware Partitioning: Splitting GPU hardware into physically isolated partitions running independent tasks.
  • Time-Triggered Execution: Scheduling tasks into strictly allocated, non-overlapping time slices.
  • Bounded Execution Shaders: Restricting shader length and complexity to ensure any pipeline state drains within a guaranteed worst-case execution time (WCET).

Standard Vulkan does not strictly guarantee real-time preemption across queues. High-priority queues provide reduced latency through best-effort scheduling, but deterministic preemption remains constrained by hardware context-switching granularity and platform scheduler limitations.
