Vulkan Multi-GPU Support via Device Groups

Vulkan supports multi-GPU rendering natively through physical device groups, a feature introduced in the VK_KHR_device_group extension and integrated into core Vulkan 1.1. This mechanism allows multiple physical graphics processing units (GPUs) to be treated as a single logical device, enabling fine-grained control over workload distribution, resource replication, and cross-GPU synchronization. This article explains the architectural components of physical device groups, resource management, execution models, and common multi-GPU rendering patterns in Vulkan.

Physical Device Groups and the Single Logical Device

In a standard Vulkan setup, each physical GPU (VkPhysicalDevice) requires its own distinct logical device (VkDevice). Under the device group paradigm, compatible GPUs—typically identical hardware connected via PCIe or dedicated interconnects like NVLink—are queried and grouped together via vkEnumeratePhysicalDeviceGroups.

When instantiating a device group, a single logical VkDevice is created using the VkDeviceGroupDeviceCreateInfo structure containing the grouped physical devices. This exposes the combined hardware under a unified API handle, drastically reducing CPU-side multi-threading overhead compared to managing separate instances and logical devices independently.

Device Masks and Command Execution

Vulkan manages the routing of commands to specific GPUs within a group through bitmasks known as device masks (deviceMask). Each physical device in the group is assigned a bit index based on its position in the group array (GPU 0 is bit 1 << 0, GPU 1 is bit 1 << 1, and so on).

Developers control execution routing via several mechanisms:

  • Command Buffers: Command buffers record commands with an initial mask. Setting vkCmdSetDeviceMask alters the target physical devices dynamically within a command sequence.
  • Render Passes: The VkRenderPassDeviceMaskInfo structure allows developers to specify which GPUs execute specific subpasses or entire render passes.
  • Draw and Dispatch Calls: If a draw call occurs while a multi-device mask (e.g., 0b11) is active, all designated GPUs execute that draw call simultaneously using their local state.

Memory Allocation and Peer Access

Memory management across multiple GPUs provides distinct modes depending on whether data should be mirrored or partitioned:

  1. Replicated Memory: By default, allocating memory creates an identical allocation on each physical device within the group. Writes to host-visible memory update across all targeted physical devices unless constrained.
  2. Device-Specific Allocation: Using VkMemoryAllocateFlagsInfo with the VK_MEMORY_ALLOCATE_DEVICE_MASK_BIT, developers can restrict memory allocations to a specific subset of GPUs, conserving VRAM for data unique to a single device.
  3. Peer Memory Access: When high-speed links or supported PCIe topographies exist, Vulkan queries peer-to-peer capabilities through vkGetDeviceGroupPeerMemoryFeatures. Supported peer memory allows one GPU to directly read from or write to the memory resident on another GPU without passing through host system RAM.

Multi-GPU Synchronization

Synchronization across GPUs in a group utilizes standard Vulkan primitives extended with multi-GPU awareness:

  • Semaphores and Fences: Semaphores operate across device boundaries. A semaphore signaled by commands executing on GPU 0 can unblock pipeline stages or queue submissions on GPU 1.
  • Image Layout Transitions: Image barriers can synchronize access across physical devices using VkSampleLocationOrDeviceGroupImageBarrier or by applying transitions across the active device mask.

Common Multi-GPU Rendering Patterns

By controlling device masks and cross-device transfers, developers can implement several multi-GPU rendering techniques:

  • Alternate Frame Rendering (AFR): GPU 0 processes even frames while GPU 1 processes odd frames. The device mask switches per frame. Cross-frame dependencies (such as temporal anti-aliasing or shadow caches) are transferred via peer-to-peer copies.
  • Split Frame Rendering (SFR): A single frame is split into multiple viewports or scissor rectangles, with each GPU rendering a specific portion of the screen simultaneously.
  • Virtual Reality (VR): Each GPU renders the view for a single eye concurrently using separate command streams or geometry passes, minimizing latency.
  • Asynchronous Compute Offloading: A secondary GPU can be dedicated solely to heavy compute pipelines—such as physics simulations, particle systems, or baking ray-traced acceleration structures—while the primary GPU handles the main rasterization pipeline.
