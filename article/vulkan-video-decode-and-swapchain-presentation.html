Vulkan Video Decode and Swapchain Presentation

Vulkan Video extensions bring hardware-accelerated video decoding directly into the Vulkan ecosystem, allowing applications to process compressed video streams on the GPU. Displaying these decoded frames requires seamless interaction with Vulkan's presentation engine via the VK_KHR_swapchain extension. This integration relies on efficient GPU-native resource management, queue family transfers, format conversion, and robust synchronization, enabling smooth playback without round-tripping video data through host CPU memory.

Resource Allocation and Image Creation

When decoding video frames using extensions like VK_KHR_video_decode_queue, the decoder writes uncompressed video data directly into destination images (VkImage). These destination images must be created with the VK_IMAGE_USAGE_VIDEO_DECODE_DST_BIT_KHR usage flag, alongside decode-specific profiles.

Swapchain images, by contrast, are allocated by the presentation engine and typically require usage flags like VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT or VK_IMAGE_USAGE_TRANSFER_DST_BIT. Because video decoders output in planar or semi-planar YCbCr formats (such as NV12 or P010) and display swapchains generally expect packed RGB formats (such as B8G8R8A8_SRGB), decoded images cannot usually serve directly as swapchain presentation targets. Instead, the decoded VkImage acts as a source resource that is converted and transferred into an acquired swapchain image.

Format Conversion via YCbCr Samplers

To bridge the gap between YCbCr video output and RGB swapchain input, Vulkan uses sampler YCbCr conversion (VK_KHR_sampler_ycbcr_conversion).

  1. The decoded picture is marked with VK_IMAGE_USAGE_SAMPLED_BIT.
  2. A VkSamplerYcbcrConversion object is created to define the color model, color range, chroma reconstruction, and component swizzle.
  3. The graphics or compute pipeline samples the decoded YCbCr image and converts it into standard RGB color space.
  4. The converted output is rendered directly onto the acquired swapchain image or copied via a blit operation.

Queue Family Ownership Transfers

Video decoding and display presentation often execute on distinct hardware engines exposed as different Vulkan queue families: a video decode queue family (VK_QUEUE_VIDEO_DECODE_BIT_KHR) and a graphics or presentation-capable queue family (VK_QUEUE_GRAPHICS_BIT).

When sharing an image between these engines:

  • Exclusive Sharing: If images are created with VK_SHARING_MODE_EXCLUSIVE, an explicit queue family ownership transfer must occur. This requires executing a pipeline barrier on the decode queue releasing the resource, followed by a matching pipeline barrier on the graphics or compute queue acquiring the resource.
  • Concurrent Sharing: If created with VK_SHARING_MODE_CONCURRENT, explicit ownership transfers are omitted, though proper execution dependencies must still be observed.

Synchronization Pipeline

Displaying a decoded frame requires tight synchronization across decoding, processing, and presentation:

  1. Acquire Swapchain Image: The application calls vkAcquireNextImageKHR, signaling an acquire semaphore when the presentation engine releases an image.
  2. Decode Execution: The decode operation submits to the video decode queue via vkCmdDecodeVideoKHR. Once decoding completes, it signals a decode-complete timeline or binary semaphore.
  3. Color Conversion and Composition: A graphics or compute command buffer waits on both the swapchain acquire semaphore and the decode-complete semaphore. It converts the decoded frame, renders any UI overlays, targets the swapchain image, and signals a render-complete semaphore.
  4. Queue Presentation: The application calls vkQueuePresentKHR, configuring the presentation engine to wait for the render-complete semaphore before scanning out the swapchain image to the physical display.
