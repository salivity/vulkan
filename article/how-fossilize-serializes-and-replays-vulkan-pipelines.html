How Fossilize Serializes and Replays Vulkan Pipelines

Fossilize is an open-source capture and replay library designed to record Vulkan pipeline creation calls and replay them independently of the host application. Developed primarily to address the persistent issue of runtime shader compilation stutter in modern PC gaming, Fossilize intercepts API calls, serializes all necessary state and shader code into portable database files, and reconstructs the pipeline objects offline or during game startup. This article explains the technical mechanics behind how Fossilize intercepts pipeline creation, packages dependent state objects, stores data efficiently, and executes the replaying process.

Interception via the Vulkan API Layer

Fossilize operates as a Vulkan layer—a standard mechanism in the Vulkan loader architecture that allows third-party code to intercept API commands before they reach the graphics driver.

When a game creates a pipeline via vkCreateGraphicsPipelines, vkCreateComputePipelines, or vkCreateRayTracingPipelinesKHR, the Fossilize layer intercepts the call. Creating a pipeline in Vulkan requires more than just the shader code; it requires an extensive hierarchy of state descriptors. Fossilize recursively traverses and captures these dependencies, including:

  • Shader Modules (VkShaderModule): The raw SPIR-V bytecode and entry-point specifications.
  • Descriptor Set Layouts and Pipeline Layouts: The resource binding signatures required by the shaders.
  • Render Pass Objects: Subpass descriptions, attachment configurations, and sample counts.
  • Fixed-Function State: Primitive topology, rasterization settings, blend states, depth-stencil tests, and dynamic state masks.
  • Specialization Constants: Specific constant data embedded into the pipeline at compile time.

Dependency Tracking and Canonicalization

A central challenge in serializing Vulkan pipelines is that Vulkan handles (e.g., VkRenderPass, VkPipelineLayout) are opaque 64-bit pointers or integers valid only within a single process execution.

Fossilize resolves this by tracking the creation parameters of every dependency leading up to pipeline creation. Instead of recording memory addresses, Fossilize builds a directed acyclic graph (DAG) of the state. Each individual object (such as a VkDescriptorSetLayoutCreateInfo struct) is extracted, copied into memory, and assigned a deterministic hash based on its raw content. This canonicalization ensures that if two identical render passes or layouts are created with different handles, Fossilize treats them as identical structural data.

Serialization and the Fossilize Database Format

Once the pipeline definition and its dependencies are resolved, Fossilize serializes the data into a binary stream. The library defines structured payloads for each object type using an internal serialization protocol.

To store these objects efficiently:

  1. Content-Addressable Storage: Each recorded object is indexed by a 64-bit or 128-bit hash computed from its serialized binary representation. If a pipeline uses a descriptor layout that has already been recorded, Fossilize writes only the hash reference rather than duplicating the layout.
  2. SPIR-V Compression: SPIR-V code represents the bulk of pipeline data. Fossilize often compresses these payloads to minimize disk footprint and disk I/O latency.
  3. Database Archives (.foz): The serialized payloads are appended to database files designed for append-only writing during gameplay. This minimizes the performance overhead of the capture layer, preventing frame-rate drops while the application is recording.

The Replay Process

Replay occurs outside the host application, typically using the fossilize-replay command-line utility or a custom implementation embedded into a game launcher (such as Steam's background shader processing system).

The replay architecture works in several stages:

  1. Database Parsing: The replayer opens the .foz database and parses the list of stored objects.
  2. Topological Sorting: Because high-level objects rely on low-level objects, Fossilize sorts the workloads to reconstruct state in the exact order required by the Vulkan specification. It first creates the VkShaderModule, VkDescriptorSetLayout, and VkRenderPass handles on the target device, followed by the VkPipelineLayout, and finally calls the pipeline creation functions.
  3. Driver-Level Compilation: As the replayer calls vkCreateGraphicsPipelines, the active Vulkan driver on the local machine compiles the intermediate SPIR-V code into machine code specific to the host GPU.
  4. Vulkan Pipeline Caches (VkPipelineCache): Replay mechanisms typically pass an active VkPipelineCache handle to the creation calls. The driver stores the compiled native binaries inside this cache.

When the game is subsequently launched by the user, the application requests the same pipelines with the same state hashes. The driver detects that these pipelines are already compiled within the local cache, bypassing the computationally expensive compilation phase entirely and eliminating runtime stutter.
