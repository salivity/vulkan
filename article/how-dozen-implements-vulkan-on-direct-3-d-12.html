How Dozen Implements Vulkan on Direct3D 12

The Dozen project (known as dzn within the Mesa 3D graphics library) is an open-source translation layer that implements the Vulkan API on top of Microsoft's Direct3D 12 (D3D12). Designed to bring hardware-accelerated Vulkan support to environments where only D3D12 drivers are available—most notably the Windows Subsystem for Linux (WSL) and Windows systems lacking native vendor Vulkan drivers—Dozen bridges the structural and conceptual differences between the two modern low-level APIs. This article explains the technical mechanisms behind Dozen, detailing how it handles shader compilation, memory allocation, descriptor binding, pipeline states, and command execution across both platforms.

Architecture within the Mesa Ecosystem

Dozen is developed as a Vulkan driver inside Mesa, allowing it to leverage shared driver infrastructure rather than implementing the entire Vulkan specification from scratch. Mesa provides common frameworks for API dispatch, state tracking, and format conversions.

By operating inside Mesa, Dozen interfaces with operating system layers via specific backends:

  • On Windows: It links directly to the user-mode d3d12.dll and DXGI runtimes.
  • On WSL (Windows Subsystem for Linux): It communicates through Microsoft's virtualization layer using a virtualized /dev/dxg device. This connects the Linux user space directly to the host Windows D3D12 kernel-mode driver (dxgkrnl), enabling direct host-GPU acceleration without traditional hypervisor graphics overhead.

Shader Translation via SPIR-V, NIR, and DXIL

Vulkan consumes shaders compiled into the SPIR-V intermediate representation, whereas Direct3D 12 requires shaders in DirectX Intermediate Language (DXIL), an LLVM-based bytecode format.

Dozen bridges this gap using Mesa’s NIR (New Intermediate Representation):

  1. SPIR-V to NIR: Ingested SPIR-V binaries are parsed and translated into Mesa’s NIR format.
  2. NIR Lowering Passes: Dozen applies target-specific optimization and transformation passes. This step handles differences in coordinate conventions (such as Y-inversion and depth ranges), dynamic indexing, and push constant emulation.
  3. NIR to DXIL: The driver uses Mesa's dedicated nir_to_dxil compiler. This backend converts the optimized NIR instructions directly into valid DXIL container blobs, which are then passed to the D3D12 API during pipeline creation.

Memory and Resource Management

While both APIs follow an explicit resource management model, their allocation paradigms diverge in subtle ways:

  • Memory Types: Vulkan defines explicit memory heaps and types with granular property flags (VK_MEMORY_PROPERTY_DEVICE_LOCAL_BIT, VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT, etc.). Dozen inspects D3D12 adapter capabilities (D3D12_FEATURE_DATA_ARCHITECTURE) and memory segments to synthesize compliant Vulkan memory types using D3D12 heap types: Default, Upload, and Readback.
  • Backing Allocations: Calls to vkAllocateMemory are typically backed by ID3D12Heap allocations or committed resources (ID3D12Resource).
  • Sub-allocation: For resources bound to imported memory or aliased structures, Dozen utilizes D3D12 placed resources (CreatePlacedResource), allocating buffers and images within pre-allocated ID3D12Heap ranges.

Descriptors and Pipeline Layouts

Vulkan uses descriptor sets and descriptor pools, whereas D3D12 relies on Root Signatures and descriptor heaps (CBV/SRV/UAV and Samplers).

  • Root Signatures: Dozen maps a Vulkan VkPipelineLayout directly to an ID3D12RootSignature. Descriptor set bindings are mapped to D3D12 descriptor tables or root parameters.
  • Descriptor Sets: To support Vulkan’s dynamic updates, Dozen allocates descriptors into internal D3D12 descriptor heaps. When descriptor sets are updated via vkUpdateDescriptorSets, Dozen writes the native D3D12 view structures (such as Constant Buffer Views or Shader Resource Views) into the corresponding heap locations.
  • Push Constants: Direct3D 12 lacks a 1:1 equivalent for Vulkan push constants. Dozen implements these by dedicating 32-bit root constants in the root signature to store the push constant payload, ensuring low-latency updates during draw calls.

Pipeline State Translation

Vulkan separates graphics and compute pipelines into VkPipeline objects, while D3D12 utilizes monolithic ID3D12PipelineState objects (PSOs).

Because Vulkan allows certain states to be defined dynamically at draw time (such as dynamic viewport, scissor, stencil reference, or blend constants), Dozen aligns dynamic Vulkan states with the corresponding D3D12 dynamic states. For states that are immutable within D3D12 PSOs (such as rasterizer states, primitive topology types, and render target formats), Dozen constructs the D3D12 pipeline description and compiles the underlying PSO during vkCreateGraphicsPipelines. If required state data is deferred, Dozen compiles and caches PSOs on demand to prevent frame stutters during execution.

Command Execution and Synchronization

Both APIs rely on recorded command buffers submitted to hardware queues, but synchronization semantics differ:

  • Command Lists: A VkCommandBuffer corresponds to a D3D12 command list (ID3D12GraphicsCommandList) and its associated allocator (ID3D12CommandAllocator). When commands are recorded in Vulkan, Dozen translates them directly into their D3D12 equivalents (e.g., vkCmdDraw maps to DrawInstanced).
  • Barriers and Transitions: Vulkan uses vkCmdPipelineBarrier with execution stages and memory access masks. Dozen translates these barrier operations into D3D12_RESOURCE_BARRIER structures. It tracks current and requested resource states, inserting state transitions (such as transitioning from D3D12_RESOURCE_STATE_RENDER_TARGET to D3D12_RESOURCE_STATE_PIXEL_SHADER_RESOURCE) into the active command list.
  • Fences and Semaphores: Vulkan timeline and binary semaphores, as well as fences, map to D3D12 monitored fences (ID3D12Fence). Submissions to a VkQueue translate to calls on an ID3D12CommandQueue, invoking Signal and Wait operations to preserve cross-queue and host synchronization boundaries.
