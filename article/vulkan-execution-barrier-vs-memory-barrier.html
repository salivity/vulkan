Vulkan Execution Barrier vs Memory Barrier

In Vulkan synchronization, pipeline barriers are the primary mechanism for coordinating work between different GPU operations. While developers often configure them together inside a single vkCmdPipelineBarrier command, synchronization in Vulkan strictly decouples the order of operations from the visibility of data. An execution barrier controls the timeline of GPU pipeline stages, ensuring specific operations finish before others start. A memory barrier controls cache coherence, ensuring that memory writes produced by earlier operations are flushed and made visible to subsequent operations.

Execution Barriers

An execution barrier establishes an execution dependency between two sets of operations. It is configured using the source stage mask (srcStageMask) and destination stage mask (dstStageMask).

  • Purpose: It dictates when tasks run relative to one another in the GPU pipeline.
  • Mechanism: When you specify a source stage (such as VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT) and a destination stage (such as VK_PIPELINE_STAGE_FRAGMENT_SHADER_BIT), the GPU ensures that all work submitted prior to the barrier reaches completion in the source stage before any work submitted after the barrier begins in the destination stage.
  • Limitation: An execution barrier does not guarantee that data modified in the source stage can be read by the destination stage. Modern GPUs feature distributed, non-coherent caches. An execution dependency ensures instructions run in sequence, but written data might still reside in local, private L1 or L2 caches.

Memory Barriers

A memory barrier establishes a memory dependency to solve the cache coherence problem. It is configured using access masks (srcAccessMask and dstAccessMask) inside descriptors like VkMemoryBarrier, VkBufferMemoryBarrier, or VkImageMemoryBarrier.

A memory dependency operates in two discrete steps:

  1. Availability: The srcAccessMask (e.g., VK_ACCESS_COLOR_ATTACHMENT_WRITE_BIT) marks written data as available. This triggers a cache flush or write-back operation, moving data from private stage caches into a central or globally accessible memory space.
  2. Visibility: The dstAccessMask (e.g., VK_ACCESS_SHADER_READ_BIT) marks the data as visible. This triggers a cache invalidation for the target unit, ensuring that subsequent read operations do not consume stale data from local caches, but instead fetch the newly available data.

A memory barrier cannot exist on its own in Vulkan; it is always tethered to an execution barrier. The execution barrier defines the temporal boundary at which the availability and visibility operations must take place.

Key Differences and Practical Usage

  • Execution Barrier = Timing: Answers when GPU pipeline stages are allowed to execute.
  • Memory Barrier = Coherence: Answers how written data is made accessible to other operations.

If you omit the memory barrier and only use an execution barrier, your commands will run in the correct chronological order, but the receiving shader or fixed-function stage may read undefined or stale data due to un-flushed caches. Conversely, if you include access masks without specifying the correct pipeline stages, the cache flush and invalidation operations may occur at the wrong time, resulting in race conditions. Correct Vulkan synchronization requires setting the execution stages accurately to define the sequence, and specifying the access flags to ensure the data is properly transferred across caches.
