Physical Storage Buffer Addressing in Vulkan and SPIR-V

Physical storage buffer addressing bridges the gap between traditional GPU descriptor-based resource management and raw, C-style 64-bit pointer dereferencing. By combining the Vulkan API's device address features with SPIR-V’s physical addressing model, developers can manipulate memory addresses directly in shaders. This article explains how this mechanism operates, detailing the Vulkan setup, the corresponding SPIR-V representation, and how the two layers interact to enable complex data structures on modern GPUs.

The Problem with Traditional Descriptor Sets

In standard Vulkan execution, shaders access buffer data via descriptor sets (VkDescriptorSet). The CPU updates descriptor sets, binds them in pipelines, and shaders index them using explicit binding decorations (layout(set = X, binding = Y)). While robust, this approach creates bottlenecks when building complex, pointer-heavy GPU data structures such as bounding volume hierarchies (BVH), scene graphs, and linked lists. Updating descriptor sets introduces CPU overhead, and indirect indexing is limited by descriptor indexing capabilities and hardware limits.

The Vulkan Side: Buffer Device Address

Physical storage buffer addressing resolves these bottlenecks through the VK_KHR_buffer_device_address extension, which was promoted to core in Vulkan 1.2.

  1. Feature Activation: The application must query and enable the bufferDeviceAddress feature in VkPhysicalDeviceBufferDeviceAddressFeatures.

  2. Buffer Creation: Any buffer intended for pointer-based access must include the VK_BUFFER_USAGE_SHADER_DEVICE_ADDRESS_BIT flag in its VkBufferCreateInfo.

  3. Retrieving the Address: Instead of constructing descriptor writes, the host queries the 64-bit integer address directly using vkGetBufferDeviceAddress():

    VkBufferDeviceAddressInfo addressInfo = {
    .sType = VK_STRUCTURE_TYPE_BUFFER_DEVICE_ADDRESS_INFO,
    .buffer = myBuffer
};
VkDeviceAddress gpuAddress = vkGetBufferDeviceAddress(device, &addressInfo);

  4. Passing Addresses to Shaders: The retrieved VkDeviceAddress is simply a 64-bit unsigned integer (uint64_t). It can be passed to the GPU using push constants, stored within uniform buffers, or embedded inside another storage buffer as a pointer to secondary data.

The SPIR-V Side: Physical Storage Buffer Model

To consume raw 64-bit addresses, SPIR-V requires specific capabilities, addressing models, and storage classes.

  • Capability: The shader module declares OpCapability PhysicalStorageBufferAddresses.
  • Addressing Model: The SPIR-V module's OpMemoryModel must specify PhysicalStorageBuffer64 instead of the standard Logical addressing model.
  • Storage Class: Pointers referencing raw device addresses use the PhysicalStorageBuffer storage class.
  • Alignment Constraints: Because hardware requires specific alignments for memory operations, types within this storage class must specify explicit memory alignments using the Aligned operand in OpLoad and OpStore instructions.

In high-level shading languages like GLSL, this functionality is accessed via GL_EXT_buffer_reference. A buffer reference type compiles into an OpTypePointer PhysicalStorageBuffer <StructType> in SPIR-V, allowing developers to define nested structures where one buffer contains pointers to others.

Interaction and Execution Flow

When a shader executes an instruction targeting a physical storage buffer address, the interaction proceeds through several stages:

  1. Address Ingestion: The shader retrieves the 64-bit base address from a push constant or uniform register.
  2. Pointer Casting: In SPIR-V, an OpConvertUToPtr instruction converts the raw 64-bit integer into a pointer of storage class PhysicalStorageBuffer.
  3. Offsetting and Arithmetic: Shaders can perform pointer arithmetic using OpAccessChain or OpInBoundsAccessChain, calculating offsets based on struct layouts and array indices directly in GPU registers without descriptor lookups.
  4. Direct Memory Access: Memory operations execute via standard OpLoad and OpStore operations on the dereferenced pointer. The GPU memory controller routes the request directly to the physical address.

Synchronization and Memory Considerations

Using physical storage buffer addressing shifts the responsibility of safety and synchronization entirely to the developer:

  • Pipeline Barriers: Because descriptors are bypassed, the Vulkan application cannot rely on descriptor-based tracking. Synchronization must be handled using pipeline barriers (VkMemoryBarrier2 or VkBufferMemoryBarrier2) with VK_PIPELINE_STAGE_ALL_COMMANDS_BIT (or specific shader stages) and access masks like VK_ACCESS_2_SHADER_STORAGE_READ_BIT and VK_ACCESS_2_SHADER_STORAGE_WRITE_BIT.
  • Bounds Checking: Physical addressing removes automatic API-level bounds checking. Accessing an unaligned or invalid device address results in undefined behavior, device loss (VK_ERROR_DEVICE_LOST), or memory corruption. The Vulkan validation layers provide GPU-assisted validation (VK_VALIDATION_FEATURE_ENABLE_GPU_ASSISTED_EXT) to catch out-of-bounds pointer reads and writes during development.
