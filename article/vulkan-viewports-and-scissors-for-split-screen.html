Vulkan Viewports and Scissors for Split-Screen

This article provides an overview of how the Vulkan graphics API manages multiple viewports and scissor rectangles to render local split-screen multiplayer games efficiently. It covers the core mechanics of Vulkan’s multi-viewport pipeline configuration, hardware capabilities, scissor clipping, dynamic state management, and the architectural approaches used to draw multiple player perspectives within a single frame buffer.

Understanding Viewports and Scissors in Vulkan

In Vulkan, rendering requires defining both a viewport and a scissor rectangle:

  • Viewport (VkViewport): Transforms incoming normalized device coordinates (NDC) ranging from [-1, 1] to the designated 2D pixel space of the render target (X, Y, Width, Height, MinDepth, MaxDepth).
  • Scissor (VkRect2D): Discards rasterized fragments that fall outside of a specified rectangular region on the render target. Unlike the viewport, it does not transform geometry; it clips pixels.

For split-screen setups, viewports scale each player's camera view to fit their designated slice of the screen, while scissors strictly confine rendering to those boundaries to prevent overlapping fragments, artifact bleeding, or unintended clears.

Hardware Capability and Feature Support

To leverage hardware-level multiple viewports, a Vulkan application must query and enable the multiViewport feature during device creation:

VkPhysicalDeviceFeatures deviceFeatures{};
deviceFeatures.multiViewport = VK_TRUE;

Developers must also inspect VkPhysicalDeviceLimits::maxViewports and maxViewportDimensions to determine the maximum number of simultaneous viewports the GPU supports (typically up to 16 on modern desktop hardware, comfortably exceeding typical 2-player or 4-player splits).

Pipeline Setup

When constructing a VkGraphicsPipeline, the viewport state is configured via VkPipelineViewportStateCreateInfo:

VkPipelineViewportStateCreateInfo viewportState{};
viewportState.sType = VK_STRUCTURE_TYPE_PIPELINE_VIEWPORT_STATE_CREATE_INFO;
viewportState.viewportCount = 4; // E.g., for a 4-player split-screen
viewportState.scissorCount = 4;

Most split-screen engines mark both viewports and scissors as dynamic states (VK_DYNAMIC_STATE_VIEWPORT and VK_DYNAMIC_STATE_SCISSOR). This allows dynamic adjustment of player screen configurations (such as transitioning from 2-player to 3-player, or handling asymmetrical splits) via command buffers without reconstructing graphics pipelines.

Execution Approaches for Split-Screen

Vulkan allows two primary strategies to direct geometry to specific split-screen partitions:

1. Sequential Command-Based Binding (Draw Loop)

The most common and flexible pattern involves looping through each active player, dynamically updating the viewport and scissor index 0, and dispatching draw calls:

  1. Bind the shared render pass and pipeline.
  2. For each player:
    • Define the player's viewport bounds and matching scissor bounds.
    • Call vkCmdSetViewport(commandBuffer, 0, 1, &playerViewport);
    • Call vkCmdSetScissor(commandBuffer, 0, 1, &playerScissor);
    • Bind camera descriptor sets for that player.
    • Submit draw calls for visible scene objects.

This approach requires no specialized shader code and allows customized frustum culling per player on the CPU side, ensuring optimal draw call efficiency.

2. Array-Indexed Viewports (Hardware Multiview)

For high-throughput rendering, Vulkan allows defining an array of viewports bound simultaneously:

vkCmdSetViewport(commandBuffer, 0, 4, viewportsArray);
vkCmdSetScissor(commandBuffer, 0, 4, scissorsArray);

Using the extension VK_EXT_shader_viewport_index_layer (or standard geometry shaders), shaders can set the built-in variable gl_ViewportIndex directly. The rasterizer will then route the primitive to the target viewport and scissor array index automatically. While this enables single-pass instancing where multiple players share identical scene geometry, it increases shader complexity and can be less optimal if each player views entirely different portions of the game world.

Preventing Artifacts with Scissor Rectangles

In split-screen scenarios, viewports alone do not guarantee strict isolation:

  • Clearing Screen Regions: Calling vkCmdClearAttachments applies only to the defined scissor rectangle. Defining isolated scissor regions ensures that clearing player two’s depth buffer does not inadvertently overwrite player one’s data.
  • Post-Processing and UI: Post-processing passes (such as motion blur or bloom) and orthographic UI layers must be constrained using scissor rects to prevent blur filters from sampling across screen splits or HUD elements from drawing onto an adjacent player's display area.

Performance Advantages

Using Vulkan's viewport and scissor architecture for split-screen games provides several efficiency gains:

  • Single Render Pass Execution: All player quadrants can share a single framebuffer, render pass, and depth-stencil attachment, eliminating costly framebuffer switching and tile-loading overhead on tile-based GPUs.
  • Reduced State Changes: Pipelines remain bound while only dynamic viewport and scissor bounds mutate, minimizing CPU-GPU synchronization bottlenecks.
  • Optimized Resource Allocation: Eliminates the need to allocate separate off-screen render targets for each player before blitting them together, conserving VRAM and bandwidth.
