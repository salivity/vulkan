Understanding Vulkan UBO Packing and std140 Layout

This article provides an overview of Uniform Buffer Object (UBO) memory packing in Vulkan, focusing on how the std140 layout rules determine the alignment, padding, and byte offsets of shader variables. Developers will learn how hardware requirements dictate memory layouts, the specific alignment rules applied to primitive types, vectors, arrays, and structs, and how to properly map host-side C/C++ memory to GPU-accessible buffers without silent corruption.

What is Uniform Buffer Object (UBO) Packing?

In the Vulkan API, a Uniform Buffer Object (UBO) is a memory buffer used to pass read-only, uniform data—such as view matrices, material properties, and light parameters—from the host CPU to GPU shaders.

Because modern GPU memory architectures are optimized to read memory in wide, aligned memory blocks (typically 16 bytes or 128 bits), variables cannot simply be packed tightly next to each other as they might be in a packed C-struct. UBO packing refers to the arrangement, spacing, and memory alignment of individual variables within a uniform buffer. Without a uniform arrangement standard, differences between CPU compiler padding and GPU memory access patterns lead to data misalignment and visual bugs.

The Purpose of the std140 Layout

To resolve discrepancies between CPU memory layouts and GPU memory architectures, GLSL and SPIR-V define standardized layouts. The std140 layout is an explicit memory layout specification defined by the OpenGL and Vulkan specifications.

When an interface block in a Vulkan shader is qualified with layout(std140), the compiler enforces deterministic, hardware-agnostic alignment and offset rules. This ensures that a given variable in the shader always resides at a predictable byte offset from the beginning of the buffer.

std140 Alignment and Offset Rules

Under std140, every variable type has a base alignment (the boundary multiple where the variable must start) and a size. Offsets must always be rounded up to the nearest multiple of the type's base alignment.

The primary rules governing variable offsets are:

  • Scalars: 32-bit types such as float, int, uint, and bool have a base alignment of 4 bytes.
  • Two-component vectors: vec2, ivec2, and uvec2 have a base alignment of 8 bytes.
  • Three-component vectors: vec3, ivec3, and uvec3 have a base alignment of 16 bytes.
  • Four-component vectors: vec4, ivec4, and uvec4 have a base alignment of 16 bytes.
  • Arrays of scalars or vectors: Each element in an array has its base alignment rounded up to a multiple of 16 bytes (the size of a vec4). An array of float values will consume 16 bytes per element, with 12 bytes of padding between each valid 4-byte scalar.
  • Structures: The base alignment of a structure is rounded up to the alignment of its largest member, and the entire struct size is padded to a multiple of 16 bytes.
  • Matrices: A matrix is treated as an array of column (or row) vectors. For example, a standard column-major mat4 is treated as an array of four vec4 vectors, each with a 16-byte alignment and 16-byte size, requiring 64 bytes total.

Calculating Variable Offsets: A Practical Example

Consider the following GLSL uniform block:

layout(std140, binding = 0) uniform CameraData {
    float exposure;   // 4 bytes
    vec3  position;   // 12 bytes, requires 16-byte alignment
    mat4  projection; // 64 bytes (4 x vec4)
    bool  enabled;    // 4 bytes
};

Following the std140 standard, the offsets are determined sequentially:

  1. exposure: Starts at offset 0. Its size is 4 bytes, covering bytes 0 through 3.
  2. position: Being a vec3, its base alignment is 16 bytes. It cannot begin immediately at byte 4. The offset is rounded up to the next 16-byte boundary, placing position at offset 16. Bytes 4 through 15 are unused padding. The vector covers bytes 16 through 27.
  3. projection: Each column vector requires a 16-byte alignment. The next available 16-byte boundary is offset 32. The matrix occupies bytes 32 through 95 (64 bytes total).
  4. enabled: Requires 4-byte alignment. Offset 96 is already a multiple of 4, so enabled sits at offset 96, spanning bytes 96 to 99.
  5. Block Size: The total size of the block is rounded to a multiple of 16, resulting in a total buffer size of 112 bytes.

Aligning Host CPU Data

To write data from a C++ host program that correctly maps to a std140 uniform buffer, developers must account for these rules using explicit padding or alignment specifiers:

struct CameraData {
    float exposure;
    float padding1[3];     // Pads offset from 4 to 16
    alignas(16) glm::vec3 position;
    alignas(16) glm::mat4 projection;
    alignas(4)  int enabled; // C++ bool representation
    float padding2[3];     // Rounds total size to 112 bytes
};

Failing to match the CPU structure layout to the std140 standard will cause the GPU to read offset values from incorrect memory locations, resulting in corrupted transforms, missing data, and undefined rendering behavior.
