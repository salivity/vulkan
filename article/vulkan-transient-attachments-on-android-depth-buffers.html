Vulkan Transient Attachments on Android Depth Buffers

In mobile graphics development, depth buffers consume substantial bandwidth and memory footprint despite rarely being needed after a frame finishes rendering. Android devices, which predominantly utilize Tile-Based Deferred Rendering (TBDR) GPUs, can completely eliminate physical memory backing for depth buffers using Vulkan's transient attachments and lazily allocated memory. By configuring Vulkan images with transient usage flags and render passes with discard operations, the Vulkan driver keeps depth data strictly within on-chip tile memory, freeing physical system RAM (DRAM) and conserving battery life.

The Mobile Architecture Context: TBDR and On-Chip Memory

Mobile chipsets found in Android devices—such as Qualcomm Adreno, ARM Mali, and Imagination PowerVR—rely on TBDR architectures. Instead of rendering the entire screen at once, the GPU divides the render target into small tiles (e.g., 16x16 pixels). Each tile is processed within high-speed, on-chip SRAM cache (often referred to as GMEM or tile memory).

During the rendering of a tile, depth testing and writing occur entirely within this local tile memory. Traditional desktop GPUs typically write this depth information back to VRAM. However, on unified memory architectures used in Android, writing depth buffers back to main system memory wastes significant memory bandwidth and power, particularly when depth is only needed to resolve occlusions within that specific frame.

Setting Up Transient Attachments in Vulkan

To avoid allocating physical RAM for depth information, the application and driver coordinate via a three-step configuration in the Vulkan API:

  1. Setting the Transient Image Flag: When creating the depth VkImage, set the usage field to include both VK_IMAGE_USAGE_DEPTH_STENCIL_ATTACHMENT_BIT and VK_IMAGE_USAGE_TRANSIENT_ATTACHMENT_BIT. The transient flag signals to the Vulkan implementation that the image will only be used temporarily within a render pass and will never be sampled or copied elsewhere.

  2. Allocating Lazily Allocated Memory: When querying vkGetImageMemoryRequirements, Android Vulkan drivers that support memory-less attachments expose a memory type featuring the VK_MEMORY_PROPERTY_LAZILY_ALLOCATED_BIT.

    Allocating memory with this flag instructs the operating system kernel and driver that while virtual address space must be reserved for the resource, physical memory pages should not be committed upfront. Physical pages are only committed if the GPU actually attempts an operation that requires physical DRAM backing.

  3. Configuring Render Pass Load and Store Operations: For transient behavior to work, the render pass description must ensure data is neither loaded from nor written to main memory:

    • loadOp: Must be set to VK_ATTACHMENT_LOAD_OP_CLEAR or VK_ATTACHMENT_LOAD_OP_DONT_CARE.
    • storeOp: Must be set to VK_ATTACHMENT_STORE_OP_DONT_CARE.

How Physical Memory is Eliminated

When the GPU starts rendering a tile, it clears or initializes the depth values directly within the on-chip tile memory without reading from DRAM. Throughout the rasterization of that tile, the depth testing against geometric primitives operates purely inside this local cache.

When tile execution finishes, the driver inspects the attachment's storeOp. Because the operation is marked as VK_ATTACHMENT_STORE_OP_DONT_CARE, the hardware drops the contents of the tile memory rather than writing them to system memory.

Because no write to DRAM ever occurs, the lazily allocated memory is never touched by an external memory write operation. The Android kernel's low-level memory manager never resolves a page fault to map real, physical RAM pages to that virtual address space. As a result, the depth buffer consumes virtual address space, but zero bytes of physical device RAM, eliminating memory allocation overhead and completely bypassing external memory bandwidth consumption.
