Image Footprint Querying in Vulkan Texture Streaming

This article explores image footprint querying in Vulkan and its role in modern feedback-driven texture streaming architectures. It covers the technical definition of shader-based image footprint querying, explains how developers obtain fine-grained access patterns directly from the GPU, and details how this metadata enables rendering engines to stream only the necessary texture mip levels and sparse tiles to minimize VRAM usage and eliminate over-fetching.

What is Image Footprint Querying?

Image footprint querying is a GPU-accelerated capability—exposed in Vulkan primarily through the VK_EXT_shader_image_footprint extension—that allows shaders to determine the exact memory footprint an image sampling operation would cover before or instead of executing the actual sample.

Under normal rendering conditions, a sampling instruction evaluates screen-space derivatives, applies filtering modes (such as trilinear or anisotropic filtering), and fetches texels from one or two mip levels. In contrast, an image footprint query evaluates these exact same sampling calculations but outputs metadata rather than color data. This metadata includes:

  • The specific mip levels chosen by the sampler's level-of-detail (LOD) and anisotropic calculation.
  • The anchor coordinates and dimensions of the accessed region (the "footprint").
  • A bitmask or boolean flag indicating whether the queried region is fully covered or resident.

Because this calculation takes place inside the shader pipeline, it inherently accounts for complex projection matrices, surface curvature, viewing angles, and anisotropic filter footprints that are impossible to predict accurately on the CPU.

The Challenge of Traditional Texture Streaming

Modern games frequently use dozens of gigabytes of high-resolution textures. Storing all mip levels in VRAM simultaneously is impractical. Traditionally, engines stream textures using CPU-side heuristics, estimating required mip levels based on distance from the camera, object bounding boxes, or rough screen-space projections.

These CPU-based heuristics suffer from major inefficiencies:

  • Over-allocation: To prevent visible texture blur or popping, engines conservatively stream higher mip levels for an entire mesh, even if only a tiny fraction of the surface is visible or unoccluded.
  • Under-allocation and Popping: Sudden camera movements or sharp glancing angles with anisotropic filtering can cause incorrect estimates, leading to delayed loading and noticeable visual artifacts.
  • Coarse Granularity: Objects must generally be loaded as complete mip chains rather than just the visible subsets of tiles.

How Image Footprint Querying Powers Feedback-Driven Streaming

Feedback-driven texture streaming solves these issues by shifting visibility and LOD determination directly to the GPU. Image footprint querying is the core mechanism that makes this process accurate and lightweight.

1. Real-Time Mip and Tile Identification

During an initial pre-pass (such as a depth pre-pass, visibility buffer pass, or a downsampled analysis pass), shaders run footprint queries on surfaces using their actual UV coordinates and screen-space gradients. Instead of loading the full texture data, the query reveals exactly which mip levels and spatial sub-regions (tiles) are visible to the rasterizer.

2. Writing to a Feedback Buffer

The footprint results are packed into a storage buffer (SSBO) or an append buffer using atomic operations or a compact render target. This generates a definitive list of required virtual texture pages for the current frame. Because the query accounts for anisotropic footprints, pixels viewed at steep glancing angles accurately request higher resolution in only the specific coordinate axes required.

3. Integration with Vulkan Sparse Resources

Vulkan provides native support for partially resident textures through sparse binding (VK_BUFFER_CREATE_SPARSE_BINDING_BIT and sparse image features). Footprint querying maps directly to these sparse tiles:

  • The streaming engine reads the GPU feedback buffer.
  • The engine identifies missing pages (tiles that are needed but not currently resident in VRAM).
  • Background I/O threads load the requested compressed tiles from disk or system memory.
  • Vulkan updates the sparse memory bindings on the image without reallocating or rebinding the entire texture.

4. Bandwidth and Memory Conservation

By using footprint queries, the GPU only requests the exact tiles that contribute to final pixels. Surfaces that are occluded, face away from the camera, or are clamped due to distance do not trigger memory requests. This drastically cuts peak VRAM consumption, reduces PCIe transfer overhead, and prevents the frame drops associated with streaming unneeded high-resolution asset data.
