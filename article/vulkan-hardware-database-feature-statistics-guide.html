Vulkan Hardware Database Feature Statistics Guide

This guide explains how graphics programmers can leverage the Vulkan Hardware Database to query global hardware feature support, evaluate cross-vendor GPU capabilities, and analyze implementation statistics. By utilizing this platform, developers can make data-driven architectural decisions regarding minimum Vulkan version targets, hardware tiering, optional extensions, and rendering engine fallback pathways.

Accessing the Global Database

The Vulkan Hardware Database (hosted at gpuinfo.org) aggregates device reports submitted by developers and users worldwide via the Vulkan Hardware Capability Viewer tool. It provides a comprehensive picture of active hardware configurations across operating systems (Windows, Linux, Android) and hardware vendors (NVIDIA, AMD, Intel, Qualcomm, ARM, and Apple via MoltenVK).

To begin querying global data, navigate to the main Vulkan section of the site. The platform organizes data into individual device submissions, broad platform overviews, and aggregated capability matrices.

Querying Feature Support Lists

To evaluate whether a particular feature is viable for production code, use the feature and extension aggregation views:

  1. Extensions List: Navigate to the "Extensions" tab. This view lists all Khronos (KHR), multi-vendor (EXT), and vendor-specific (NV, AMD, INTEL) extensions. Clicking any extension reveals its overall adoption percentage and a breakdown of which driver versions and devices support it.
  2. Features Matrix: Open the "Features" tab to view specific fields of core structs like VkPhysicalDeviceFeatures, VkPhysicalDeviceVulkan11Features, VkPhysicalDeviceVulkan12Features, and VkPhysicalDeviceVulkan13Features. This allows you to check support for specific flags, such as samplerAnisotropy, descriptorIndexing, or meshShaderQueries.
  3. Format Properties: Use the "Formats" section to inspect support flags for various VkFormat values (e.g., linear tiling, optimal tiling, and buffer feature flags) across different hardware targets.

Using the Advanced Coverage Query Tool

Graphics developers often need to check whether a combination of multiple features and extensions is supported simultaneously on target hardware. The database provides a dedicated search and coverage tool for this purpose:

  1. Open the Reports & Search section and select the Coverage or Database Search tool.
  2. Define your criteria by selecting target platforms (e.g., Windows and Android) and the minimum Vulkan API version.
  3. Add specific required extensions (e.g., VK_KHR_dynamic_rendering, VK_KHR_synchronization2).
  4. Add specific hardware limits (e.g., maxPushConstantsSize >= 256, maxComputeWorkGroupInvocations >= 1024).
  5. Run the query. The system will calculate the percentage of submitted devices that satisfy all criteria concurrently, highlighting the market segment your engine will reach.

Programmatic Access and Automation

For teams requiring automated checks or integration into continuous integration (CI) workflows, the database provides machine-readable endpoints:

  • JSON Dumps: Aggregated and individual device data can be exported as structured JSON files for custom analysis or data pipeline parsing.
  • Database API: You can query the database directly using HTTP endpoints provided by the platform to programmatically fetch the latest reports for specific GPUs or API versions.

Applying Statistics to Engine Design

When reviewing results from the database, apply the following practices:

  • Establish Minimum Hardware Tiers: Use the coverage percentages to set your hard minimum spec. If an extension sits at 95% global availability, treat the remaining 5% as a candidate for a software fallback or an exclusion from your minimum system requirements.
  • Detect Vendor-Specific Behaviors: Filter search results by vendor to anticipate implementation differences, particularly concerning physical device memory properties and alignment limits (such as minUniformBufferOffsetAlignment).
  • Cross-Reference With Platform Context: Account for client sample bias. Submissions from desktop Linux and Windows platforms represent a different demographic than mobile Android devices. Always filter by OS and device type (desktop discrete vs. mobile integrated) when scoping target platforms.
