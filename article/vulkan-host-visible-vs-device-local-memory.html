Vulkan Host-Visible vs Device-Local Memory

In Vulkan, managing memory explicitly is essential for achieving optimal rendering and compute performance. Host-visible memory allows the CPU to directly map, read, and write data, making it suitable for dynamic updates and staging. Conversely, device-local memory resides directly on or near the GPU, providing the highest possible bandwidth and lowest latency for shaders and render pipelines. This article explains the architectural differences, performance characteristics, and primary use cases for both memory types.

Understanding Vulkan Memory Types

Vulkan does not hide hardware architecture behind automatic allocations. Instead, it exposes physical memory through heaps and property flags. When an application queries physical device memory properties via vkGetPhysicalDeviceMemoryProperties, Vulkan returns several memory types tailored to different hardware setups (discrete GPUs, integrated GPUs, and unified memory architectures).

The two most fundamental property flags are:

  • VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT
  • VK_MEMORY_PROPERTY_DEVICE_LOCAL_BIT

Host-Visible Memory

Host-visible memory is accessible directly by the CPU (the "host"). To transfer data to this memory, the application maps the allocation into the CPU's virtual address space using vkMapMemory.

  • CPU Access: Direct write and read operations are supported via standard pointers (e.g., memcpy).
  • Cache Management: Host-visible memory is often paired with VK_MEMORY_PROPERTY_HOST_COHERENT_BIT, which guarantees that writes from the CPU are automatically visible to the GPU without manual cache flushing. If non-coherent, the application must explicitly call vkFlushMappedMemoryRanges after writing and vkInvalidateMappedMemoryRanges before reading.
  • Performance Profile: On discrete GPUs, host-visible memory typically resides in system RAM or traverses the PCIe bus. As a result, reading or writing from GPU shaders is significantly slower compared to dedicated VRAM.
  • Primary Use Cases: Staging buffers for asset uploading, dynamic uniform buffers that update every frame, and transferring compute results back to the CPU.

Device-Local Memory

Device-local memory is physically optimized for execution on the GPU (the "device"). On a discrete graphics card, this corresponds to high-bandwidth VRAM (such as GDDR6 or HBM).

  • GPU Performance: Provides the maximum possible memory bandwidth and minimal latency, allowing thousands of shader cores to sample textures and process vertices concurrently.
  • CPU Access: By default, standard device-local memory cannot be mapped or directly accessed by the CPU. The CPU cannot write to it using a standard memory pointer.
  • Primary Use Cases: Long-lived GPU resources, including render targets, depth-stencil attachments, static mesh vertex/index buffers, and textures.

Key Differences

Feature Host-Visible Memory Device-Local Memory
CPU Access Yes (via vkMapMemory) No (typically inaccessible directly)
GPU Bandwidth Low to Moderate (limited by PCIe) Maximum available on the GPU
Primary Location System RAM or mapped PCIe apertures Dedicated GPU VRAM / On-chip memory
Optimal For Data staging, per-frame CPU data uploads Shaders, textures, render targets

The Staging Buffer Pattern

Because the CPU cannot directly write to device-local memory, applications use a staging buffer pattern to load assets into the GPU:

  1. Create a temporary buffer in host-visible memory (the staging buffer).
  2. Map the buffer and copy the raw asset data (such as texture pixels or vertex arrays) from the CPU into it.
  3. Create the permanent resource (such as a VkImage or vertex VkBuffer) in device-local memory.
  4. Record a GPU transfer command (vkCmdCopyBuffer or vkCmdCopyBufferToImage) to transfer the data across the bus from the staging buffer to the device-local resource.
  5. Submit the command buffer to a transfer or graphics queue, synchronize using a fence or semaphore, and destroy or reuse the staging buffer.

The Hybrid Case: Device-Local and Host-Visible

Modern systems with Resizable BAR (Base Address Register) or AMD Smart Access Memory allow a portion—or the entirety—of dedicated VRAM to be exposed to the CPU. In Vulkan, this appears as a single memory type possessing both VK_MEMORY_PROPERTY_DEVICE_LOCAL_BIT and VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT.

When this memory type is available, the CPU can write directly into high-speed VRAM, bypassing the need for an intermediate staging buffer for dynamic resources like frequently updated transform matrices or particle data.
