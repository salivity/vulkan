Linear vs Optimal Tiling in Vulkan

In the Vulkan API, image layout in memory is governed by image tiling, primarily divided into linear tiling and optimal tiling. This article provides a comprehensive overview of the fundamental differences between VK_IMAGE_TILING_LINEAR and VK_IMAGE_TILING_OPTIMAL, examining how each layout organizes memory, affects hardware performance, impacts CPU accessibility, and dictates common graphics development workflows.

Memory Organization

  • Linear Tiling (VK_IMAGE_TILING_LINEAR): Memory is stored in a strict row-major order, exactly like a standard C-style 2D array. Pixels in a row are placed sequentially in memory, with an optional row pitch (stride) padding the end of each row to satisfy alignment requirements.
  • Optimal Tiling (VK_IMAGE_TILING_OPTIMAL): Memory is arranged in an implementation-dependent, proprietary format determined by the GPU hardware vendor. GPUs typically arrange optimal memory in 2D tiles, Morton order (Z-order curves), or swizzled patterns. This ensures that texels that are spatially close in 2D space are also contiguous or close in physical memory.

Performance and Cache Locality

  • Linear Tiling: Highly inefficient for GPU sampling and rendering operations. Because the layout spans wide rows, fetching neighboring pixels vertically requires jumping large memory offsets, resulting in frequent cache misses during texture filtering, blending, or multi-sample lookups.
  • Optimal Tiling: Maximizes GPU cache efficiency. Spatial locality minimizes memory bandwidth consumption when accessing neighboring texels along both the X and Y axes, making it essential for high-performance rendering, compute shader sampling, and framebuffers.

CPU Accessibility and Host Mapping

  • Linear Tiling: The memory layout is predictable and standardized, allowing the CPU to directly map and write to the image memory via vkMapMemory. Because the host can compute exact byte offsets (offset = y * rowPitch + x * texelSize), linear images can be populated directly by the host without an intermediate conversion step.
  • Optimal Tiling: The layout is opaque to the host application. Because the memory interleaving scheme is vendor-specific and hidden, the CPU cannot directly write meaningful texel data into optimal memory.

API Capabilities and Limitations

  • Linear Tiling: Severely constrained by GPU drivers. Most hardware platforms do not support linear tiling for common operations such as render target attachments, depth-stencil testing, or standard texture sampling. Its use is predominantly restricted to simple transfer sources or readback operations.
  • Optimal Tiling: Fully featured. It supports the entire spectrum of GPU operations, including texture sampling, storage images, attachment targets, multisampling, and blitting.

Standard Vulkan Workflow

Because optimal tiling provides superior performance but prevents direct CPU writes, Vulkan applications standardly use a transfer mechanism:

  1. Data is loaded from disk into a host-visible linear resource (typically a VkBuffer or occasionally a linear VkImage).
  2. The destination VkImage is created with VK_IMAGE_TILING_OPTIMAL in device-local (VRAM) memory.
  3. A command buffer records a copy operation, such as vkCmdCopyBufferToImage.
  4. The GPU’s hardware copy engine rearranges the linear byte stream into the vendor-specific optimal tiled layout.
