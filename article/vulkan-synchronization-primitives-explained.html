Vulkan Synchronization Primitives Explained

Vulkan provides explicit low-level control over the GPU, requiring developers to manually manage execution order and memory access dependencies. This article outlines the primary synchronization primitives in Vulkan—fences, semaphores, pipeline barriers, and events—detailing how each primitive operates, their operational scope across the CPU and GPU, and their ideal use cases in rendering and compute workflows.

Fences (VkFence)

Fences synchronize work between the GPU and the CPU (host). A fence is submitted alongside commands to a queue and is signaled by the GPU once those commands complete execution. The CPU can then query the fence status or block its execution using vkWaitForFences until the GPU finishes the work.

  • Scope: GPU-to-CPU.
  • Common Use Case: Frame pacing, such as preventing the CPU from overwriting dynamic uniform buffers or command buffers that the GPU is currently reading.

Semaphores (VkSemaphore)

Semaphores coordinate execution dependencies across GPU queue submissions. Unlike fences, semaphores do not stall the CPU; they operate strictly on the device to control when a queue begins processing a specific batch of work. Vulkan supports two types of semaphores:

  • Binary Semaphores: Exist in either an unsignaled or signaled state. When signaled by a queue submission, a waiting submission resets the state to unsignaled and begins execution. They are primarily used to orchestrate swapchain operations (e.g., waiting for an image to be acquired before rendering, and waiting for rendering to complete before presentation).
  • Timeline Semaphores: Use a monotonically increasing 64-bit integer counter rather than a binary state. Submissions can wait for or signal specific values. Because timeline semaphores can also be signaled and waited on from the host, they provide a flexible, unified primitive for complex multi-queue and multi-threaded synchronization.

Pipeline Barriers (vkCmdPipelineBarrier)

Pipeline barriers provide fine-grained synchronization inside command buffers. Recorded directly into a command stream, a barrier enforces execution and memory dependencies between commands executed within the same queue, or across different queues via queue family ownership transfers.

A pipeline barrier defines:

  • Execution Dependencies: Specifies which pipeline stages must complete (srcStageMask) before subsequent stages can begin (dstStageMask).
  • Memory Dependencies: Ensures that memory writes from previous stages are made visible to subsequent read operations using access masks (srcAccessMask and dstAccessMask).
  • Image Layout Transitions: Transitions an image from one layout (e.g., VK_IMAGE_LAYOUT_COLOR_ATTACHMENT_OPTIMAL) to another (e.g., VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL).

With Vulkan 1.3 and the VK_KHR_synchronization2 extension, barriers use an updated API (vkCmdPipelineBarrier2) that streamlines flags and clarifies stage and access mask definitions.

Events (VkEvent)

Events provide fine-grained, non-blocking synchronization similar to pipeline barriers, but split into two distinct actions: signaling and waiting. An event can be signaled on the GPU (vkCmdSetEvent) or CPU (vkSetEvent), and subsequently waited upon on the GPU (vkCmdWaitEvents) or checked on the CPU (vkGetEventStatus).

  • Scope: Intra-queue, inter-queue (on some implementations), and CPU-to-GPU.
  • Common Use Case: Overlapping independent GPU work within a single command buffer. By placing vkCmdSetEvent after an early task and delaying vkCmdWaitEvents until right before the dependent task, the GPU can run other unrelated work in the intervening space without stalling the pipeline.
