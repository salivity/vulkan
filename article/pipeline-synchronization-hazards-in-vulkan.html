Pipeline Synchronization Hazards in Vulkan

This article explains the underlying causes of pipeline synchronization hazards—specifically Read-After-Write (RAW), Write-After-Read (WAR), and Write-After-Write (WAW)—within the Vulkan graphics and compute API. Because Vulkan is an explicit API that provides minimal automatic driver intervention, the developer is directly responsible for managing execution order and memory access. Readers will learn how the GPU's asynchronous execution architecture, multiple pipeline stages, and decentralized memory caching systems inherently cause these hazards unless explicit synchronization mechanisms are employed.

The Explicit Synchronization Model

In legacy APIs like OpenGL or Direct3D 11, graphics drivers invisibly track resource dependencies and inject memory flushes and execution stalls to ensure data integrity. Vulkan removes this overhead, operating on an explicit execution model.

When commands are submitted to a Vulkan queue via command buffers, the GPU does not process them strictly sequentially from start to finish. Instead, commands are launched asynchronously. The GPU will overlap operations whenever hardware resources are available, unless the developer explicitly tells it to wait.

Asynchronous Pipeline Stages

The GPU pipeline is divided into multiple stages—such as transfer, vertex shading, fragment shading, and compute shading. Different stages run on distinct functional units within the hardware.

Because these stages operate independently:

  • An operation dispatched later in a command buffer may reach its execution stage before an earlier command finishes its work.
  • Two separate dispatches or draw calls can execute their respective stages concurrently.

Without explicit barriers, there is no guarantee of execution order between operations in different pipeline stages, even if they are submitted sequentially in the same command buffer.

GPU Memory Architectures and Caching

Execution order is only half of the problem; memory visibility is the other. Modern GPUs utilize hierarchical, non-coherent caches distributed across compute units, texture processing clusters, and memory controllers.

When a pipeline stage writes data:

  1. The data initially resides in a local cache (e.g., an L1 cache or write buffer) and is not instantly written back to shared memory or global L2 cache.
  2. Other pipeline stages reading from different hardware units reference their own local caches, which may hold stale data.

In Vulkan, writing data does not automatically make it available (flushed from the writer's local cache), nor does reading data automatically make it visible (invalidating the reader's cache to pull fresh data).

How Hazards Occur

The combination of out-of-order execution stages and non-coherent caches causes classic pipeline hazards:

1. Read-After-Write (RAW) Hazards

A RAW hazard occurs when a command needs to read data written by an earlier command, but the read occurs before the write is complete, or before the written data is made visible.

  • Cause: A compute shader writes results to a storage buffer, and an immediately following draw call reads that buffer as a vertex buffer. If no synchronization is defined, the vertex fetch stage may run before the compute shader completes, reading incomplete data. Even if the compute shader finishes, the vertex hardware might read stale values if the compute unit's write cache was not flushed.

2. Write-After-Read (WAR) Hazards

A WAR hazard happens when an operation writes to a memory location before a previous operation has finished reading from it.

  • Cause: A fragment shader is currently sampling from a texture. A subsequent transfer command (such as vkCmdCopyBufferToImage) is submitted to update that same texture for a future frame. Because transfer operations can execute faster than heavy fragment workloads, the transfer might overwrite the texture memory while the fragment shader is still actively reading it, resulting in visual artifacts or tearing.

3. Write-After-Write (WAW) Hazards

A WAW hazard occurs when two commands write to the same memory location, and the operations complete out of order.

  • Cause: Two consecutive compute dispatches write to the same storage image. If the second dispatch completes faster than the first, the first dispatch’s output will overwrite the second’s. The final state of the memory becomes non-deterministic.

Preventing Hazards in Vulkan

To prevent these hazards, developers must coordinate both execution flow and memory domains using Vulkan's synchronization primitives:

  • Execution Dependencies: Specify which pipeline stages (srcStageMask) must complete before other stages (dstStageMask) are permitted to start. This prevents operations from overlapping in time.
  • Memory Dependencies: Specify access types (srcAccessMask and dstAccessMask) to govern cache behavior. A source access mask flushes written data to make it available to the GPU, while a destination access mask invalidates reader caches to ensure fresh data is fetched.

These dependencies are deployed through pipeline barriers (vkCmdPipelineBarrier), subpass dependencies within render passes, or timeline semaphores across queues, providing the necessary boundaries that eliminate pipeline synchronization hazards.
