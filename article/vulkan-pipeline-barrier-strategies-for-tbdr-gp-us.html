Vulkan Pipeline Barrier Strategies for TBDR GPUs

This article explores the fundamentals of Tile-Based Deferred Rendering (TBDR) architectures and how their unique hardware design dictates synchronization choices in the Vulkan API. You will learn how TBDR differs from traditional immediate-mode rendering, why naive execution barriers can devastate mobile GPU performance, and how to effectively structure render passes, subpass dependencies, and pipeline barriers to maximize on-chip cache utilization.

What is Tile-Based Deferred Rendering (TBDR)?

Tile-Based Deferred Rendering is a GPU architecture primarily found in mobile and low-power devices, such as those powered by ARM Mali, Qualcomm Adreno, Imagination PowerVR, and Apple Silicon. Unlike Immediate Mode Rendering (IMR) common on desktop GPUs—which processes geometry and shades pixels directly to external VRAM—TBDR breaks the screen into small, discrete grids called tiles (typically 16x16 or 32x32 pixels).

TBDR operates in two distinct phases:

  1. The Binning (Geometry) Phase: The GPU processes all vertex shaders for a scene, determines which primitives intersect which tiles, and builds a per-tile list of primitives in memory.
  2. The Tiling (Rasterization and Shading) Phase: The GPU processes the frame tile by tile. The entire color, depth, and stencil data for a single tile resides in ultra-fast, on-chip SRAM cache. The GPU performs Hidden Surface Removal (HSR) upfront, discarding occluded fragments before fragment shaders ever run, and only writes the final resolved pixels back to main system memory (DRAM) once the entire tile is complete.

Because off-chip memory access is the single largest consumer of energy and bandwidth on mobile hardware, TBDR dramatically reduces power consumption by keeping intermediate pixel operations inside local tile memory.

How TBDR Influences Vulkan Pipeline Barrier Strategies

In Vulkan, pipeline barriers (vkCmdPipelineBarrier or vkCmdPipelineBarrier2) synchronize execution and memory access between commands. While IMR architectures generally handle execution barriers with minimal overhead—often just flushing L1/L2 caches or waiting for a pipeline stage to idle—TBDR hardware is highly sensitive to barrier placement.

1. Preventing Mid-Pass Flushes

The most critical rule of TBDR synchronization is avoiding explicit pipeline barriers inside an active render pass. If an application inserts an execution barrier between draw calls that changes resource states or forces memory visibility within a render pass, the hardware may be forced to flush its local tile memory back to main system DRAM and reload it afterward. This stall eliminates the primary bandwidth advantage of TBDR.

2. Utilizing Subpasses Instead of In-Pass Barriers

To perform multipass rendering (such as deferred shading, tone mapping, or ambient occlusion) without leaving tile memory, developers must use Vulkan subpasses (VkSubpassDependency) or dynamic rendering local reads.

Subpass self-dependencies and inter-subpass dependencies allow you to declare read-after-write hazards to the driver. When attachments are consumed in a subsequent subpass via VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL or VK_IMAGE_LAYOUT_GENERAL as an input attachment, TBDR hardware keeps the data in the tile's local SRAM cache. The driver translates these dependencies into internal tile-level synchronization rather than issuing full pipeline flushes to system memory.

3. Optimizing Attachment Load and Store Operations

TBDR architectures rely heavily on VkAttachmentLoadOp and VkAttachmentStoreOp to manage tile cache lifecycles:

  • Use VK_ATTACHMENT_LOAD_OP_CLEAR or VK_ATTACHMENT_LOAD_OP_DONT_CARE whenever you do not need the previous contents of a tile.
  • Use VK_ATTACHMENT_STORE_OP_DONT_CARE for transient data, such as intermediate G-buffer depth, normals, or specular targets that are only consumed during that specific render pass.

Placing a global memory barrier or improper layout transition on a transient image forces it to be written out to DRAM, negating VK_ATTACHMENT_STORE_OP_DONT_CARE and wasting memory bandwidth.

4. Batching Barriers Outside Render Passes

Synchronization between compute dispatches, transfer operations, and graphics passes should always take place outside the bounds of vkCmdBeginRenderPass and vkCmdEndRenderPass.

When transitioning resources:

  • Batch transitions: Consolidate multiple image and buffer memory barriers into a single vkCmdPipelineBarrier2 call before beginning a render pass to allow the hardware to schedule work efficiently.
  • Keep masks precise: Avoid coarse masks like VK_PIPELINE_STAGE_2_ALL_COMMANDS_BIT or broad VK_ACCESS_2_MEMORY_READ_BIT / VK_ACCESS_2_MEMORY_WRITE_BIT combinations. Specifying exact source and destination stages (e.g., VK_PIPELINE_STAGE_2_COLOR_ATTACHMENT_OUTPUT_BIT to VK_PIPELINE_STAGE_2_FRAGMENT_SHADER_BIT) allows TBDR drivers to overlap the binning phase of the next frame with the shading phase of the current frame.
