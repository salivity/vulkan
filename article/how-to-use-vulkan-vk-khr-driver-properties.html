How to Use Vulkan VK_KHR_driver_properties

The VK_KHR_driver_properties extension provides Vulkan applications with a standardized, reliable mechanism to query detailed driver metadata, including the precise driver name, driver identification ID, custom build information, and conformance test suite version. Originally introduced as an extension and later integrated into core Vulkan 1.2, it replaces the ambiguity of legacy vendor-specific version encoding by allowing developers to query a dedicated physical device properties structure. This article explains how the extension works, how to query it via structure chaining, and what specific details it exposes.

Query Mechanism via Structure Chaining

To retrieve driver properties, Vulkan utilizes structure chaining through the pNext pointer of the extended VkPhysicalDeviceProperties2 structure.

  1. Verify Support: Ensure the physical device supports VK_KHR_driver_properties (or core Vulkan 1.2 or later, where the extension features are available under the core name VkPhysicalDeviceDriverProperties).
  2. Initialize Structures: Allocate and initialize an instance of VkPhysicalDeviceDriverPropertiesKHR. Set its sType field to VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_DRIVER_PROPERTIES_KHR and set pNext to NULL.
  3. Chain to Properties Query: Initialize a parent VkPhysicalDeviceProperties2 structure, set its sType to VK_STRUCTURE_TYPE_PHYSICAL_DEVICE_PROPERTIES_2, and assign the pointer of the VkPhysicalDeviceDriverPropertiesKHR structure to the parent's pNext member.
  4. Call the Query Function: Call vkGetPhysicalDeviceProperties2 (or vkGetPhysicalDeviceProperties2KHR). Vulkan traverses the pNext chain and populates the driver properties structure directly.

Fields Populated by the Query

Once the query completes, the VkPhysicalDeviceDriverPropertiesKHR structure contains several key fields:

  • driverID (VkDriverIdKHR): A unique enum value representing the specific driver implementation rather than just the hardware vendor. This allows applications to distinguish between different driver stacks running on identical hardware (for example, distinguishing between AMD's proprietary driver, AMD's open-source AMDGPU-PRO, and the Mesa RADV driver).
  • driverName (array of char): A null-terminated UTF-8 string containing the readable name of the driver (e.g., "NVIDIA", "AMD proprietary driver", or "Mesa RADV").
  • driverInfo (array of char): A null-terminated UTF-8 string containing supplementary driver build and revision details, often including internal build numbers, branch identifiers, or release dates provided by the driver vendor.
  • conformanceVersion (VkConformanceVersionKHR): A structure containing major, minor, subminor, and patch fields. This indicates the precise version of the official Vulkan Conformance Test Suite (CTS) that the driver was certified against.

Advantages Over Legacy Queries

Prior to VK_KHR_driver_properties, developers had to rely solely on the driverVersion field in VkPhysicalDeviceProperties. Because the format of driverVersion was vendor-defined—NVIDIA, AMD, and Intel each packed version numbers differently into the 32-bit integer—parsing it required vendor-specific bitmasks and guessing. VK_KHR_driver_properties standardizes driver identification across all conformant Vulkan implementations, making it simple to log system diagnostics, gather telemetry, and apply targeted workarounds for driver-specific bugs.
