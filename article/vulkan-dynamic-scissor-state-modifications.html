Vulkan Dynamic Scissor State Modifications

In the Vulkan graphics API, dynamic scissor state modifications allow developers to define and update the scissor rectangle—the area of the framebuffer where rendering occurs—during active command buffer recording without rebuilding the graphics pipeline. Permissible modifications depend on how the pipeline was created, whether extended dynamic state features are enabled, and adherence to specific command ordering rules. This guide outlines the exact dynamic scissor modifications permitted during command buffer recording, the required pipeline states, and the commands used to apply them.

Pipeline Requirements for Dynamic Scissor State

To modify scissor rectangles dynamically, the active pipeline must be configured to treat scissor states as dynamic during pipeline creation:

  • VK_DYNAMIC_STATE_SCISSOR: Must be included in the pDynamicStates array of VkPipelineDynamicStateCreateInfo. This enables updating the scissor rectangle dimensions and offsets dynamically, while the total number of scissors remains fixed to the pipeline's viewport count.
  • VK_DYNAMIC_STATE_SCISSOR_WITH_COUNT: Available in Vulkan 1.3 or via the VK_EXT_extended_dynamic_state extension. This dynamic state allows you to modify both the scissor rectangles and the dynamic count of active scissors simultaneously.

If a pipeline does not declare scissor state as dynamic, any calls modifying the scissor state will have no effect on rendering commands executed with that pipeline.

Permissible Scissor Commands and Placement

During command buffer recording (in the recording state after vkBeginCommandBuffer), the following commands are permissible:

  • vkCmdSetScissor: Modifies the scissor rectangles. It can be invoked both inside and outside of active render pass instances.
  • vkCmdSetScissorWithCount: Modifies both the total number of scissor rectangles and their corresponding properties. Can also be invoked inside or outside render pass instances.

Dynamic scissor state changes are permissible at any point prior to a draw call (such as vkCmdDraw or vkCmdDrawIndexed). A valid scissor state must be bound before any draw command executes with a pipeline utilizing dynamic scissors.

Permissible Parameter Modifications

When invoking vkCmdSetScissor or vkCmdSetScissorWithCount, the following parameter adjustments are permitted:

  1. Rectangle Dimensions and Offsets:
    • The offset (x, y) can be modified to shift the starting position. Negative offsets are not valid for static coordinates, but must fall within valid framebuffer boundaries.
    • The extent (width, height) can be scaled or resized. The sum of offset.x + extent.width and offset.y + extent.height should not exceed the physical limits of the implementation's maximum viewport dimensions (maxViewportDimensions).
  2. Partial Array Updates (firstScissor):
    • When using multi-viewport configurations, vkCmdSetScissor allows modifying a subset of the scissor array using the firstScissor parameter. You can update specific scissor indices without modifying the entire array.
  3. Dynamic Scissor Count:
    • If VK_DYNAMIC_STATE_SCISSOR_WITH_COUNT is used, the scissor count can be dynamically increased or decreased per draw command, provided the count does not exceed the implementation's maxViewports limit.

State Persistence and Command Buffer Boundaries

Dynamic scissor state modifications obey specific lifetime and persistence rules:

  • Persistence Across Draw Calls: Once a dynamic scissor command is recorded, its state persists across subsequent pipeline binds and draw calls within the same command buffer, provided the newly bound pipelines also declare the scissor state as dynamic.
  • Primary and Secondary Command Buffers: Dynamic scissor state set in a primary command buffer does not inherit down into secondary command buffers by default unless dynamic state inheritance extensions (VK_NV_inherited_viewport_scissor or Vulkan 1.3 dynamic state inheritance) are specifically configured. Conversely, state set inside a secondary command buffer does not propagate back to the calling primary command buffer.
