Vulkan Multithreaded Draw Call Generation

Vulkan achieves high-performance graphics processing by decoupling command recording from command execution, enabling CPU multithreading that was impossible in legacy APIs. By utilizing isolated command pools and recording commands into independent command buffers across multiple threads, Vulkan allows applications to generate thousands of draw calls simultaneously without CPU-bound driver bottlenecks. These recorded buffers are later aggregated and submitted to a GPU queue in a single, lightweight operation.

The Limitation of Legacy APIs

Traditional APIs like OpenGL and DirectX 11 rely on a monolithic, global state machine tied to a single rendering context. In these architectures, issuing a draw call requires immediate state validation and translation by the driver on the thread hosting the context. Multithreading attempts in such systems often introduce significant synchronization overhead, driver locks, and minimal performance scaling because the underlying driver must serialize commands before sending them to hardware.

Independent Command Pools and Buffers

Vulkan removes global state by shifting synchronization responsibilities entirely to the application. Multithreaded command recording centers around two core Vulkan objects:

  1. VkCommandPool: Memory pools from which command buffers are allocated. Command pools are externally synchronized, meaning they cannot be accessed concurrently by multiple threads. To achieve thread safety without locks, each worker thread is assigned its own dedicated VkCommandPool.
  2. VkCommandBuffer: Structures allocated from pools that store recorded commands. Because each thread allocates and writes to its own command buffer using its dedicated pool, multiple threads can execute functions like vkCmdBindPipeline, vkCmdBindDescriptorSets, and vkCmdDraw concurrently without mutex contention or driver-level stalls.

Primary and Secondary Command Buffers

Vulkan divides command buffers into two execution tiers: primary and secondary. This distinction is what makes fine-grained multithreaded rendering practical within a single render pass.

  • Primary Command Buffers (VK_COMMAND_BUFFER_LEVEL_PRIMARY): These can be submitted directly to a VkQueue for GPU execution, and they can execute secondary command buffers.
  • Secondary Command Buffers (VK_COMMAND_BUFFER_LEVEL_SECONDARY): These cannot be directly submitted to a queue. Instead, they inherit state from a primary command buffer and are recorded independently by worker threads.

During a complex scene render, the main thread begins a primary command buffer and defines the render pass. Worker threads simultaneously record draw calls for distinct scene components (such as static geometry, characters, and UI elements) into separate secondary command buffers. Once worker threads complete recording, the primary command buffer references them using vkCmdExecuteCommands.

State Isolation and Validation

In Vulkan, pipeline state objects (VkPipeline) bake all graphics state—such as blend modes, depth testing, and vertex layouts—into immutable GPU-ready objects before runtime. Because state is immutable and encapsulated within pipelines rather than stored in a shared context, worker threads can bind different pipelines and descriptor sets in parallel without corrupting one another's state.

Queue Submission

Once all threads finish recording, their command buffers represent complete, static GPU instruction streams. The main thread collects these buffers and submits them to a VkQueue using vkQueueSubmit.

While queue submission is synchronized and must be handled carefully across threads, the CPU overhead of vkQueueSubmit is negligible compared to the cost of generating draw calls. By offloading command generation, descriptor binding, and draw call emission to worker threads, Vulkan fully utilizes modern multi-core CPUs to keep the GPU consistently saturated.
