Vulkan Depth Bounds Testing in Deferred Lighting

Depth bounds testing is a powerful hardware-accelerated feature in Vulkan that dramatically improves the performance of deferred lighting pipelines. In deferred rendering, calculating illumination from localized lights often results in wasted GPU cycles on pixels outside a light’s effective range. By establishing a restricted depth interval for each light source, depth bounds testing discards fragments that fall outside this slice before the fragment shader executes, significantly reducing arithmetic workload, memory bandwidth consumption, and overall render time.

The Challenge of Light Culling in Deferred Rendering

In a standard deferred lighting pass, lights are typically rendered as 3D bounding geometry, such as spheres or cones, or as screen-aligned quads mapped to the screen-space bounding box of the light. While the G-buffer contains the precise world or view-space positions via its depth buffer, rasterizing these light volumes causes pixels to invoke the lighting fragment shader even if the surface geometry is far in front of or behind the actual volume.

Without targeted culling, the GPU evaluates expensive lighting equations—sampling multiple G-buffer textures (albedo, normals, roughness) and performing complex BRDF math—for fragments where the light's contribution is zero. Traditional mitigations, such as stencil-based volume culling, require multi-pass rasterization (e.g., rendering back faces then front faces to build a stencil mask), which increases draw call overhead and bandwidth pressure.

How Depth Bounds Testing Works

Depth bounds testing allows the GPU to test the existing depth buffer value of a fragment against two explicitly defined boundaries: a minimum depth (minDepthBounds) and a maximum depth (maxDepthBounds). If the depth value stored in the depth attachment falls outside this defined [min, max] interval, the fragment is discarded.

Crucially, this test occurs alongside or immediately after the standard early depth/stencil test, well before the execution of the fragment shader.

Implementing Depth Bounds Testing in Vulkan

Vulkan natively supports depth bounds testing as an optional core feature. To use it in a deferred lighting pipeline, developers perform the following steps:

  1. Feature Enablement: Query and enable depthBounds in VkPhysicalDeviceFeatures during logical device creation.

  2. Pipeline State Configuration: Set depthBoundsTestEnable = VK_TRUE inside VkPipelineDepthStencilStateCreateInfo when assembling the lighting pipeline. Add VK_DYNAMIC_STATE_DEPTH_BOUNDS to the pipeline's dynamic states to avoid baking static ranges into the pipeline object.

  3. Per-Light Calculation: For each light volume, calculate the minimum and maximum Z coordinates in view space, then project these values into normalized device coordinates (NDC), mapped to the [0.0, 1.0] depth range.

  4. Dynamic State Updates: Prior to drawing each light's bounding geometry or screen-aligned scissor rect, invoke:

    vkCmdSetDepthBounds(commandBuffer, minDepth, maxDepth);

  5. Draw Call: Issue the draw call for the light volume.

Direct Optimization Benefits

Elimination of Redundant Shader Invocations

By restricting evaluation to the depth interval spanning the light volume, geometry situated in the foreground or background is culled early. The fragment shader only runs for surfaces that physically intersect the depth range of the light, cutting down fragment shader invocations significantly in scenes with dense geometric depth layering.

Single-Pass Light Volume Evaluation

Traditional stencil culling approaches require two passes per light (or double-sided stencil state tracking) to mark the volume's entry and exit points before running the shading pass. Depth bounds testing replaces or complements this by providing precise depth culling in a single pass, eliminating extra state transitions and draw calls.

Reduced G-Buffer Read Bandwidth

Deferred lighting is heavily memory bandwidth bound due to multiple texture samples per fragment. Discarding fragments early via depth bounds prevents the texture units from fetching material properties from the G-buffer attachments for non-contributing surfaces, preserving memory bandwidth for active lighting calculations.
