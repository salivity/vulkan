Vulkan Push Constants Size Limits Explained

Push constants offer the lowest-latency method to pass small amounts of uniform data to shaders in Vulkan without the overhead of descriptor sets or memory allocation. However, because they are backed directly by fast on-chip registers, their capacity is strictly limited by hardware capabilities and driver implementations. This guide outlines the minimum size guarantees defined by the Vulkan specification, real-world hardware limits across major GPU vendors, and best practices for managing this constrained memory pool.

The Vulkan Specification Minimum

The Vulkan core specification mandates that every compliant device must support a minimum push constant buffer size of 128 bytes. This limit is queried via the VkPhysicalDeviceLimits::maxPushConstantsSize field.

In practical terms, 128 bytes provides enough space for:

  • Two 4x4 matrices of 32-bit floats (each matrix consumes 64 bytes).
  • One 4x4 matrix (64 bytes) alongside a collection of 16-bit or 32-bit scalar values, vectors, and dynamic indices.
  • Thirty-two 32-bit scalar values (floats, integers, or booleans).

Because 128 bytes is the only guaranteed baseline across all Vulkan-compliant implementations, cross-platform applications targeting broad compatibility must treat this value as a hard ceiling.

Real-World Hardware Variance

While the specification dictates a 128-byte minimum, actual hardware capacity varies between mobile and desktop architectures:

  • Mobile GPUs (ARM Mali, Qualcomm Adreno, PowerVR): Almost universally restrict maxPushConstantsSize to the minimum 128 bytes. Mobile hardware prioritizes silicon area and thermal efficiency, leaving little dedicated register space for large immediate state data.
  • NVIDIA Desktop GPUs: Modern architectures (such as Turing, Ampere, and Ada Lovelace) typically expose 256 bytes. This allows developers to fit up to four 4x4 matrices or additional per-draw transform data directly into the push constant block.
  • AMD Desktop GPUs: Modern RDNA and older GCN architectures often report 128 to 256 bytes, depending on driver version and platform architecture. While the underlying hardware command processor can manage larger parameter buffers, the driver often clamps the exposed limit to keep execution predictable and prevent register spilling.
  • Intel Integrated and Discrete GPUs: Typically provide 128 bytes on older integrated hardware, with newer discrete architectures (such as Arc / Alchemist) sometimes extending this to 256 bytes.

Shader Stage Sharing and Layout Constraints

The maxPushConstantsSize limit applies to the entire pipeline layout, not to individual shader stages. If a pipeline layout declares push constant ranges across multiple stages (such as vertex, fragment, and compute), all ranges draw from the same shared pool of memory:

  • Overlapping Ranges: Different stages can access the same offsets within the push constant block (for example, reading a shared camera matrix at offset 0).
  • Distinct Ranges: If separate data is dedicated to specific stages (such as vertex transforms at offset 0 to 64, and material properties at offset 64 to 128), the cumulative range must fit within the device's maximum size.

Additionally, push constant data must adhere to strict alignment rules. Vulkan requires member offsets to be multiples of 4 bytes, while complex types like vectors and matrices follow standard GLSL std430 layout rules. Poorly packed structures can introduce unexpected padding, quickly exhausting the limited byte budget.

Practical Recommendations

To maximize performance and avoid compatibility failures:

  1. Target 128 Bytes: Design standard rendering paths to fit within a 128-byte footprint to ensure seamless execution on mobile and entry-level hardware.
  2. Use Dynamic Querying: If larger payloads are necessary, query maxPushConstantsSize at initialization and branch rendering logic or fall back to dynamic uniform buffers (UBOs) on devices limited to 128 bytes.
  3. Pack Aggressively: Store booleans as bitmasks, use 16-bit floats or integers where precision permits, and organize struct members by descending size to minimize alignment padding.
