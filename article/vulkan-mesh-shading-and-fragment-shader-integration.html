Vulkan Mesh Shading and Fragment Shader Integration

The mesh shading pipeline in Vulkan fundamentally reorganizes the front-end geometry processing by replacing traditional vertex, tessellation, and geometry stages with compute-like Task and Mesh shaders, while preserving the existing rasterization and fragment shading back-end. This article explains how the outputs generated by Vulkan mesh shaders pass through hardware rasterization to seamlessly interface with standard fragment shaders, detailing data flow, attribute declarations, per-primitive outputs, and pipeline configuration.

The Pipeline Architecture

In the standard Vulkan graphics pipeline, vertex data moves from fixed-function Input Assembly through Vertex Shaders, optional Tessellation, and optional Geometry Shaders before rasterization. The mesh shading extension (VK_EXT_mesh_shader) replaces this sequence with two stages:

  1. Task Shader (Optional): Emits dynamic workgroups of mesh shaders based on high-level culling or level-of-detail tests.
  2. Mesh Shader (Required): Operates as a compute-style workgroup to produce a compact meshlet consisting of vertices and primitive topology indices.

Once the mesh shader completes execution, its output payload is routed directly into the hardware rasterizer. The rasterizer interpolates generated attributes across primitive surfaces and dispatches fragment shader invocations, exactly as it does in the traditional graphics pipeline.

Mesh Shader Output Interface

A mesh shader explicitly defines the maximum number of vertices and primitives it can emit using execution mode qualifiers in GLSL or HLSL:

layout(local_size_x = 32) in;
layout(triangles, max_vertices = 64, max_primitives = 126) out;

Data flows from the mesh shader to the fragment shader via output arrays. The mesh shader writes both per-vertex and per-primitive attributes:

// Per-vertex attributes (interpolated across fragments)
layout(location = 0) out vec3 outWorldPos[];
layout(location = 1) out vec2 outUV[];

// Per-primitive attributes (constant across the primitive)
layout(location = 2) perprimitiveEXT out uint outMaterialIndex[];

The mesh shader specifies the actual count of generated geometry at runtime using the SetMeshOutputsEXT(vertexCount, primitiveCount) function before populating these output arrays and the primitive index buffer (gl_PrimitiveTriangleIndicesEXT[]).

Consuming Attributes in the Fragment Shader

The fragment shader remains largely agnostic of whether geometry originated from a classic vertex shader or a mesh shader. Inputs matching the mesh shader's output locations are declared normally:

// Receives interpolated vertex values
layout(location = 0) in vec3 inWorldPos;
layout(location = 1) in vec2 inUV;

// Receives flat per-primitive values
layout(location = 2) perprimitiveEXT in flat uint inMaterialIndex;

layout(location = 0) out vec4 fragColor;
  • Per-Vertex Interpolation: Attributes marked per-vertex are automatically perspective-interpolated across fragments generated during triangle rasterization.
  • Per-Primitive Inputs: The perprimitiveEXT qualifier allows the fragment shader to read non-interpolated data assigned directly to a specific triangle or line (such as primitive IDs or material indices) without relying on provoking vertex conventions.

Built-in Interfacing and Culling

Built-in variables bridge viewport routing, primitive identification, and layer selection:

  • Positioning: The mesh shader writes to gl_MeshVerticesEXT[i].gl_Position, which defines screen-space coordinates for the rasterizer to clip and project before invoking fragment shaders.
  • Primitive Indices: Mesh shaders can write to gl_MeshPrimitivesEXT[j].gl_PrimitiveID, which exposes gl_PrimitiveID directly inside the fragment shader.
  • Layer and Viewport Routing: Mesh shaders can emit gl_MeshPrimitivesEXT[j].gl_Layer and gl_ViewportIndex, enabling multi-view or cube-map rendering in a single pass without needing a geometry shader.
  • Primitive Culling: Mesh shaders can assign gl_MeshPrimitivesEXT[j].gl_CullPrimitiveEXT = true to drop primitives before rasterization, preventing any associated fragment shader invocations from being scheduled.

Pipeline Creation in Vulkan

To establish this pipeline via the Vulkan API, a VkGraphicsPipelineCreateInfo structure is submitted with shader stages that omit VK_SHADER_STAGE_VERTEX_BIT and instead supply:

  • VK_SHADER_STAGE_MESH_BIT_EXT
  • VK_SHADER_STAGE_TASK_BIT_EXT (optional)
  • VK_SHADER_STAGE_FRAGMENT_BIT

Because the mesh shader computes its own topology and vertex counts, pVertexInputState and pInputAssemblyState can be set to NULL (or point to empty structures). The remaining graphics pipeline states—including rasterization parameters (VkPipelineRasterizationStateCreateInfo), multisampling, depth-stencil tests, and color blending—apply to fragment shading in the exact same manner as in legacy pipelines.
