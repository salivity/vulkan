Vulkan Video Encoding: H.264, H.265, and AV1

Hardware-accelerated video encoding through the Vulkan API enables low-overhead, cross-platform access to dedicated media silicon on modern GPUs. By extending Vulkan’s explicit control model to video processing, developers can encode H.264 (AVC), H.265 (HEVC), and AV1 streams directly within the same graphics and compute context. This article explains the underlying architecture of Vulkan Video, codec-specific extensions, the step-by-step encoding execution pipeline, and how zero-copy integration delivers deterministic performance.

The Vulkan Video Architecture

Unlike software encoding or general-purpose GPU compute (GPGPU) encoding via compute shaders, Vulkan Video interacts directly with fixed-function ASIC processing blocks found on modern hardware, such as Nvidia’s NVENC, AMD’s VCN, and Intel’s Quick Sync.

To maintain consistency with the rest of the API, Vulkan treats video encoding as an execution queue type alongside standard graphics, compute, and transfer queues. The foundation relies on core extensions:

  • VK_KHR_video_queue: Establishes common structures, session definitions, profile queries, and execution patterns for video functionality.
  • VK_KHR_video_encode_queue: Implements the base encode pipeline, defining parameter structures, rate control mechanisms, and output buffer definitions.

Specific codecs are implemented as modular layers on top of this foundation:

  • H.264: Supported via VK_KHR_video_encode_h264, controlling macroblock mappings, slice headers, and SPS/PPS (Sequence/Picture Parameter Sets).
  • H.265: Supported via VK_KHR_video_encode_h265, exposing HEVC coding unit parameters, tiling, and VPS/SPS/PPS generation.
  • AV1: Supported via VK_KHR_video_encode_av1, managing Open Bitstream Units (OBUs), frame headers, tile groups, and CDF (Cumulative Distribution Function) updates.

Core Encoding Pipeline Components

Executing hardware encoding in Vulkan involves several explicit components:

  1. VkVideoProfileInfoKHR: Defines the codec syntax, profile, level, chroma subsampling (typically 4:2:0 YCbCr), and bit depth (such as 8-bit or 10-bit).
  2. VkVideoSessionKHR: Represents the configured state of the video processing unit. It encapsulates codec parameters, reference frame structures, and underlying hardware initialization.
  3. VkVideoSessionParametersKHR: Holds persistent parameter sets (such as SPS/PPS in H.264/H.265 or Sequence Headers in AV1) that define the stream's structural specifications without requiring reinitialization per frame.
  4. Decoded Picture Buffer (DPB): A collection of image resources bound to the video session to store reconstructed reference frames necessary for inter-frame temporal prediction (P-frames and B-frames).

Step-by-Step Encoding Workflow

The hardware encoding sequence follows Vulkan’s command-buffer-driven model:

1. Capability and Parameter Setup

The application queries device limits for the target codec (e.g., maximum supported resolution, GOP patterns, and rate control modes like CBR or VBR) using vkGetPhysicalDeviceVideoCapabilitiesKHR. The VkVideoSessionKHR and corresponding parameters are then instantiated and bound to dedicated device memory pools.

2. Resource Management

The developer provisions the uncompressed input frame (a VkImage), the DPB images for temporal references, and a linear output VkBuffer allocated to receive the compressed elementary bitstream.

3. Command Buffer Recording

Encoding operations are dispatched inside command buffers explicitly tied to a video encode queue family:

  • Session Binding: vkCmdBeginVideoCodingKHR locks the video session and binds the DPB references and target output bitstream buffer.
  • Rate Control and Parameters: Dynamic rate control settings, quality presets, or dynamic parameter updates are applied.
  • Dispatching the Encode: vkCmdEncodeVideoKHR submits the execution command. This struct contains picture-level control information:
    • For H.264/H.265: Target slice modes, reference picture lists (L0/L1), and Quantization Parameter (QP) offsets.
    • For AV1: Primary frame references, filter settings (loop filter, CDEF), and temporal delimiters.
  • Session Termination: vkCmdEndVideoCodingKHR closes the video operation block.

4. Execution and Synchronization

The command buffer is submitted to a VkQueue supporting the VK_QUEUE_VIDEO_ENCODE_BIT_KHR flag. Synchronization is handled using standard Vulkan synchronization primitives:

  • Barriers and Semaphores: A graphics or compute pass renders directly into a frame buffer, an execution barrier transitions the image layout from a color attachment or storage image to VK_IMAGE_LAYOUT_VIDEO_ENCODE_SRC_KHR, and a timeline semaphore signals the video queue to begin execution.
  • Once encoding finishes, a fence or semaphore notifies the host or transfer queue that the bitstream is ready to be parsed, containerized (e.g., into MP4 or WebM), or transmitted over a network.

Zero-Copy Interoperability and Efficiency

The architectural advantage of Vulkan Video encoding is the elimination of cross-API interop and host-memory round-trips. Traditional encoding workflows often render a frame in a graphics API, copy the surface to system memory, and re-upload it to a proprietary vendor SDK (like NVENC or AMF) or require shared handle overhead across disparate drivers.

In Vulkan, rendered 3D frames remain in VRAM throughout the entire lifecycle. The uncompressed output of a rendering or compute pipeline functions directly as the input surface for the encoder. By removing memory duplication and proprietary abstraction layers, hardware encoding via Vulkan reduces CPU usage, lowers latency, and ensures high frame throughput across diverse GPU architectures.
