Hardware-Accelerated Ray Tracing in Vulkan

This article explores how hardware-accelerated ray tracing integrates into the Vulkan API's core pipeline infrastructure. Vulkan incorporates ray tracing primarily through two mechanisms: the dedicated Ray Tracing Pipeline (VK_KHR_ray_tracing_pipeline) and Ray Queries (VK_KHR_ray_query), both supported by Acceleration Structures (VK_KHR_acceleration_structure). By introducing specialized shader stages, dedicated memory management paradigms like the Shader Binding Table, and direct low-level hooks into GPU fixed-function traversal hardware, Vulkan exposes explicit, deterministic control over ray tracing workloads alongside its traditional rasterization and compute workflows.

Acceleration Structures: BVH Representation

Hardware-accelerated ray tracing relies on Bounding Volume Hierarchies (BVH) to traverse scenes efficiently. Vulkan divides this hierarchy into a two-level acceleration structure managed through the VkAccelerationStructureKHR handle:

  • Bottom-Level Acceleration Structures (BLAS): Contain actual geometric data (triangles or Axis-Aligned Bounding Boxes for custom primitives). These define the local geometry and are typically static or updated only when underlying meshes deform.
  • Top-Level Acceleration Structures (TLAS): Contain instances of BLAS, complete with transformation matrices, instance masks, and shader record offsets. The TLAS defines the global scene configuration.

Applications allocate device memory explicitly to back these structures via vkGetAccelerationStructureBuildSizesKHR and issue build commands (vkCmdBuildAccelerationStructuresKHR) directly into command buffers, leveraging asynchronous compute queues and explicit barrier synchronization.

The Dedicated Ray Tracing Pipeline

Vulkan provides a distinct pipeline abstraction for ray tracing created via vkCreateRayTracingPipelinesKHR. Unlike raster pipelines that process primitives down a fixed vertex-to-fragment flow, the ray tracing pipeline is recursive and dynamic, introducing dedicated shader stages:

  1. Ray Generation (raygen): The entry point executed per pixel or work item. It initializes rays and invokes traversal via the traceRayEXT SPIR-V instruction.
  2. Intersection (intersection): Evaluates intersections for non-triangle custom primitives.
  3. Any-Hit (anyhit): Executes on every candidate intersection to determine whether a hit should be accepted (useful for alpha testing/transparency).
  4. Closest-Hit (closesthit): Invoked once the traversal concludes and the closest valid surface intersection along the ray is confirmed. Shading and secondary ray spawning typically happen here.
  5. Miss (miss): Executes when a ray fails to intersect any geometry, commonly used to sample environment maps or skyboxes.
  6. Callable (callable): Reusable execution units that can be dispatched dynamically from other ray tracing shaders to execute general logic.

The Shader Binding Table (SBT)

Because rays dynamically encounter varying geometry and materials, the standard static descriptor binding model is insufficient. Vulkan solves dynamic material dispatch through the Shader Binding Table (SBT).

The SBT is a user-managed VkBuffer composed of shader records. Each record consists of a fixed-size shader identifier (queried via vkGetRayTracingShaderGroupHandlesKHR) followed by custom application data, such as resource indices, constants, or descriptor handles. When an intersection or miss occurs, the GPU calculates an offset into the SBT using indices embedded in the TLAS instances and geometry parameters, mapping ray-primitive collisions directly to specific shader code and resources without CPU-side dispatch overhead.

Command Execution and Hardware Traversal

To dispatch the ray tracing pipeline, applications record vkCmdTraceRaysKHR into a command buffer, specifying grid dimensions (width, height, depth) and the memory addresses of the SBT regions (Raygen, Miss, Hit, and Callable).

At the silicon level:

  • The Raygen stage launches warps/wavefronts across standard compute units.
  • Calls to traceRayEXT offload ray traversal to dedicated hardware units (such as RT Cores). These units asynchronously test rays against the BVH nodes and triangle primitives.
  • The hardware suspends ray execution, calls Any-Hit or Intersection shaders as needed, and finally schedules the appropriate Closest-Hit or Miss shader based on the SBT layout.

Ray Queries: Inline Ray Tracing

In addition to full ray tracing pipelines, Vulkan exposes ray tracing inside traditional shader stages (vertex, fragment, compute, mesh) via Ray Queries (VK_KHR_ray_query).

Ray queries do not require specialized shader stages or an SBT. Instead, they expose rayQuery*EXT functions directly inside standard GLSL or HLSL code, executing traversal loops sequentially within the current execution context. This allows developers to add selective hardware-accelerated features—such as ambient occlusion, shadow testing, or reflection checks—directly into existing rasterization fragment shaders or compute-driven post-processing passes.
