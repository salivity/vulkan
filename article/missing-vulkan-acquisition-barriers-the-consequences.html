Missing Vulkan Acquisition Barriers: The Consequences

In the Vulkan graphics and compute API, transferring resource ownership between distinct queue families requires a synchronized pair of operations: a release barrier on the source queue and an acquisition barrier on the destination queue. Omitting the destination acquisition barrier is a direct specification violation that leads to undefined behavior. This article examines the immediate and downstream technical consequences of skipping an acquisition barrier, including memory hazards, cache incoherence, silent data corruption, and catastrophic GPU timeouts.

Memory Hazards and Race Conditions

Queue family ownership transfer is an asynchronous protocol. When a release barrier is executed on the source queue, it only defines when the source operations finish and makes the associated memory available. It does not establish a dependency on the destination queue.

If you omit the acquisition barrier on the destination queue, there is no execution or memory dependency linking the two queues. The destination queue may begin reading or writing to the resource before the source queue has finished writing to it, resulting in:

  • Read-After-Write (RAW) Hazards: The destination queue reads stale or partially written data.
  • Write-After-Write (WAW) Hazards: Destination writes overwrite the memory concurrently while the source is still finalizing its write pipeline stages.

Cache Incoherence and Stale Data

Even if CPU-side fences or GPU timeline semaphores are used to synchronize execution order between queues, semaphores alone do not perform memory domain operations.

Memory domain transfers require an acquisition barrier to:

  1. Make memory available to the destination queue's memory domain.
  2. Invalidate the destination queue’s local hardware caches (such as texture L1/L2 caches or compute L1 caches).

Without the acquisition barrier, the hardware will not invalidate its local caches. Subsequent operations on the destination queue will read outdated data retained in cache lines from prior operations rather than fetching the newly modified data from main memory.

Visual Artifacts and Silent Corruption

Because Vulkan drivers do not automatically insert safety barriers, omitting the acquisition barrier often results in non-deterministic bugs:

  • Flickering and Tearing: Textures transferred from a transfer queue to a graphics queue for sampling may flicker, display tearing, or alternate between the previous and current frame contents.
  • Incorrect Compute Outputs: Buffers passed from graphics to compute pipelines may contain uninitialized values or partially completed compute inputs, leading to math errors in physics, AI, or ray tracing passes.

Because these errors depend on memory timing and cache line evictions, they may work seemingly fine on one vendor's GPU architecture (e.g., unified memory architectures) while failing consistently on others (e.g., discrete GPUs with partitioned caches).

Device Lost Errors and GPU Hangs

Under specific conditions—particularly with compressed image layouts—omitting the acquisition barrier can trigger a GPU crash. If the image layout transition metadata is expected to be applied or finalized via the acquisition barrier, operating on the memory without that transition can cause hardware decoders to access invalid image block metadata. When hardware decoders attempt to interpret corrupted memory structures, the graphics driver typically detects a hardware hang and returns a fatal VK_ERROR_DEVICE_LOST error.

Validation Layer Reporting

The Vulkan Validation Layers strictly track queue family ownership transfers. Omitting an acquisition barrier will cause the validation layers to trigger a message indicating an unmatched release barrier. The layers report that an ownership transfer was initiated on one queue family but never completed on the target queue family, warning developers that the resource remains in an invalid state for destination queue access.
