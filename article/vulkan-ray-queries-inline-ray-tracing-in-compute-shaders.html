Vulkan Ray Queries: Inline Ray Tracing in Compute Shaders

This article provides an overview of Vulkan ray queries and explains how they enable developers to perform inline ray tracing directly inside compute shaders. It explores the core differences between dedicated ray tracing pipelines and ray queries, breaks down the inline traversal execution model, and highlights practical use cases where ray queries offer optimal performance and integration simplicity.

Understanding Ray Queries in Vulkan

In the Vulkan API, hardware-accelerated ray tracing is exposed primarily through two mechanisms introduced in the KHR ray tracing extensions: ray tracing pipelines (VK_KHR_ray_tracing_pipeline) and ray queries (VK_KHR_ray_query). While ray tracing pipelines introduce a complete pipeline architecture with dedicated shader stages (ray generation, closest hit, any-hit, and miss shaders), ray queries provide a lightweight alternative.

Ray queries allow developers to initiate ray traversal directly from within existing shader stages, such as compute or fragment shaders. This mechanism is referred to as "inline ray tracing" because the ray traversal logic is embedded straight into standard shader code without requiring dedicated ray tracing pipelines, shader binding tables (SBTs), or pipeline switches.

How Inline Ray Tracing Operates in Compute Shaders

To utilize ray queries within a compute shader, the application enables the VK_KHR_ray_query device extension and includes the corresponding shading language extension, such as GL_EXT_ray_query in GLSL.

The execution process in a compute shader revolves around a dedicated query object and follows a distinct control flow:

  1. Acceleration Structure Binding: The compute pipeline binds the top-level acceleration structure (TLAS) as an acceleration structure descriptor set, making the scene geometry accessible to the shader.
  2. Object Declaration: The shader instantiates a rayQueryEXT object, which encapsulates the internal state of the ray traversal.
  3. Initialization: The shader calls rayQueryInitializeEXT(). This function takes the TLAS, ray flags (such as cull masks or flags for terminating on first hit), the ray origin, minimum and maximum traversal distances, and the ray direction vector.
  4. Traversal Loop: Traversal is driven manually via a loop using rayQueryProceedEXT(). This function executes the hardware traversal through the bounding volume hierarchy (BVH) and returns a boolean indicating whether the traversal is ongoing or complete.
  5. Intersection Handling: During traversal, the shader can inspect candidate intersections (such as custom intersection logic for procedural geometry or alpha-tested geometry) and confirm or ignore them using rayQueryConfirmIntersectionEXT().
  6. Result Evaluation: Once rayQueryProceedEXT() returns false, the traversal finishes. The shader queries the final result using functions like rayQueryGetIntersectionTypeEXT() to determine if a geometry hit occurred, and accesses hit properties such as barycentric coordinates, instance IDs, and hit distances.

Advantages of Ray Queries over Dedicated Pipelines

Using ray queries inside compute shaders provides several architectural advantages:

  • Minimal Pipeline Overhead: Ray queries bypass the complex setup of shader binding tables and ray tracing pipeline layout objects. They run inside standard VkComputePipeline dispatches.
  • Coherence and Control: In a ray tracing pipeline, dynamic dispatch across various hit and miss shaders can introduce execution divergence. With ray queries, the control flow remains entirely inside the compute shader, allowing the compiler and developer to manage register allocation and divergence more strictly.
  • Seamless Hybrid Rendering: Compute-based post-processing passes can easily integrate ray-traced effects. A single compute pass can evaluate screen-space data and conditionally trace shadow, ambient occlusion, or reflection rays only for pixels that fail screen-space checks.

Ray queries provide Vulkan developers with a flexible, low-overhead method to integrate hardware-accelerated visibility, collision, and lighting tests directly into compute workloads.
