Vulkan Video Decode Memory Management Explained

Vulkan Video integrates hardware-accelerated video decoding into the Vulkan ecosystem, requiring developers to explicitly handle device memory rather than relying on high-level driver abstractions. This article explains how memory management operates during Vulkan video decoding sessions, covering session-specific memory requirements, Decoded Picture Buffer (DPB) allocation, bitstream buffer management, and image layout transitions.

Video Session Initialization and Memory Binding

A decoding workflow begins with the creation of a VkVideoSessionKHR object, which encapsulates the codec profile, resolution, and hardware decoder state. Unlike standard Vulkan objects that allocate internal resources invisibly, a video session requires explicit memory allocations provided by the application.

Developers query these requirements using vkGetVideoSessionMemoryRequirementsKHR. The implementation returns one or more memory requirements structures representing distinct memory types needed by the hardware, such as scratch spaces, internal working memory, or context buffers.

Each requirement specifies:

  • Memory size and alignment requirements.
  • Memory type bits indicating supported host or device memory types.
  • A binding index corresponding to the specific internal purpose defined by the driver.

The application allocates the necessary VkDeviceMemory via vkAllocateMemory and binds it to the session using vkBindVideoSessionMemoryKHR. A video session cannot execute decoding commands until all required memory bindings are satisfied.

The Decoded Picture Buffer (DPB)

Inter-frame prediction codecs (such as H.264, H.265, and AV1) require previously decoded frames to reconstruct subsequent pictures. These frames reside in the Decoded Picture Buffer (DPB).

In Vulkan, DPB memory is explicitly managed using standard VkImage allocations configured with the VK_IMAGE_USAGE_VIDEO_DECODE_DPB_BIT_KHR flag. Depending on the implementation and chosen profile, DPB storage can follow two structural approaches:

  1. Individual Images: Separate VkImage allocations for each reference slot in the DPB.
  2. Arrayed Image: A single layered VkImage where each layer represents a reference frame slot.

Developers query decoder capabilities via VkVideoDecodeCapabilitiesKHR to determine the maximum number of active references and whether the hardware prefers array or independent image structures. Memory for DPB images must be allocated from device-local memory (VK_MEMORY_PROPERTY_DEVICE_LOCAL_BIT) to ensure low-latency access for the video hardware engine.

Destination and Display Images

The target image that receives the newly decoded frame is flagged with VK_IMAGE_USAGE_VIDEO_DECODE_DST_BIT_KHR.

Depending on codec configuration and implementation limits, the destination image and the DPB image may be distinct resources or the same resource:

  • Coinciding DPB and Destination: When the decoded frame immediately enters the reference list, the destination image can serve directly as a DPB entry, avoiding extra memory transfers.
  • Distinct DPB and Destination: If the implementation requires separate output storage, or if the format of the output needs post-processing (such as format conversion for rendering), distinct images are allocated, and the decoder writes simultaneously or copies to the target.

Bitstream Source Buffers

The compressed video stream fed into the decoder must be placed in a VkBuffer created with VK_BUFFER_USAGE_VIDEO_DECODE_SRC_BIT_KHR.

Because bitstream data is written by the CPU and read by the GPU, memory management for these buffers typically utilizes host-visible, host-coherent memory (VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT | VK_MEMORY_PROPERTY_HOST_COHERENT_BIT) or staging buffers with fast copy operations into device-local buffers. Ring buffers are frequently used to manage continuous streaming without constant reallocation.

Memory Layouts and Synchronization

Video operations must transition images into appropriate layouts using memory barriers (vkCmdPipelineBarrier2 with VkImageMemoryBarrier2):

  • Bitstream input buffers must be synchronized with VK_PIPELINE_STAGE_2_VIDEO_DECODE_BIT_KHR and access flag VK_ACCESS_2_VIDEO_DECODE_READ_BIT_KHR.
  • Reference frames in the DPB require the layout VK_IMAGE_LAYOUT_VIDEO_DECODE_DPB_KHR and access VK_ACCESS_2_VIDEO_DECODE_READ_BIT_KHR.
  • Target output frames require the layout VK_IMAGE_LAYOUT_VIDEO_DECODE_DST_KHR and access VK_ACCESS_2_VIDEO_DECODE_WRITE_BIT_KHR.

Once decoding is complete, standard image layout transitions allow the output frame to be handed off to the graphics queue (VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL) for rendering or presentation to the swapchain (VK_IMAGE_LAYOUT_PRESENT_SRC_KHR). Active DPB slots cannot be reused or transitioned away until the codec’s reference picture marking processes indicate that the referenced pictures are no longer needed.
