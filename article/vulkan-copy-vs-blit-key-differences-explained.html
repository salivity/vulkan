Vulkan Copy vs Blit: Key Differences Explained

In the Vulkan graphics API, transferring image data is primarily achieved using either a copy operation (vkCmdCopyImage) or a blit operation (vkCmdBlitImage). While both commands transfer texel data from one resource to another, they serve distinct architectural purposes. A copy operation performs a raw, bitwise data transfer between identically sized regions, whereas a blit operation utilizes graphics hardware to perform scaling, format conversion, and filtering during the transfer. This article explains the technical differences between these two commands, covering capabilities, hardware requirements, and appropriate use cases.

Data Manipulation and Scaling

The most prominent difference lies in whether the pixel data can be altered during the transfer:

  • Copy Operations (vkCmdCopyImage): Perform an exact 1:1 bitwise copy. The source region and destination region must have the exact same pixel dimensions (width, height, and depth). No scaling, shearing, stretching, or pixel filtering can occur.
  • Blit Operations (vkCmdBlitImage): Support dynamic scaling and stretching. You can define source and destination regions with different dimensions. Vulkan allows you to specify a filter—either VK_FILTER_NEAREST or VK_FILTER_LINEAR—to interpolate pixel values when magnifying or minifying the image.

Format Compatibility and Conversion

Image formats impose strict rules on which transfer command can be executed:

  • Copy Operations: Require format compatibility, but not necessarily identical formats. The source and destination formats must belong to the same format compatibility class (meaning texels must have identical byte sizes and layout structures). However, no color space transformation or conversion takes place.
  • Blit Operations: Support automatic format conversion between entirely different formats (for example, blitting an R8G8B8A8_UNORM image into an R16G16B16A16_SFLOAT image). The hardware automatically unpacks, converts, and repacks texel data into the target format.

Hardware Execution and Queue Families

Vulkan exposes different hardware queues for different types of work, which dictates where these operations can execute:

  • Copy Operations: Can be executed on dedicated transfer queues (VK_QUEUE_TRANSFER_BIT), compute queues, and graphics queues. Because copies bypass the rasterizer and filtering pipeline, they can run on asynchronous transfer hardware (DMA engines) without interrupting rendering workloads.
  • Blit Operations: Generally require a graphics-capable queue (VK_QUEUE_GRAPHICS_BIT). Blitting relies on rasterization, texture sampling, and filtering pipelines to process and transform the image data. Images must also support the VK_FORMAT_FEATURE_BLIT_SRC_BIT and VK_FORMAT_FEATURE_BLIT_DST_BIT flags in their respective format properties.

Performance

  • Copy Operations: Typically offer the highest possible throughput and lowest execution overhead. Because they avoid the graphics pipeline and do not sample or filter data, copies are ideal for raw memory bandwidth efficiency.
  • Blit Operations: Incur more overhead than a pure copy due to the invocation of fixed-function sampling and conversion units. While highly optimized on modern GPUs, blitting should not be used when a direct copy is sufficient.

Typical Use Cases

  • Use vkCmdCopyImage when:
    • Copying data between staging resources and final textures.
    • Moving data between render targets of identical size and format.
    • Preserving exact bit-level image data where filtering or modification would corrupt information (e.g., depth-stencil textures, packed integer data, or G-buffer layouts).
    • Submitting operations to a dedicated transfer queue asynchronously.
  • Use vkCmdBlitImage when:
    • Generating mipmaps programmatically (progressively downscaling an image by a factor of two using linear filtering).
    • Rescaling a rendered frame buffer to match a display swapchain surface of a different resolution.
    • Converting between color spaces or mismatched pixel formats during a transfer.
