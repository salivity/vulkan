Vulkan Attachment Write Hazards in Multi-Pass Rendering

In Vulkan multi-pass rendering, attachment write hazards occur when multiple subpasses or distinct render passes attempt to read from or write to the same framebuffer attachments without sufficient synchronization. Because the Vulkan specification assumes the GPU executes operations asynchronously and out-of-order by default, omitting or misconfiguring subpass dependencies, pipeline stage masks, access flags, and image layout transitions leads directly to read-after-write (RAW), write-after-read (WAR), or write-after-write (WAW) data races.

Absence of Subpass Dependencies

Within a single VkRenderPass, subpasses do not execute sequentially by default. The GPU driver can overlap the execution of separate subpasses unless explicitly instructed otherwise. If subpass \(B\) relies on the output of subpass \(A\), failing to declare an explicit VkSubpassDependency linking the two allows the GPU to schedule write operations simultaneously, causing a write hazard.

Incorrect Pipeline Stage Masks

A common source of write hazards is specifying mismatched or incomplete pipeline stages in srcStageMask and dstStageMask within a VkSubpassDependency or VkMemoryBarrier.

  • If color attachments are modified, the dependency must include VK_PIPELINE_STAGE_COLOR_ATTACHMENT_OUTPUT_BIT in the source stage mask.
  • If depth or stencil attachments are involved, the hazard often stems from excluding VK_PIPELINE_STAGE_EARLY_FRAGMENT_TESTS_BIT or VK_PIPELINE_STAGE_LATE_FRAGMENT_TESTS_BIT.
  • Waiting on the wrong stage allows subsequent draw calls to initiate write operations before the preceding writes have fully reached the attachment.

Inaccurate Memory Access Masks

Execution dependencies ensure only that execution steps finish in order, not that memory caches are flushed and invalidated. An attachment write hazard arises when memory availability and visibility operations are omitted via incorrect srcAccessMask and dstAccessMask entries:

  • Write-After-Write (WAW): Occurs when a write finishes, but VK_ACCESS_COLOR_ATTACHMENT_WRITE_BIT (or depth equivalent) is omitted from srcAccessMask, preventing the cache flush before the next write begins.
  • Read-After-Write (RAW): Occurs when an attachment is read as an input attachment in a subsequent subpass without declaring VK_ACCESS_INPUT_ATTACHMENT_READ_BIT in dstAccessMask.

Implicit Layout Transitions and Self-Dependencies

When attachments change layouts between subpasses (e.g., transitioning from a color write layout to a shader read-only layout), Vulkan performs an automatic layout transition. This transition is tied directly to the subpass dependency configuration. If no dependency covers the transition, the hardware attempts to compress, decompress, or reformat memory while a write operation is actively writing to the memory, corrupting the target data.

Additionally, reading and writing to the exact same pixel coordinate within the same subpass requires a subpass self-dependency (VK_DEPENDENCY_BY_REGION_BIT) alongside appropriate storage or input attachment declarations. Without this, simultaneous reads and writes to identical attachment memory blocks cause fragment-level race conditions.

Missing Synchronization Across Multiple Render Passes

When multi-pass rendering is split across separate VkRenderPass instances rather than subpasses inside a single render pass, subpass dependencies cannot resolve data hazards. Attachment write hazards in this scenario are caused by:

  • Omitting an explicit VkImageMemoryBarrier between vkCmdEndRenderPass and the subsequent vkCmdBeginRenderPass.
  • Misconfiguring loadOp and storeOp. If storeOp is set to VK_ATTACHMENT_STORE_OP_DONT_CARE, or if the previous render pass has not completed its store operation before the next pass executes its VK_ATTACHMENT_LOAD_OP_LOAD or write phase, write collisions occur at the memory controller level.
