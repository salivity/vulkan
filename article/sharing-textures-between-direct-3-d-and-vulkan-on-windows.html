Sharing Textures Between Direct3D and Vulkan on Windows

Cross-API interoperability between Direct3D and Vulkan on Windows allows developers to share texture resources without copying data across system memory. This article explains the underlying mechanisms facilitating this exchange, including Windows Display Driver Model (WDDM) shared resource handles, Direct3D export interfaces, Vulkan external memory extensions, and cross-API synchronization primitives required for safe execution.

WDDM and DXGI Shared Handles

The foundation of resource sharing on Windows relies on the Windows Display Driver Model (WDDM) and the DirectX Graphics Infrastructure (DXGI). At the driver level, a texture is allocated as a physical allocation managed by the graphics kernel. WDDM allows these physical allocations to be associated with an operating system kernel object, commonly referred to as an NT handle.

Older legacy systems utilized global KMT (Kernel Mode Transport) handles, which were represented by simple 32-bit integer identifiers. Modern implementations use standard Win32 NT handles (HANDLE), which provide robust process security, access rights management, and lifecycle tracking.

Direct3D Allocation and Export

To make a texture shareable from Direct3D (either D3D11 or D3D12), the resource must be created with explicit sharing flags:

  • In Direct3D 11: The texture must be instantiated using the D3D11_RESOURCE_MISC_SHARED_NTHANDLE flag in its description struct.
  • In Direct3D 12: The backing heap or committed resource must specify D3D12_HEAP_FLAG_SHARED.

Once the resource is created, the application calls the CreateSharedHandle method from the relevant device or resource interface (ID3D11Resource::QueryInterface for IDXGIResource1 or ID3D12Device::CreateSharedHandle). This outputs a Win32 HANDLE pointing to the underlying GPU memory allocation.

Vulkan External Memory Extensions

Vulkan consumes these shared textures via its external memory extension ecosystem. The primary extensions required include:

  • VK_KHR_external_memory: Defines generic cross-API and cross-process resource sharing capabilities.
  • VK_KHR_external_memory_win32: Provides Win32-specific import and export capabilities for NT handles.

To import the texture into Vulkan:

  1. The application queries the memory requirements using vkGetPhysicalDeviceImageFormatProperties2 with a chained VkPhysicalDeviceExternalImageFormatInfo struct to ensure compatibility.
  2. An image is initialized using vkCreateImage, including a chained VkExternalMemoryImageCreateInfo struct that specifies VK_EXTERNAL_MEMORY_HANDLE_TYPE_OPAQUE_WIN32_BIT.
  3. Memory is bound to the image using vkAllocateMemory, chaining a VkImportMemoryWin32HandleInfoKHR structure containing the NT HANDLE obtained from Direct3D.

Format Matching and Tiling Compatibility

Both APIs must agree on how the texture is stored and sampled. The DXGI format (such as DXGI_FORMAT_R8G8B8A8_UNORM) must map precisely to its equivalent Vulkan format (VK_FORMAT_R8G8B8A8_UNORM). Furthermore, because different APIs or drivers may implement disparate proprietary memory layouts, shared textures generally must use standard optimal tiling architectures recognized by the underlying unified device driver.

Cross-API Synchronization

Sharing memory only maps the backing store; it does not serialize commands across the Direct3D and Vulkan queues. Without synchronization, concurrent access results in race conditions.

To synchronize texture access:

  • Keyed Mutexes: Direct3D 11 often uses IDXGIKeyedMutex. Vulkan supports this via VK_KHR_win32_keyed_mutex, allowing Vulkan command buffers to acquire and release the texture using keyed lock states.
  • Shared Fences and Semaphores: Direct3D 12 and modern Vulkan workflows share timeline semaphores and fences. The extension VK_KHR_external_semaphore_win32 allows importing a Direct3D 12 fence (ID3D12Fence) as a Vulkan semaphore, allowing GPU-to-GPU execution dependency tracking without host CPU intervention.
