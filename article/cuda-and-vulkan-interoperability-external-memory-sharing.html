CUDA and Vulkan Interoperability: External Memory Sharing

External memory sharing enables high-performance interoperability between CUDA and Vulkan by allowing both APIs to access the exact same physical GPU allocations without routing data through host system memory. Traditionally, passing computational outputs from CUDA to a graphics API like Vulkan required costly device-to-host and host-to-device memory copies. By utilizing OS-level handles and dedicated API extensions, developers can create seamless zero-copy pipelines where CUDA performs heavy compute, AI inference, or physics simulations, and Vulkan immediately renders the results with minimal latency.

The Mechanism of Shared Allocations

At the core of this interoperability is the ability to export and import dedicated GPU memory objects. The process relies on platform-specific operating system primitives:

  1. POSIX File Descriptors (Linux): Memory is bound to an integer file descriptor representing the GPU buffer.
  2. NT Handles (Windows): Memory is referenced via standard Windows security handles.

In Vulkan, memory is allocated using the VK_KHR_external_memory extension (or core functionality in modern Vulkan versions). When allocating memory with vkAllocateMemory, the developer specifies an export handle type via VkExportMemoryAllocateInfo. This flags the memory chunk as exportable to other device drivers or APIs running on the same hardware.

Once allocated, Vulkan exports the memory handle using platform-specific extensions such as VK_KHR_external_memory_fd for Linux or VK_KHR_external_memory_win32 for Windows.

Importing Memory into CUDA

On the CUDA side, the developer utilizes the CUDA External Resource Interoperability API. CUDA does not allocate new device memory for the incoming data; instead, it creates a virtual mapping over the existing Vulkan buffer:

  • The exported OS handle is passed into CUDA using the cudaImportExternalMemory function, configured via the cudaExternalMemoryHandleDesc structure.
  • After importing, CUDA maps the external allocation into its address space as either a linear pointer via cudaExternalMemoryGetMappedBuffer or a CUDA array via cudaExternalMemoryGetMappedMipmappedArray.

CUDA kernels can now directly read from and write to the same physical memory addresses that Vulkan references, eliminating redundant data transfer overhead entirely.

Cross-API Synchronization

Sharing memory is only functional if concurrent operations are properly coordinated to avoid race conditions. Vulkan and CUDA operate on separate command queues and execution models, making API-level synchronization mandatory.

Synchronization is achieved through external semaphores:

  • Vulkan Setup: Vulkan exports timeline or binary semaphores using the VK_KHR_external_semaphore extension alongside OS-specific helpers (VK_KHR_external_semaphore_fd or VK_KHR_external_semaphore_win32).
  • CUDA Import: CUDA imports these synchronization primitives via cudaImportExternalSemaphore.
  • Execution Flow: Vulkan signals an external semaphore upon completing a rendering pass, prompting CUDA to wait via cudaWaitExternalSemaphoresAsync. Once CUDA finishes processing the shared buffer, it signals another external semaphore using cudaSignalExternalSemaphoresAsync, which unblocks subsequent Vulkan queue submissions.

Practical Impact

By pairing shared external memory allocations with shared semaphores, CUDA and Vulkan operate as complementary components of a unified GPU pipeline. Applications like real-time neural rendering, machine learning post-processing, and interactive physical simulations gain dramatic performance improvements through zero-copy data persistence and deterministic cross-API queue scheduling.
