AFR Synchronization in Vulkan SLI and CrossFire

Alternate-Frame Rendering (AFR) distributes consecutive frames across multiple graphics processing units (GPUs), alternating execution between cards like AMD CrossFire or NVIDIA SLI setups. Under the Vulkan API, this synchronization is shifted from opaque graphics drivers to explicit, developer-managed constructs introduced natively through Vulkan Device Groups. This article explores how Vulkan orchestrates cross-GPU communication, peer-to-peer data transfers for temporal effects, queue synchronization primitives, and swapchain presentation to maintain smooth frame pacing in AFR configurations.

Explicit Multi-GPU Architecture via Device Groups

Unlike DirectX 11 or legacy OpenGL, which relied heavily on driver profiles to guess and force SLI or CrossFire AFR, Vulkan utilizes the core VK_KHR_device_group extension (integrated into Vulkan 1.1). Instead of exposing multiple distinct logical devices, the Vulkan driver bundles compatible physical GPUs into a single logical VkDevice.

Each physical GPU within this group is assigned a device index bitmask. In an AFR implementation, the application allocates command buffers and binds render targets to alternate physical GPU masks (e.g., Device Mask 0x1 for GPU 0 on odd frames, and Device Mask 0x2 for GPU 1 on even frames).

Cross-GPU Data Transfers and Peer Memory

The primary technical bottleneck in AFR is temporal dependency—rendering frame N on GPU 1 often requires information from frame N-1 rendered on GPU 0 (such as motion vectors, temporal anti-aliasing (TAA) buffers, or dynamic shadow maps).

Vulkan addresses this dependency using explicit peer-to-peer memory transfers across the interconnect (PCIe or high-speed links like NVLink):

  1. Peer Memory Capabilities: The application queries vkGetDeviceGroupPeerMemoryFeaturesKHR to determine whether GPUs can directly sample or copy across device bounds.
  2. Buffer Transfers: When a temporal asset is needed, a synchronization barrier (vkCmdPipelineBarrier) transitions the texture state on the rendering GPU. The asset is then copied to the peer GPU using vkCmdCopyImage or directly accessed if unified memory mapping is supported.
  3. Bandwidth Optimization: Developers must only synchronize minimal delta data. Transferring entire rendered frame buffers across buses causes severe latency spikes, which historically caused micro-stutter in legacy SLI/CrossFire setups.

Synchronization Primitives: Semaphores and Fences

To prevent race conditions—where GPU 1 attempts to draw before GPU 0 has finished providing necessary inter-frame dependencies—Vulkan provides cross-device synchronization primitives:

  • Timeline Semaphores: Vulkan utilizes timeline semaphores (VK_KHR_timeline_semaphore) to coordinate work across different device queues. A monotonically increasing 64-bit integer tracks progress, allowing GPU 1 to wait on a specific signal value from GPU 0's queue before consuming dependency buffers.
  • Binary Semaphores: Standard queue submissions (vkQueueSubmit) accept VkDeviceGroupSubmitInfo, allowing binary semaphores to be signaled on one physical device and waited on by another within the same device group.
  • Fences: CPU-GPU synchronization relies on VkFence objects to track frame completion, preventing the CPU execution engine from submitting frame descriptors too far ahead of hardware execution, thus managing frame latency and queue depth.

Swapchain and Presentation Synchronization

In a multi-GPU system, typically only one GPU is physically connected to the display output. Presenting frames from alternating GPUs requires synchronized handoffs to the presentation engine:

  1. Present Masking: The presentation engine is targeted via vkQueuePresentKHR along with the VkDeviceGroupPresentInfoKHR struct. This specifies the deviceMask indicating which physical GPU completed the frame.
  2. Swapchain Blitting: If the frame was drawn on the non-connected secondary GPU, the Vulkan runtime facilitates an internal copy across the bus to the primary display GPU's swapchain image.
  3. Present Semaphores: A presentation semaphore ensures that the image transfer and rendering operations are complete before the display engine reads the final image, effectively eliminating frame tearing and micro-stuttering inherent to unmanaged AFR execution.
