Vulkan Asynchronous Occlusion Queries Without CPU Stalls

This article provides an overview of how game and rendering engines read occlusion query results asynchronously in Vulkan without introducing CPU pipeline bubbles. By replacing synchronous query polling with multi-frame readback latency, non-blocking flags, and GPU-driven rendering techniques like conditional rendering and compute-based indirect draws, engines can leverage occlusion culling while maintaining maximum GPU and CPU parallelism.

The Bottleneck: Synchronous Query Reads

In Vulkan, occlusion queries count the number of fragments or samples that pass depth and stencil tests using a VkQueryPool. The most straightforward way to retrieve these results is via the vkGetQueryPoolResults function.

However, calling vkGetQueryPoolResults with the VK_QUERY_RESULT_WAIT_BIT flag forces the CPU to wait until the GPU has fully processed all geometry associated with that query. Because the CPU typically runs one or two frames ahead of the GPU, synchronizing here stalls the CPU thread, destroys parallelism, and severely impacts frame rates. To avoid this, engines employ asynchronous approaches.

Method 1: Multi-Frame Latency with Non-Blocking Flags

The simplest asynchronous CPU-side approach is to introduce frame latency (typically 1 to 2 frames) before reading the query results.

  1. Issue the Query: On Frame \(N\), issue the occlusion test between vkCmdBeginQuery and vkCmdEndQuery.
  2. Postpone the Read: Do not attempt to read the query within Frame \(N\). Instead, read it on Frame \(N+1\) or Frame \(N+2\).
  3. Use Non-Blocking Retrieval: Call vkGetQueryPoolResults without VK_QUERY_RESULT_WAIT_BIT. Instead, pass VK_QUERY_RESULT_WITH_AVAILABILITY_BIT.
  4. Evaluate Availability: This flag writes an extra integer along with the query result indicating whether the data is actually ready. If the data is ready, update the visibility state. If the data is not ready (VK_NOT_READY), employ a conservative fallback heuristic: assume the object is visible to avoid popping artifacts, and retain the previous frame's visibility state.

Because queries from two frames ago are almost always completed by the time the CPU processes the current frame, this approach yields high hit rates with zero CPU wait time.

Method 2: GPU-to-Buffer Copy (vkCmdCopyQueryPoolResults)

Rather than pulling data directly to host memory using CPU commands, you can instruct the GPU to write query results into a VkBuffer using vkCmdCopyQueryPoolResults.

vkCmdCopyQueryPoolResults(
    commandBuffer,
    queryPool,
    firstQuery,
    queryCount,
    dstBuffer,
    dstOffset,
    stride,
    VK_QUERY_RESULT_64_BIT | VK_QUERY_RESULT_WAIT_BIT
);

In this context, VK_QUERY_RESULT_WAIT_BIT only makes the GPU execution wait for the query to finish within the GPU pipeline; it does not stall the CPU.

The engine can then handle the destination buffer in two ways:

  • Asynchronous Host Readback: Use a persistently mapped, host-coherent buffer ring corresponding to the engine's frames-in-flight. The CPU only maps and reads the buffer when the corresponding frame fence signals completion.
  • Keep Data on GPU: Leave the results in VRAM for direct consumption by subsequent compute passes or indirect commands.

Method 3: Completely GPU-Driven Occlusion (Zero CPU Involvement)

High-performance modern engines eliminate the CPU from the occlusion loop entirely. Transferring query data back to the CPU introduces temporal lag, which causes visible popping when the camera moves quickly. GPU-driven approaches solve this issue completely.

Conditional Rendering (VK_EXT_conditional_rendering)

Using the VK_EXT_conditional_rendering extension, the GPU determines whether to execute draw commands based on values in a VkBuffer.

  1. Render bounding boxes into the query pool.
  2. Call vkCmdCopyQueryPoolResults to write the results into a VkBuffer.
  3. Wrap subsequent high-detail mesh draws with vkCmdBeginConditionalRenderingEXT and vkCmdEndConditionalRenderingEXT, pointing directly to the query result in that buffer.
  4. If the sample count is zero, the GPU automatically discards the draw call without CPU intervention.

Compute Shader Compaction

Alternatively, the engine can copy query results to a storage buffer and dispatch a compute shader. The compute shader reads the visibility count, evaluates the object’s visibility, and populates a VkDrawIndexedIndirectCommand buffer. Visible objects are packed into the draw buffer, and hidden objects are omitted. The engine then calls vkCmdDrawIndexedIndirectCount to render only the visible meshes.

Proper Query Pool Recycling

To maintain asynchronous execution, the engine must handle query pool lifecycles correctly:

  • Per-Frame Allocation: Allocate separate query pools (or separate segments of a larger pool) for each frame-in-flight to prevent race conditions.
  • Asynchronous Resets: Use vkCmdResetQueryPool within a command buffer rather than vkResetQueryPool on the host. This ensures that queries are reset on the GPU timeline strictly after past reads have completed and immediately before new queries are begun.
