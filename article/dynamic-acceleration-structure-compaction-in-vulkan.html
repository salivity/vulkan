Dynamic Acceleration Structure Compaction in Vulkan

Dynamic acceleration structure compaction is a Vulkan optimization technique that significantly minimizes the VRAM footprint of ray tracing scenes by resizing over-allocated Bounding Volume Hierarchies (BVHs) to their exact post-build memory requirements. When an application builds Bottom-Level Acceleration Structures (BLAS), the driver must initially allocate memory based on a conservative, worst-case estimate. Compaction resolves this inefficiency by measuring the actual data footprint generated by the GPU during the initial build and copying the pruned, tightly packed hierarchy into a smaller, final buffer.

The Over-Allocation Problem in Ray Tracing

Vulkan builds ray tracing acceleration structures using geometry primitives (triangles, AABBs) to produce hierarchical structures that enable fast ray-primitive intersection queries. Before a BLAS can be built, the host application must query the GPU driver for required memory sizes using vkGetAccelerationStructureBuildSizesInfoKHR.

Because the driver cannot predict how efficiently specific geometry can be partitioned without actually processing it, the returned accelerationStructureSize must account for the worst-case geometric topology. As a result, the initial uncompacted acceleration structure is often significantly larger—sometimes consuming two to three times more memory than is strictly necessary.

The Compaction Process

Dynamic compaction operates as a multi-step, GPU-driven workflow that measures and reallocates the acceleration structure:

  1. Initial Build with Compaction Flag: The application builds the original BLAS into temporary scratch and acceleration structure buffers, including the VK_BUILD_ACCELERATION_STRUCTURE_ALLOW_COMPACTION_BIT_KHR flag in the build parameters.
  2. Querying Compacted Size: Alongside or immediately following the build command, a query is issued using vkCmdWriteAccelerationStructuresPropertiesKHR with the query type VK_QUERY_TYPE_ACCELERATION_STRUCTURE_COMPACTED_SIZE_KHR. The GPU calculates the exact byte size of the fully resolved BVH and writes it to a query pool.
  3. Reading the Query Results: The application retrieves the compacted sizes from the query pool via vkGetQueryPoolResults on the CPU or synchronizes directly on the GPU using indirect buffers.
  4. Allocating the Final Buffer: A new, tightly bounded VkBuffer is allocated using the precise size obtained from the query. A corresponding compacted VkAccelerationStructureKHR handle is created within this buffer.
  5. Executing the Compact Copy: The application dispatches vkCmdCopyAccelerationStructureKHR with the copy mode set to VK_COPY_ACCELERATION_STRUCTURE_MODE_COMPACT_KHR. The GPU copies the BVH data into the new destination buffer, trimming all unneeded padding and dead space.
  6. Reclaiming Temporary Memory: Once the copy completes, the original, oversized acceleration structure buffer and its associated scratch memory are safely deallocated.

Memory and Traversal Benefits

Compaction provides both direct memory savings and indirect rendering performance gains:

  • Substantial VRAM Reduction: Compaction typically reduces the memory footprint of static geometry BLAS instances by 30% to 55%, depending on the driver and mesh density. For modern scenes containing millions of unique primitives, this can free gigabytes of VRAM.
  • Improved Cache Efficiency: Smaller acceleration structures translate directly to a denser memory representation. When ray traversal shaders traverse the BVH nodes, fewer cache lines are invalidated, improving L1/L2 cache hit rates and overall ray traversal throughput.

Implementation Considerations

Compaction involves an extra copy operation and requires synchronization between the initial build, the query result, and the copy command. Performing this pipeline synchronously per-BLAS causes severe CPU/GPU pipeline stalls.

To maximize efficiency, applications should batch the process: build multiple BLAS instances concurrently in a single command buffer, record all compaction size queries simultaneously, allocate the compacted buffers in bulk, and execute a batched compaction copy. Consequently, dynamic compaction is best suited for static assets or assets loaded during streaming phases, rather than dynamic, deformable meshes that must be rebuilt every frame.
