Vulkan GPU-Assisted Validation for Descriptor Indexing

Vulkan GPU-assisted validation (GAV) detects runtime out-of-bounds descriptor indexing by modifying application shaders with injected instrumentation code, supplying internal GPU buffers containing descriptor array limits, and evaluating indices directly on the device at execution time. This process enables developers to pinpoint illegal accesses within dynamically indexed or "bindless" resource setups that CPU-based validation layers cannot track ahead of time.

The Challenge of Dynamic Descriptor Indexing

Standard CPU-side Vulkan validation layers intercept API calls on the host. While they can verify static bindings, pipeline layouts, and state transitions, they cannot inspect values computed entirely within shader execution on the GPU. When using descriptor indexing—often enabled via modern bindless rendering pipelines—shaders access large descriptor arrays using runtime-calculated values, such as instance IDs, material IDs, or uniform buffer offsets. If a dynamic calculation results in an index exceeding the array size allocated in the descriptor pool or set, the result is undefined behavior, device loss, or visual corruption.

SPIR-V Bytecode Instrumentation

GPU-assisted validation solves this visibility problem by transforming the shader code before pipeline creation. When GAV is enabled within the Vulkan Validation Layers, the layer intercepts the compiled SPIR-V bytecode during vkCreateGraphicsPipelines or vkCreateComputePipelines.

The instrumentation engine scans the SPIR-V modules for instructions that load or sample from descriptor-backed variables, such as OpImageSample*, OpLoad, or OpAccessChain. Before these memory operations execute, the layer injects conditional SPIR-V instructions that evaluate the calculated array index.

Internal Limit Buffers and Bindings

To validate an index on the GPU, the shader must know the legal boundaries of each descriptor array. The validation layer automatically manages this state:

  1. Descriptor Size Tables: The layer creates internal storage buffers containing the allocated size and descriptor count for every active descriptor set binding.
  2. Resource Re-mapping: The layer augments the application's pipeline layouts to bind these validation-owned storage buffers at designated binding points reserved for debug tracking.
  3. Index Comparison: The injected shader instructions read the valid array upper bound from the internal limit buffer and compare it against the dynamically computed index.

Error Recording and Safe Fallback

If an injected check discovers an out-of-bounds index:

  • Error Logging: The shader writes a structured error record to a dedicated GPU-side output buffer (implemented as an atomic ring buffer). This record contains metadata about the fault, including the descriptor set index, binding number, illegal array index, shader stage, and the unique ID of the offending SPIR-V instruction.
  • Execution Clamping: To prevent a hardware crash, hard page fault, or system TDR (Timeout Detection and Recovery), the instrumentation replaces the out-of-bounds index with a safe, valid default index (typically 0). This allows execution to proceed to a point where the host can safely read the error output.

Host Readback and Reporting

After the command buffer executes, or during synchronization events such as vkQueueWaitIdle, vkWaitForFences, or command buffer completion, the CPU-side validation layer maps and parses the GPU-side error buffer.

The layer cross-references the instruction ID and metadata with the original SPIR-V debug information (such as OpLine directives). It then routes a formatted error message through the VK_EXT_debug_utils callback, delivering a precise report containing the exact pipeline, draw call, shader stage, file name, line number, and invalid index that triggered the fault.
