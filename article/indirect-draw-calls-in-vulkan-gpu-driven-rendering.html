Indirect Draw Calls in Vulkan: GPU-Driven Rendering

In modern graphics programming, optimizing the boundary between the CPU and the GPU is critical for achieving high performance. This article explains the mechanics of indirect draw calls in Vulkan, contrasting them with traditional direct rendering commands. It explores how indirect drawing shifts parameter generation from the CPU to GPU-resident memory, and details how compute shaders can be leveraged to implement dynamic culling, level-of-detail selection, and fully GPU-driven rendering pipelines.

In a conventional rendering pipeline using Vulkan, drawing commands such as vkCmdDraw or vkCmdDrawIndexed require the CPU to record the exact parameters of every mesh to be rendered. The CPU specifies arguments like vertex counts, instance counts, first vertex indices, and base instance IDs directly within the command buffer. This model creates a tight dependency on the CPU: if an application needs to determine which objects are visible through frustum culling or occlusion queries, the CPU must either calculate this visibility itself or read back data from the GPU, which introduces significant latency and pipeline stalls.

Indirect draw calls change this paradigm by decoupling draw arguments from CPU command recording. Instead of passing parameters directly into the API call, functions like vkCmdDrawIndirect and vkCmdDrawIndexedIndirect instruct the GPU to read its drawing parameters from a VkBuffer. The layout of this buffer matches predefined structures: VkDrawIndirectCommand for non-indexed draws and VkDrawIndexedIndirectCommand for indexed draws. These structures hold the exact fields the hardware needs—such as indexCount, instanceCount, firstIndex, vertexOffset, and firstInstance.

Because the draw parameters reside inside a GPU-accessible buffer, the GPU can generate and modify its own workloads without CPU intervention. A typical GPU-driven pipeline operates in stages:

  1. Scene Data Upload: The CPU uploads raw instance and transform data to GPU storage buffers once or as objects move.
  2. Compute-Based Culling: A compute shader is dispatched prior to the render pass. This shader tests instances against the camera's view frustum, evaluates bounding boxes against hierarchical Z-buffers for occlusion culling, and selects appropriate Level of Detail (LOD) meshes.
  3. Command Generation: For each visible instance, the compute shader writes or increments instance counts and index offsets inside the indirect command buffer using atomic operations. If an entire group of instances is culled, the compute shader writes an instanceCount of zero, effectively skipping the draw call without CPU oversight.
  4. Execution: The render pass begins, and the graphics pipeline executes vkCmdDrawIndexedIndirect, consuming the parameters written during the compute pass.

Vulkan further expands this autonomy with the multi-draw indirect feature and vkCmdDrawIndirectCount (promoted to core in Vulkan 1.2). While standard indirect draws require the CPU to specify the total number of draw commands to execute, vkCmdDrawIndirectCount reads the draw count directly from another VkBuffer. This allows compute shaders to dynamically determine not only how many instances to draw per mesh, but also the total number of distinct draw calls submitted to the pipeline.

By transferring visibility testing, command population, and draw count determination to compute shaders, indirect draw calls eliminate the traditional CPU overhead associated with complex scenes containing thousands of individual objects. The CPU simply issues a static set of compute and indirect draw commands, while the GPU autonomously controls its own workload distribution in real time.
