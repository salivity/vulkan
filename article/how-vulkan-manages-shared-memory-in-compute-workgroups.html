How Vulkan Manages Shared Memory in Compute Workgroups

In the Vulkan graphics and compute API, shared memory—often termed workgroup local memory—provides high-speed, on-chip storage accessible by all invocations (threads) within a single compute workgroup. This article covers how Vulkan handles shared memory allocation during compute dispatches, including static definition in SPIR-V shaders, hardware resource limits, occupancy constraints on compute hardware, and synchronization requirements during execution.

Shared Memory Declaration and Compile-Time Sizing

Unlike APIs such as CUDA or Metal, core Vulkan does not permit dynamically sized shared memory allocations passed directly via the API command buffer (such as parameters in vkCmdDispatch). Instead, shared memory is statically sized within the shader source.

In GLSL, shared variables are declared using the shared storage qualifier, which compiles to the Workgroup storage class in SPIR-V:

shared float localTile[16][16];

Because the memory requirements are defined in the shader, the Vulkan driver determines the exact byte footprint required per workgroup during the creation of the compute pipeline (VkComputePipelineCreateInfo). If an application requires variable allocation sizes without recompiling full shaders, it must use Specialization Constants to adjust array dimensions at pipeline creation time.

Device Limits and Pipeline Creation

Vulkan enforces strict hardware bounds on the shared memory an individual workgroup can claim. During pipeline creation, the driver validates the pipeline's memory footprint against the device's limits:

  • maxComputeSharedMemorySize: Queried via VkPhysicalDeviceLimits, this property defines the maximum total bytes of workgroup memory available to a single compute workgroup. On modern desktop GPUs, this typically ranges between 32 KB and 64 KB.
  • Failures at Creation: If the total size of all variables marked with the Workgroup storage class exceeds maxComputeSharedMemorySize, vkCreateComputePipelines will fail and return an error (such as VK_ERROR_INITIALIZATION_FAILED).

Workgroup Scheduling and Hardware Occupancy

When vkCmdDispatch or vkCmdDispatchIndirect is submitted, the command processor distributes the requested 3D grid of workgroups across the physical execution engines (such as Streaming Multiprocessors on NVIDIA or Compute Units on AMD/Intel).

Allocation happens dynamically at the hardware level per workgroup:

  1. Hardware Reservation: Before a compute unit launches a workgroup, it reserves the required shared memory footprint from its on-chip SRAM cache.
  2. Occupancy Impact: Because physical shared memory per compute unit is finite, a high shared memory allocation per workgroup restricts the number of active workgroups that can reside on that unit simultaneously. This directly limits warp/wavefront occupancy, potentially reducing the GPU's ability to hide memory latency.
  3. Deallocation: When all invocations in a workgroup complete execution, the hardware immediately releases the workgroup’s shared memory allocation, freeing on-chip capacity for pending workgroups in the dispatch queue.

Lifetime and Scope Isolation

Memory allocated for a workgroup exists strictly within the execution lifetime of that specific workgroup. There is no persistence across workgroups or dispatches:

  • Isolation: Workgroups cannot access the shared memory of another workgroup, even if both reside concurrently on the same physical compute unit.
  • Undefined Initial State: Shared memory is uninitialized upon workgroup launch. Reading from it before writing yields undefined behavior.

Synchronization and Coherency

Because invocations within a workgroup execute in lockstep warps or wavefronts asynchronously relative to one another, reads and writes to shared memory require explicit synchronization to avoid race conditions.

SPIR-V and GLSL provide execution and memory barriers to manage consistency:

  • barrier(): Enforces execution synchronization, ensuring all invocations in the workgroup reach the same point in execution.
  • memoryBarrierShared(): Enforces memory ordering, guaranteeing that all prior writes to shared memory by any invocation in the workgroup become visible to subsequent reads.

Without these barriers, the driver and GPU hardware are free to reorder reads and writes, leading to data hazards in shared memory buffers.
