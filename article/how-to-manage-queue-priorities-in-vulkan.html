How to Manage Queue Priorities in Vulkan

Managing execution priorities between compute and graphics workloads in Vulkan requires configuring hardware queue priorities at the device level, utilizing queue submission structures, and leveraging specialized extensions for system-wide prioritization. Because Vulkan abstracts GPU thread scheduling through hardware queues, developers must deliberately partition queues and define priority values during initialization to prevent heavy compute tasks from stalling latency-sensitive graphics rendering.

1. Identify Queue Family Capabilities

Query the physical device to discover supported queue families and their capabilities using vkGetPhysicalDeviceQueueFamilyProperties. Look for distinct queue families that support VK_QUEUE_GRAPHICS_BIT and VK_QUEUE_COMPUTE_BIT. Utilizing an asynchronous, dedicated compute queue family (often lacking graphics capabilities) separate from the main graphics queue family allows the GPU hardware scheduler to alternate tasks effectively based on priority.

2. Configure Relative Priorities at Device Creation

Define execution priorities during logical device creation by configuring VkDeviceQueueCreateInfo.

  • Allocate floating-point priority arrays where each value ranges from 0.0f (lowest priority) to 1.0f (highest priority).
  • Assign the array pointer to VkDeviceQueueCreateInfo::pQueuePriorities.
  • Set higher values (e.g., 1.0f) for the main rendering queue to ensure responsive frame presentation, and lower values (e.g., 0.25f or 0.5f) for background compute operations.

These normalized priorities serve as hints to the underlying GPU hardware scheduler to allocate more execution slots and memory bandwidth to higher-priority queues.

3. Use Global Priority Extensions for System-Level Control

For mission-critical tasks such as VR timewarp, camera tracking, or real-time physics, relative priority hints may be insufficient. Use the VK_KHR_global_priority (or VK_EXT_global_priority) extension to request system-level scheduling priority:

  • Query VkQueueFamilyGlobalPriorityPropertiesKHR to identify supported global priority levels (LOW, MEDIUM, HIGH, or REALTIME).
  • Chain a VkDeviceQueueGlobalPriorityCreateInfoKHR struct to the pNext chain of VkDeviceQueueCreateInfo.
  • Set the globalPriority field to the desired level. Note that elevated priorities like REALTIME typically require elevated operating system permissions.

4. Separate Workload Submissions

Isolate your rendering commands and compute dispatches into separate VkCommandBuffer instances recorded for their respective queues. Use vkQueueSubmit to submit compute work to the lower-priority compute queue and graphics commands to the higher-priority graphics queue. This prevents compute kernels from blocking the graphics pipeline within the same command buffer.

5. Synchronize Execution with Timeline Semaphores

Prevent resource contention and race conditions without stalling the GPU scheduler:

  • Use VkSemaphoreSubmitInfo or timeline semaphores (VK_KHR_timeline_semaphore) to define explicit execution dependencies across different queues.
  • Signal semaphores from the graphics queue when compute input buffers are ready, and wait on compute semaphores in the graphics queue only at the exact pipeline stage where the computed data is needed.
  • Properly execute queue family ownership transfers using buffer or image memory barriers to preserve data integrity across the distinct queues.
