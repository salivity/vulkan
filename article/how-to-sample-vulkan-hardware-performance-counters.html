How to Sample Vulkan Hardware Performance Counters

Accurately sampling hardware performance counters in Vulkan requires leveraging specialized API extensions to capture low-level metrics directly from the GPU. This process involves enabling the performance query extension, identifying and configuring target hardware counters, acquiring an exclusive profiling lock, wrapping workload execution within query pool commands, and reading back the resulting data. Following a structured profiling workflow ensures metrics such as cache utilization, pipeline stall cycles, and shader unit activity are measured without interference from dynamic power scaling or asynchronous workload overlap.

1. Enable the Required Extensions

Direct hardware counter sampling is provided by the VK_KHR_performance_query device extension, which relies on VK_KHR_get_physical_device_properties2 at the instance level.

When creating the logical device, pass a VkPhysicalDevicePerformanceQueryFeaturesKHR structure chained to VkDeviceCreateInfo::pNext with performanceCounterQueryPools set to VK_TRUE. Additionally, check VkPhysicalDevicePerformanceQueryPropertiesKHR to determine the maximum number of passes required to capture the counters you plan to use.

2. Enumerate and Select Performance Counters

Hardware counters vary across vendors (AMD, NVIDIA, Intel, ARM, Qualcomm). To find available counters on a specific queue family:

  1. Call vkEnumeratePhysicalDeviceQueueFamilyPerformanceQueryCountersKHR to retrieve the total count and properties (VkPerformanceCounterKHR) of available metrics.
  2. Inspect the returned descriptions, metrics (such as percentages, bytes, or cycles), and underlying storage formats (float32, float64, uint32, or uint64).
  3. Select the indices of the counters you need. If the selected combination exceeds the hardware's internal simultaneous monitoring resources, the implementation will require multiple passes to record the data.

3. Initialize the Performance Query Pool

Create a VkQueryPool configured for performance queries:

VkQueryPoolPerformanceCreateInfoKHR perfPoolInfo = {
    .sType = VK_STRUCTURE_TYPE_QUERY_POOL_PERFORMANCE_CREATE_INFO_KHR,
    .queueFamilyIndex = targetQueueFamilyIndex,
    .counterIndexCount = selectedCounterCount,
    .pCounterIndices = selectedCounterIndices
};

VkQueryPoolCreateInfo poolInfo = {
    .sType = VK_STRUCTURE_TYPE_QUERY_POOL_CREATE_INFO,
    .pNext = &perfPoolInfo,
    .queryType = VK_QUERY_TYPE_PERFORMANCE_QUERY_KHR,
    .queryCount = numberOfQueriesToAllocate
};

vkCreateQueryPool(device, &poolInfo, NULL, &perfQueryPool);

4. Acquire the Profiling Lock

To guarantee accurate and stable metrics, Vulkan requires exclusive hardware access during counter collection. Dynamic frequency scaling (boost clocks) and concurrent OS processes can severely distort results.

Before submitting command buffers containing performance queries, acquire the profiling lock:

VkAcquireProfilingLockInfoKHR lockInfo = {
    .sType = VK_STRUCTURE_TYPE_ACQUIRE_PROFILING_LOCK_INFO_KHR,
    .timeout = 1000000000 // 1 second timeout
};

vkAcquireProfilingLockKHR(device, &lockInfo);

The profiling lock stabilizes clock frequencies and restricts other applications from changing the GPU state. Always release the lock via vkReleaseProfilingLockKHR once query recording and submission are complete.

5. Record Queries Around Command Execution

Insert the performance query boundaries around the target commands inside your command buffer:

  1. Reset the query pool using vkCmdResetQueryPool or vkResetQueryPoolEXT.
  2. Call vkCmdBeginQuery(commandBuffer, perfQueryPool, queryIndex, 0).
  3. Record the draw, dispatch, or transfer operations you wish to analyze.
  4. Call vkCmdEndQuery(commandBuffer, perfQueryPool, queryIndex).

If the selected counter set requires multiple passes (indicated by VkPhysicalDevicePerformanceQueryPropertiesKHR), the command sequence must be submitted and executed identically across that exact number of passes, passing the current pass index into the query commands where required.

6. Synchronize and Retrieve Results

Because GPU execution is asynchronous, counters cannot be read accurately until the GPU signals completion:

  1. Use a fence or pipeline barrier to wait until the submitted command buffer completes.
  2. Retrieve the results into a buffer containing an array of VkPerformanceCounterResultKHR structures using vkGetQueryPoolResults:
vkGetQueryPoolResults(
    device,
    perfQueryPool,
    firstQuery,
    queryCount,
    dataSize,
    pData,
    stride,
    VK_QUERY_RESULT_WAIT_BIT
);
  1. Parse each result union according to the data type defined in the corresponding VkPerformanceCounterKHR description.

Practices for Measurement Accuracy

  • Insert Barriers for Isolation: GPU architectures execute commands out of order or concurrently across execution units. Place full execution barriers (vkCmdPipelineBarrier) before vkCmdBeginQuery and after vkCmdEndQuery to prevent adjacent pipeline stages from leaking into the sample window.
  • Warm-up Iterations: Perform several unmeasured passes before initiating counter collection to ensure caches, pipeline states, and descriptor bindings are populated, avoiding cold-start latency artifacts.
  • Minimize Profiling Overhead: Keep query spans targeted to specific operations (such as a compute dispatch or a specific subpass) rather than wrapping entire frame graphs, reducing CPU overhead and counter overflow risks.
