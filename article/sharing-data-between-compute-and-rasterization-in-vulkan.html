Sharing Data Between Compute and Rasterization in Vulkan

In Vulkan, sharing data between compute pipelines and rasterization pipelines occurs directly within device memory without requiring host-side intervention or memory duplication. Because Vulkan features an explicit, unified memory model, developers can allocate resources—such as buffers and images—that serve as inputs and outputs across different pipeline types. This article breaks down the primary mechanisms that facilitate this seamless data transfer, including dual-usage flags, synchronization barriers, layout transitions, and queue family ownership transfers.

Dual-Usage Resource Creation

The foundation of sharing data directly between compute and rasterization stages lies in Vulkan's resource creation model. Both VkBuffer and VkImage objects can be configured with multiple usage flags via their respective creation information structs (VkBufferCreateInfo and VkImageCreateInfo).

  • Buffers: A buffer can be designated for compute compute writing and rasterization vertex fetching simultaneously by combining flags such as VK_BUFFER_USAGE_STORAGE_BUFFER_BIT (written by a compute shader) and VK_BUFFER_USAGE_VERTEX_BUFFER_BIT (read by the vertex input assembly). This enables GPU-driven geometry processing, such as compute-based mesh culling or procedural vertex generation.
  • Images: An image can be created with VK_IMAGE_USAGE_STORAGE_BIT (for compute shader reads/writes) alongside VK_IMAGE_USAGE_SAMPLED_BIT (for fragment shader texturing) or VK_IMAGE_USAGE_COLOR_ATTACHMENT_BIT (for direct rendering output).

By allocating the underlying VkDeviceMemory once and binding it to these multi-purpose resources, data written by one pipeline is immediately available in-place for the other.

Pipeline Barriers and Memory Synchronization

While resources reside in the same memory, GPUs execute workloads asynchronously. To safely read data generated by a compute shader inside a rasterization stage—or vice versa—developers must enforce execution and memory dependencies using pipeline barriers (vkCmdPipelineBarrier or the modernized vkCmdPipelineBarrier2).

A pipeline barrier defines:

  1. Source and Destination Stages: It dictates that the source stage (e.g., VK_PIPELINE_STAGE_COMPUTE_SHADER_BIT) must complete its work before the destination stage (e.g., VK_PIPELINE_STAGE_VERTEX_SHADER_BIT or VK_PIPELINE_STAGE_FRAGMENT_SHADER_BIT) begins reading.
  2. Access Masks: It ensures memory caches are flushed and invalidated. For instance, a barrier will transition cache writes from VK_ACCESS_SHADER_WRITE_BIT in the compute stage to VK_ACCESS_SHADER_READ_BIT or VK_ACCESS_VERTEX_ATTRIBUTE_READ_BIT in the rasterization stages, preventing Read-After-Write (RAW) data hazards.

Image Layout Transitions

Textures and render targets require specific hardware-optimized memory layouts depending on how they are accessed. Compute shaders typically access images in VK_IMAGE_LAYOUT_GENERAL, whereas fragment shaders read sampled images most efficiently from VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL.

Through an image memory barrier, Vulkan handles the transition between these layouts. When a compute pipeline finishes writing to an image, the barrier changes the image layout from VK_IMAGE_LAYOUT_GENERAL to the appropriate rasterization layout, handling any required cache flushing and data tiling conversions under the hood.

Queue Family Ownership Transfers

Vulkan enables compute workloads to run either on the same queue as the graphics pipeline or asynchronously on dedicated compute queues. How resources are shared depends on the queue design:

  • Concurrent Sharing (VK_SHARING_MODE_CONCURRENT): Resources can be accessed by multiple queue families simultaneously without explicit ownership transfers, though this can sometimes introduce hardware overhead.
  • Exclusive Sharing (VK_SHARING_MODE_EXCLUSIVE): Resources are owned by one queue family at a time for optimal performance. To pass a buffer or image from a dedicated compute queue to a graphics queue for rasterization, an explicit queue family ownership transfer must be executed. This is accomplished using a pair of pipeline barriers: one released by the compute queue and one acquired by the graphics queue.
