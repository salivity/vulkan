Vulkan Large BLAS Memory Footprint Explained

Building large Bottom-Level Acceleration Structures (BLAS) in the Vulkan API introduces significant GPU memory implications that can quickly exhaust VRAM if not properly managed. This article breaks down the primary drivers of this memory footprint—including peak scratch buffer demands, pre-compaction storage padding, and memory fragmentation—while detailing the architectural strategies required to optimize memory consumption during the acceleration structure build process.

Dual Memory Requirements: Result vs. Scratch Buffers

When constructing a BLAS, Vulkan requires two distinct memory allocations determined by querying vkGetAccelerationStructureBuildSizesKHR:

  1. Result Acceleration Structure Memory: The physical buffer space where the final spatial hierarchy (often a Bounding Volume Hierarchy, or BVH) resides.
  2. Scratch Buffer Memory: A temporary workspace (buildScratchSize) used by the GPU to sort primitives, compute bounding boxes, and construct node trees.

For massive geometry sets, the scratch buffer requirement can equal or exceed the size of the final acceleration structure. Because scratch memory must be device-local and strictly aligned, concurrently building multiple large BLAS instances can cause extreme, transient memory spikes that lead to out-of-memory (OOM) errors.

Build Flags and Initial Over-Allocation

The memory size reported for the final BLAS depends heavily on the build flags specified in VkAccelerationStructureBuildGeometryInfoKHR:

  • VK_BUILD_ACCELERATION_STRUCTURE_PREFER_FAST_TRACE_BIT_KHR: Directs the driver to generate higher-quality BVH trees (e.g., deeper trees with primitive splitting), increasing both build scratch usage and the final structure's memory footprint to maximize run-time ray intersection performance.
  • VK_BUILD_ACCELERATION_STRUCTURE_PREFER_FAST_BUILD_BIT_KHR: Minimizes tree depth and construction time, resulting in a lighter initial footprint at the expense of runtime traversal performance.

Regardless of the chosen strategy, the driver calculates worst-case buffer requirements before construction begins. Consequently, the initial memory footprint represents an upper bound rather than the actual amount of data the hierarchy requires.

The Impact of Acceleration Structure Compaction

To reclaim the unused space allocated by worst-case estimates, Vulkan provides a compaction mechanism via VK_BUILD_ACCELERATION_STRUCTURE_ALLOW_COMPACTION_BIT_KHR.

Without compaction, large BLAS instances retain significant internal padding. With compaction enabled, developers must:

  1. Build the BLAS into an initial, conservatively sized buffer.
  2. Query the actual compacted size using vkCmdWriteAccelerationStructuresPropertiesKHR.
  3. Allocate a new, smaller buffer based on that query.
  4. Execute vkCmdCopyAccelerationStructureKHR with VK_COPY_ACCELERATION_STRUCTURE_MODE_COMPACT_KHR.
  5. Free the original buffer and scratch memory.

Compaction typically reduces the permanent memory footprint of a large BLAS by 25% to 55%. However, this optimization temporarily increases peak memory usage because both the original uncompacted structure and the new compacted structure must briefly coexist in VRAM.

Memory Fragmentation and Sub-Allocation

Creating individual VkBuffer and VkDeviceMemory allocations for each large BLAS exacerbates memory fragmentation, leading to premature allocation failures under tight memory budgets. High-performance Vulkan implementations avoid this by sub-allocating both scratch and result buffers from dedicated memory pools managed by custom allocators.

Sub-allocation also simplifies the reuse of scratch space: rather than allocating separate scratch buffers for every mesh, applications can allocate a single global scratch buffer sized to the largest individual BLAS build in the scene, sequentially reusing it across builds to drastically curb memory bloat.
