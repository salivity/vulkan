Vulkan POSIX File Descriptor Semaphores for IPC

POSIX file descriptor semaphores in Vulkan bridge native Unix-like operating system handles with GPU hardware synchronization, enabling independent processes to safely coordinate rendering operations on shared GPU resources. By exporting and importing synchronization payloads across processes using standard Unix domain sockets, separate rendering pipelines can sequence work on the GPU without costly CPU-side stalls or out-of-order execution bugs.

What Are POSIX File Descriptor Semaphores?

In Vulkan, synchronization is primarily managed via binary and timeline semaphores (VkSemaphore). Standard semaphores exist entirely within the context of a single VkDevice and process. POSIX file descriptor semaphores extend these primitives by leveraging the VK_KHR_external_semaphore and VK_KHR_external_semaphore_fd extensions.

These extensions enable a Vulkan driver to associate the internal GPU sync point (such as a Linux sync file or drm_syncobj) with a standard POSIX file descriptor (int). Once represented as a file descriptor, the semaphore payload can cross process boundaries using standard Linux Inter-Process Communication (IPC) mechanisms.

The Need for Inter-Process Synchronization

Complex graphics architectures—such as Wayland compositors, multi-process web browsers like Chromium, and OpenXR runtimes—isolate user-facing logic, rendering engines, and final display composition into distinct operating system processes.

While shared textures and buffers can be mapped into multiple processes via external memory extensions (VK_KHR_external_memory_fd), memory sharing alone does not guarantee execution order. If Process A renders into an off-screen buffer and Process B composites that buffer onto the screen, Process B must not read the buffer before Process A completes its rendering passes. POSIX file descriptor semaphores provide the low-level signal mechanism required to enforce this sequence directly on the GPU timeline.

How Inter-Process Synchronization Works in Vulkan

The synchronization lifecycle involves four fundamental steps: configuration, export, IPC transmission, and importing.

1. Creation and Export

The producer process creates a semaphore configured with an exportable handle type:

VkExportSemaphoreCreateInfo exportInfo = {
    .sType = VK_STRUCTURE_TYPE_EXPORT_SEMAPHORE_CREATE_INFO,
    .handleTypes = VK_EXTERNAL_SEMAPHORE_HANDLE_TYPE_OPAQUE_FD_BIT
};

VkSemaphoreCreateInfo semaphoreInfo = {
    .sType = VK_STRUCTURE_TYPE_SEMAPHORE_CREATE_INFO,
    .pNext = &exportInfo
};

VkSemaphore producerSemaphore;
vkCreateSemaphore(device, &semaphoreInfo, NULL, &producerSemaphore);

After submitting a command buffer that will signal this semaphore, the producer extracts the file descriptor using vkGetSemaphoreFdKHR:

int fd = -1;
VkSemaphoreGetFdInfoKHR getFdInfo = {
    .sType = VK_STRUCTURE_TYPE_SEMAPHORE_GET_FD_INFO_KHR,
    .semaphore = producerSemaphore,
    .handleType = VK_EXTERNAL_SEMAPHORE_HANDLE_TYPE_OPAQUE_FD_BIT
};

vkGetSemaphoreFdKHR(device, &getFdInfo, &fd);

2. File Descriptor Transfer

File descriptors cannot be shared simply by passing their integer values, as file descriptor tables are local to each process. The producer transmits the descriptor across a UNIX domain socket using sendmsg() with an SCM_RIGHTS control message. The kernel duplicates the underlying open file description into the consumer process's descriptor table.

3. Importing the File Descriptor

The consumer process receives the file descriptor via recvmsg() and imports it into a locally allocated VkSemaphore using vkImportSemaphoreFdKHR:

VkImportSemaphoreFdInfoKHR importInfo = {
    .sType = VK_STRUCTURE_TYPE_IMPORT_SEMAPHORE_FD_INFO_KHR,
    .semaphore = consumerSemaphore,
    .flags = 0, // Or VK_SEMAPHORE_IMPORT_TEMPORARY_BIT
    .handleType = VK_EXTERNAL_SEMAPHORE_HANDLE_TYPE_OPAQUE_FD_BIT,
    .fd = receivedFd
};

vkImportSemaphoreFdKHR(device, &importInfo);

4. GPU-Side Waiting

The consumer process binds the imported semaphore to the pWaitSemaphores array of its own VkSubmitInfo or VkPresentInfoKHR. The GPU driver holds back the consumer's queue execution until the producer's GPU hardware operations signal the underlying sync primitive. Neither process blocks the CPU during this exchange.

Handle Types: Opaque FD vs. Sync FD

Vulkan supports different handle abstractions through VkExternalSemaphoreHandleTypeFlagBits:

  • VK_EXTERNAL_SEMAPHORE_HANDLE_TYPE_OPAQUE_FD_BIT: Represents driver-specific synchronization primitives (commonly Linux drm_syncobj). This handle represents the semaphore entity itself and can often be signaled and waited on repeatedly, depending on whether it is imported permanently or temporarily.
  • VK_EXTERNAL_SEMAPHORE_HANDLE_TYPE_SYNC_FD_BIT: Maps directly to a Linux sync file descriptor (/dev/sync). A sync file descriptor is a single-shot, write-once synchronization fence. Exporting a sync FD transfers the current pending payload of the semaphore, and importing it is typically treated as a temporary payload transfer.

Choosing between opaque descriptors and sync file descriptors depends on whether the system requires persistent sync pipelines (common in compositors using sync objects) or explicit, per-frame synchronization tracking (common in Android and Linux explicit sync workflows).
